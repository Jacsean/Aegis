# CHECKLIST R2 — 笔记应用数据存储（第七维示范例）

> 这份样例演示**两件事同时合格**该长什么样：
> ①**第七维**（外部参照标注 + 未覆盖方向）；②**五元素**（从哪来 / 不问会怎样 / 你该怎么判断 / 选项后果 / 我可能没问对）。
> 完整的一份 R2 还应有 A/B/C/D 四类问题，见 `CHECKLIST-demo-align-R2.md`。
>
> 场景：用户说「想做一个本地优先的笔记应用，能在手机和电脑之间同步」。

---

## 3. 数据存在哪里？

**从哪来：** 你说的是「本地优先」+「手机电脑之间同步」。这两句放在一起有个矛盾：既然要同步，那就得有一份东西在两边之间跑。所以「本地」到底指什么，得先问清。

**不问会怎样：** 如果我理解成"云为主、本地只是缓存"，你以后断网打不开自己的笔记——而这恰好是你说"本地优先"时想避免的事。

**你该怎么判断：** 想一个具体场景：你在高铁上没信号，打开这个应用，你觉得应该能正常写字吗。

> 依据：[检索] 少数派 2025-03《八款双链笔记横评》—— 7 款默认本地存储，云端仅作备份
> 依据：[检索] Obsidian 官方文档 Sync 章节 —— 云端为付费增值项，本地为默认
> 依据：[推荐] 单人起步阶段倾向纯本地 + 手动导出（无出处，基于复杂度判断）
> 依据：[无参照] 多设备冲突的自动合并策略，未找到适配小团队的公开资料

A. 纯本地文件（Markdown 存本地目录）
   后果：断网完全可用，数据是你的；但多设备要自己拷，冲突要手工解决
B. 本地为主 + 可选云同步（本地是真相，云是副本）
   后果：两边都好；但要设计"谁是真相"，冲突时以哪边为准
C. 云端为主（服务端存储，本地只缓存）
   后果：多设备无缝；但断网受限，且你要维护服务端
D. 其他：_______________

**我的倾向：** B。因为你说了「本地优先」，而 A 又不满足「手机电脑同步」这个明确要求。

## 4. 多设备同时改同一条笔记，怎么办？

**从哪来：** 这是第 3 条选 B 之后必然冒出来的问题。你原话里没提冲突——但「手机和电脑同步」一旦成立，两边同时改就是迟早的事。

**不问会怎样：** 存储层会按"最后保存的那份赢"来写。等你真遇到两边同时改，会发现一篇笔记凭空少了一半内容，而且找不回来。到那时候改，整套存储要推倒重做。

**你该怎么判断：** 想一下你的真实用法：你会在手机上写一半，然后在电脑上接着写同一篇吗？如果会，选简单方案就会丢东西。

> 依据：[检索] CRDT.tech 文档 —— Yjs / Automerge 是当前主流的两套实现
> 依据：[检索] Ink & Switch 2019《Local-first software》—— 提出本地优先的七条理想
> 依据：[推荐] 起步阶段用「后写覆盖 + 保留版本历史」，比上 CRDT 简单一个数量级（无出处）
> 依据：[无参照] 移动端后台同步的系统限制（iOS 后台任务、Android 电池优化），未找到系统对比

A. 后写覆盖（最后保存的那份赢），冲突时保留旧版本供你手动找回
   后果：简单，一周能做完；但两人同时改会丢一份，靠版本历史兜底
B. 逐段落合（同一篇里不同段落能各自保留）
   后果：体验好很多；但实现复杂度跳一级，要设计段落级的冲突检测
C. CRDT（无冲突复制数据类型，数学上保证合并后一致）
   后果：最省心，业界领先产品在用；但学习成本高，库的体积和兼容性都要评估
D. 其他：_______________

**我的倾向：** A 起步。因为 B 和 C 的前提是"你真的会多设备同时编辑"，而这需要先有真实使用数据。

**我可能根本没问对：** 上面三个选项都是技术手段。如果你其实想说「我一个人用，根本不会同时改，别在这上面花时间」，那这整条就不该问，请直接这么说。

## 未覆盖方向

| 方向 | 为什么没列为选项 | 要采用还需了解什么 |
|---|---|---|
| CRDT 本地优先 + P2P 直连（设备间不经过服务器） | 复杂度最高；需要 NAT 穿透、设备发现，1 人 2 周做不完 | Syncthing / libp2p 的工作方式、移动端后台保活限制 |
| 纯云端 + 服务端合并（如 Notion 模式） | 需要后端和账号体系，超出「本地工具」定位 | 服务端成本、离线可用性方案、数据归属问题 |
| 用 Git 仓库做同步（每台设备一个工作副本） | 冲突解决对非技术用户不友好，且大文件性能差 | Git 的冲突提示能否做成人话、自动提交策略 |
| 文件系统级同步（Dropbox / iCloud 盘） | 委托给系统，自己不控制冲突 | 各家同步盘的冲突文件命名规则、延迟特性 |

> 关于「离线优先 vs 云端」这个方向，Ink & Switch 的《Local-first software》给了很好的框架，
> 但它是 2019 年的文章，此后工具生态有变化，我没有核对新进展。
