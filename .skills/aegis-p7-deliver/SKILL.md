# Aegis P7 Deliver

## Overview

把"我做完的东西"变成"别人能用的东西"。

核心原则：**一个没参与开发的人，只看这份说明，能自己跑起来并用起来。**

P6 是给 agent 的归档，P7 是给使用者的交付。读者不同，写法就不同。

## When to Use

- P5 校验通过、P6 归档完成，准备交付
- 要写 RELEASE 说明
- 用户问"怎么用"

## 铁律：交付必须真跑一遍

**写 RELEASE 时禁止凭代码阅读想象步骤。**

必须做一次冒烟验证：干净环境 + 严格照抄文档命令 + 从零走到能用，把输出贴进文档。

冒烟失败 → **退回 P4 修**，不是改文档描述来迁就现状。
文档迁就现状 = 把 bug 写成特性。

## 动作

### 1. 先冒烟，后写文档（顺序不能反）

```bash
rm -rf /tmp/smoke && git clone . /tmp/smoke && cd /tmp/smoke
make setup            # 文档里写的安装命令
<文档里写的启动命令>
```

| 项目类型 | 验证什么 |
|---|---|
| Web 前端 | 打开首页 / 点主流程 / 刷新后状态还在 |
| 后端服务 | 启动 / 健康检查 / 一个真实业务请求 |
| 数据脚本 | 示例数据跑一遍 / 输出内容合理 |
| 库 SDK | `pip install -e .` / 跑示例代码 |

跑出来的输出才是文档的素材。

### 2. 写 `docs/release/RELEASE-v<X.Y.Z>.md`

强制五节：交付了什么 / 怎么用 / 已知限制 / 验证证据 / 签收。

「怎么用」三个硬要求：
1. 命令可直接复制粘贴（占位符单独列表，不混在命令里）
2. 写清前置条件（版本要求，缺了报什么错）
3. 写清成功的样子（"看到 XXX 就是成功"）

「已知限制」**至少 1 条**，写"无"通常说明没认真找。必须写具体场景：

| ❌ | ✅ |
|---|---|
| 性能一般 | 超过 1 万条时列表页加载约 5 秒 |
| 兼容性有限 | 只在 Chrome/Edge 测过，Safari 未验证 |

隐藏限制比限制本身更伤信任。

### 3. 检查"用户的第一分钟"

- 不知道这是什么 → 开头一句话说清用途
- 不知道从哪开始 → 给最小可跑步骤
- 跑失败了 → 给常见错误对照表
- 跑成功了 → 给"接下来可以试什么"

### 4. 请用户签收（要问"能用吗"，不问"满意吗"）

```
v1.3.0 交付完成。约 2 分钟可验证：
1. <命令>
2. <命令>
3. 打开 <地址>，应该看到 <预期>

已知限制 3 条，请特别看第 2 条。

能用请回"可以"；不能用请说现象，我修完重新交付。
```

满意是主观评价，能用是可验证事实。

### 5. 最后才合并分支

```bash
make branch-finish NAME=<任务短名>
```

顺序：过门禁 → 合并 → 打 tag → 清理。
不要先合再签收 —— 签收前发现不能用，main 已被污染。

## 完成标准

- [ ] RELEASE-v<X.Y.Z>.md 存在，五节非空
- [ ] 已知限制 ≥ 1 条且具体
- [ ] 第 5 节有真实输出（不是"已测试"）
- [ ] 第 2 节命令与冒烟一致（能照抄成功）
- [ ] 用户已签收（STATE.md 有 P7 记录）
- [ ] `bash scripts/gate.sh P7` PASS

## Common Mistakes

| 错误 | 纠正 |
|---|---|
| 没跑就写步骤 | 用户第一步就失败，信任归零 |
| 冒烟失败却改文档迁就 | 把 bug 写成特性，退回 P4 修 |
| 已知限制写"无" | 用户踩坑后不再信任其他说明 |
| 命令里混占位符 | 用户复制后报错 |
| 只说"已完成"不说怎么验 | 用户只能盲信 |
| 问"满意吗" | 得到的是客气话 |
| 先合并再签收 | main 被污染 |
| 交付说明写成技术总结 | 使用者不需要知道内部结构 |

## Red Flags — STOP

- "步骤肯定没问题，我看代码写的" → 看过 ≠ 跑过
- "用户很熟，不用写这么细" → 三个月后他自己也不熟了
- "没什么已知限制" → 没找到，通常是因为没测边界
- "先合并，签收回头再说" → 顺序反了
- "用户说'行'就够了" → 要问"你验证过了吗"
- "跑不通就在文档里写'可能需要注意'" → 这是掩盖问题

## 交付之后

新需求一律回 P0.5 意图校准，哪怕只改一句文案。

深层含义（改哪句、给谁看、为什么改）恰恰最容易被误读。
唯一例外：用户明确说"不用讨论"，登记豁免后直接执行。
