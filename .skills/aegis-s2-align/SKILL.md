# Aegis Align

## Overview

在写任何方案、任何需求文档、任何代码之前，先确认**用户到底想要什么**。

核心原则：**没校准的意图 = 猜的。猜的方案 = 废的方案。**

## When to Use

- 用户提出新任务或新要求
- 用户的需求表述有歧义
- agent 发现自己"大概知道要做什么"但说不出细节
- 用户说"你直接做吧"（此时更要先校准）

## 铁律

**禁止在被要求讨论之前给出方案、计划、代码。**

用户说"帮我做个 X"，正确反应不是"好的，方案如下"，
而是"我先确认几个问题，确保我理解对了"。

## 选项式 checklist（核心形式）

**每个关键点都由 agent 提供描述与选项，用户只做选择。**
用户的成本从"表达"降为"识别"。

单条结构（四要素缺一不可）：

```markdown
## <编号>. <关键点，日常语言>

**判断依据：** <怎么判断哪种对>

**我可能理解错的地方：**
- A. <一种理解> → 后果：<...>
- B. <另一种理解> → 后果：<...>
- C. <第三种理解> → 后果：<...>
- D. 其他：_______________   ← 必须有

**我的倾向：** <A/B/C>
```

两条原则：

1. **先给描述或标准** —— 用户据此回复，不是凭空想
2. **列出可能的理解偏差** —— 用户指认正确方向，把"猜错"提前暴露

硬规则：
- 每条 **必须含「其他：___」**（省了 = 逼迫选择，比开放式更糟）
- 实选项 **3-4 个**（2 个易被迫选错，5 个以上认知负担反超开放式）
- 选项 **互斥不重叠**
- 选项是**理解方向**，不是**实现方案**
- 每个选项写清**后果**

## 动作

### 步骤 0：建分支（不可省）

```bash
bash scripts/branch.sh start <任务短名>
```

例如 `bash scripts/branch.sh start user-login` → 建 `feat/user-login`。

### 步骤 1：R1 复述轮

先写 `docs/align/CHECKLIST-<任务>-R1.md`（**选项式**），**交给用户确认 checklist 本身**，
再逐条讨论。

R1 内容：用自己的话把用户的要求复述一遍，让他纠正。

六条固定方向：
1. 我这样理解你的要求，对吗？
2. 你想解决的是这个麻烦吗？
3. 做完之后，你希望看到什么？
4. 这次明确不要的是什么？
5. 我猜这些不在范围内，对吗？
6. 「两轮」你指的是哪种？

写完 `docs/align/ALIGN-<任务>-R1.md` 记录每条的选择与结论。

### 步骤 2：R2 深层轮

先写 `docs/align/CHECKLIST-<任务>-R2.md`（**选项式**），再讨论。

四类问题，每类 2-3 条：
- **A 为什么** — 为什么现在做？不做会怎样？
- **B 成败** — 什么情况算做对？什么情况算搞砸？
- **C 边界** — 选项都不对时怎么办？有没有红线？一次问几条？
- **D 优先级** — 时间紧时先跳哪部分？

写完 `docs/align/ALIGN-<任务>-R2.md`。

### 步骤 3：（条件）R3 边界轮

仅在 R2 发现两种不同理解方向时触发。

### 步骤 4：写汇总

`docs/align/ALIGN-<任务>.md`，按 `99-reference/align-schema.md` 十节结构。
末节请用户签字。

## 小白语言规则（硬要求）

每条 checklist 都必须让**不懂技术的人**能回答。

写完后自检三问：
1. 不懂编程的人能看懂吗？
2. 需要先解释技术名词才能答吗？
3. 用户会回"这什么意思"吗？

任一为"是" → 重写。

**替换示例：**
- ❌ 确认鉴权方案 → ✅ 谁能看到这些内容？没登录能看吗？
- ❌ 确认数据模型 → ✅ 要存哪些信息？每条长什么样？
- ❌ 确认 API 契约 → ✅ 两部分之间怎么传话？传什么？
- ❌ 确认事务一致性 → ✅ 做到一半失败了，前面的要不要撤销？

**允许用技术词的情况**：用户自己先用了；或用户明确要求技术描述。

## 完成标准

- [ ] 分支已建（非 main）
- [ ] R1、R2 的 CHECKLIST 与 ALIGN 记录都存在
- [ ] **每条 checklist 含「其他：___」**
- [ ] **每条至少 3 个方向选项（A/B/C）**
- [ ] checklist 无未解释的技术词
- [ ] 汇总文档十节齐全
- [ ] 用户在汇总末尾签字
- [ ] 文档已登记 `docs/INDEX.md`
- [ ] `bash scripts/gate.sh S2` 输出 PASS

## Common Mistakes

| 错误 | 纠正 |
|---|---|
| 直接给方案 | 铁律六禁止，必须先讨论 |
| **选项里没有「其他」** | 逼迫选择，比开放式更糟；必须有 |
| **只给 A/B 两个选项** | 两个都不完美时被迫选错；给 3 个以上 |
| **选项写成"用 React 还是 Vue"** | 越界替你决定实现方案；只列理解方向 |
| 一轮问完所有问题 | 必须分轮，R2 基于 R1 结论 |
| 讨论完不落文档 | 每轮必须写 ALIGN 记录 |
| checklist 用技术词 | 用户答不了，讨论失效 |
| 讨论完直接设计 | 顺序：S2 → S3（PRD）→ S4（设计） |
| "用户没意见"当确认 | 必须逐条回复 |

## Red Flags — STOP

- "需求很清楚，不用讨论" → 清楚的是你，不是用户
- "先做出来再说" → 做错成本远高于问清成本
- "问太多用户会烦" → 答错方案更烦
- "我猜是这个意思" → 猜就是歧义的来源
- **"选项就这两个，不然问他"** → 恰恰要列全方向 + 其他
- "用户急着要" → 越急越要先确认方向

## 3. 七条铁律（不可违反）

### 铁律一：阶段不可跳

未通过当前阶段的全部出口门禁，**禁止**进入下一阶段。
用户要求跳步时，必须先说明"当前在 Sn，缺 X"，并获得用户**明确豁免**（记入 `STATE.md`）。

### 铁律二：设计前必须可视

**前端类项目的 S4 展开阶段，必须产出可在浏览器打开的 HTML demo，并获用户确认后，才能进入 S6 写业务代码。**
没有 demo 的前端设计 = 没有设计。

### 铁律三：完成必须留证

宣称"完成""修好""通过"时，**必须贴出验证输出**。
"我觉得可以""应该没问题"不算完成，视为未完成。

延伸到 S8：**交付说明里的步骤必须真的照抄跑过一遍。**
没跑过就写文档 = 交付假货。

### 铁律三之二：任务必须留档

**每个任务结束（合并进 main 前）必须写一条开发事件记录**，
记在 `dev/handoff/H-<编号>-<短名>.md`，并在 `dev/HANDOFF.md` 索引加一行。

七要素：时间 / 谁 / 事件 / 为什么这样处理 / 怎么处理的 / **试过什么（成没成）** / 下一步等谁。

- **「试过什么」不许空**：没走过弯路就写「本任务未走过弯路」
- **事实 / 推断 / 未知 分开标**：`〔推断〕`、`〔未知〕`，不标视为事实
- **过期不删**：划掉并指向新条目，因为下个 agent 读到旧结论会把新工作改回去

为什么必须有：**没有这一栏，下一个人（或三个月后的你）会把失败的路重走一遍。**

细则见 `.ai/99-reference/handoff-schema.md`。

### 铁律四：问题必须沉淀

任何调试超过 **15 分钟**、或试错 **2 次以上**、或发现"设计时没考虑到"的情况，
**必须**新建 `docs/incidents/INC-xxxx.md`。

其中 **「预防」一节为必填** —— 没有预防措施的 incident 不算闭环。

### 铁律五：单一真相源

`.ai/*.md` 是规矩的**唯一真相**。
`.skills/`、`adapters/`、`AGENTS.md` 内联段都是**派生物**，由 `make sync` 生成。
禁止手工维护两份内容 —— 这是 token 浪费的根源。

### 铁律六：讨论前置，禁止自作主张

**用户提出任何新要求后，禁止直接给出方案、计划或代码。**

必须先进入 S2 对齐，完成**至少两轮讨论**：

| 轮次 | 目的 | 强制 |
|---|---|---|
| R1 复述轮 | 用自己的话复述，让用户纠正 | ❌ 不可跳 |
| R2 深层轮 | 挖"为什么/什么算失败/什么情况例外" | ❌ 不可跳 |
| R3 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件 |

**每轮开始前必须先产出一份 checklist**，用户确认清单本身后再逐条讨论。
checklist 必须使用**日常语言**——判断标准是：不懂技术的人也能直接回答。

**写清单之前还有一步：调研前置（第七维）。**
顺序是「判定领域 → 征询是否联网调研 → 调研 → 生成清单」。
每个关键点下面必须写清依据来源（`[检索]` / `[推荐]` / `[无参照]`），
清单末尾必须有「未覆盖方向」一节。无联网能力时必须**先告知再询问**，不许静默降级，不许伪装成查过。
详见 `.ai/11-S2-align.md` 的「第零步：调研前置」。

**讨论结论必须落文档**（`docs/align/`），它是 S3 写 PRD 的唯一依据。

> 违反示例：用户说"帮我做个 X"，agent 回"好的，我的方案是……"。
> 正确反应：先建 checklist，复述理解，确认后再谈方案。

---

### 铁律七：概念先定义后使用

**项目中反复使用的词，禁止在未定义的情况下当作已共识使用。**

概念固化的三个挂点（不新增阶段）：

| 挂点 | 动作 | 强制 |
|---|---|---|
| 校准（S2 对齐） | 列出本次工作的新词候选清单，逐个用五元素问用户「这个词你怎么理解」 | ❌ 不可跳 |
| 任务进行中 | 新词出现 → 先命名再讨论；达成一致理解后写入 `docs/CONCEPTS.md`，标 `暂定` | 随发生随做 |
| S7 固化 | 在 handoff 记录写「**新词**」一行（无则写「无」）；有新词的，词条状态要落实（升 `已定` 或保持 `暂定` 并注明待验收） | ❌ 不可跳 |

概念的出现不是在项目一开始就全部涌现（用户原话）——所以固化是常设动作，不是一次性工程。

## 3.2 修订留痕规则（设计被推翻时，三动作同时做）

**推翻或改造任何已成文的设计时，禁止只写新设计、不动旧设计。** 三动作缺一不可：

1. **旧文件头**加状态行：`> 状态：已作废（日期）→ 被〈新路径/新设计〉取代（见 H-xxxx）`
2. **INDEX**（`docs/INDEX.md`）状态列同步更新——agent 找文档先查索引，作废的在索引上显形
3. **handoff 记录**「怎么处理的」写明「旧设计 XX 已作废，指向 YY」

设计文档头部必须有状态行（`定稿` / `暂定` / `已作废→指向`），状态词沿用概念表四态。
门禁对「缺状态行」「已作废却无指向」告警（铁律五的配套，。

## 3.1 分支铁律（配套铁律六）

**每个新任务或新要求，必须建立独立分支。**

```
main/master  ← 始终保持可运行
  └── feat/<任务短名>   新功能
  └── fix/<任务短名>    修问题
  └── docs/<任务短名>   文档
```

- 开始任务：`make branch NAME=<任务短名>`
- 完成任务：过完门禁 → `make branch-finish NAME=<任务短名>`
- **禁止**在 main 上直接改动（`gate.sh` 会拦截）
- 分支名不合规 → 门禁 FAIL

## 分工原则（最高约束，2026-10-21 定）

- **用户提供应用方向和需求，agent 基于这个展开设计，并用用户的要求设计验证场景去验证设计。**
- **禁止让用户既提要求、又去设计**——设计是 agent 的职责，用户不承担。
- agent 内部的机制选择（实现路径、内部命名、工具取舍）由 agent 自行裁决并记录理由，**不得包装成「请你裁决」上交**；需要用户拍板的，只提方案性问题（见「决策权归属」）。
- 用户说「不确定」时，agent 不得替用户拍板，也不得把问题原样扔回——正确动作：参考同行经验、或自行推演并自行设计场景验证后给答复。

---

## 分支与版本

- 每个新任务 / 新要求，**必须新建分支**，不直接改主分支。
- 完成任务后提交、走门禁、合并回主分支，并清理分支。
- 分支命名：`<类型>/<任务短名>`，短名用连字符。

---

## 决策权归属（重要）

**agent 不得替用户做以下决定**，必须停下来问：

- 技术栈选型（语言 / 框架 / 数据库）
- 是否引入新依赖
- 架构分层方式
- 前端视觉风格、布局、配色、交互方式
- 需求范围增减
- 是否删除/重写已有代码

> 这些是"方案性问题"，不是"实现细节"。方案由用户定，实现由 agent 做。

## 代码

- 注释：中文。
- 设计取向：拒绝过度设计，优先简单可读。
- 依赖策略：能不加就不加；加之前说明用途与替代方案。
- 命名：语义清晰优先于简短。
- 错误处理：明确处理，禁止空 catch 吞异常。

## 环境

- **Python 项目必须使用 `.venv`**，不用系统 Python。
  - 所有命令以 `.venv/bin/python` 显式调用，不依赖 `activate`。
  - 依赖固定在 `pyproject.toml`（或 `requirements.txt` + 锁定版本）。
- Node 项目统一用 `pnpm`。
- 环境必须可一条命令重建（`make setup`）。

## 文档

- Markdown 格式，结构化（标题 / 表格 / 清单）。
- 每篇开头一句话说明"解决什么问题"。
- 新增文档必须登记进 `docs/INDEX.md`。
- 文档之间用编号互相引用（ADR-xxxx、INC-xxxx），形成可追溯链。

## 交付

- 每次交一个**可运行的最小版本**，不交半成品。
- 交付必须说明：怎么用 / 已知限制 / 下一步。
- 重要决策落文档，不留在聊天记录里。

## 明确不要做的

- ❌ 未经确认就生成方案和计划
- ❌ 前端不先给 HTML demo 就写代码
- ❌ 说"应该能跑"代替实际验证
- ❌ 大范围重构或删文件前不确认
- ❌ 重复造轮子而不先查 `docs/incidents/` 与 `docs/adr/`

## 外部经验（参考同行）

- **先征询再调研**：不要自己决定要不要联网查。先说「我判断这是 X 领域，要不要查同类做法？」
- **不许静默降级**：没有联网能力时，必须**先告知**「我这边没联网，拿不到专业文献」，**再问**「要不要用训练数据里的印象给参照，还是这次不需要同行经验」。
- **四个标记要分清**：
  - `[检索]` 有出处的（必须写清哪个站点/文献/时间）
  - `[推荐]` 无出处的倾向（要写明"无出处"）
  - `[无参照]` 既无事实也无倾向
  - `[未覆盖]` 知道有但没列为选项 → 写进清单末尾「未覆盖方向」
- **禁止「业界普遍 / 通常认为 / 大家都」这类无出处断言**。这类话读起来像事实，其实是语气，用户无法反驳。
- **「未覆盖方向」不能是空的**。空等于声称选项已穷尽，而那几乎总是假的。想不出来就写实话：「我不确定是否还有别的方向」。

## 目录（一句话列，供会话启动时快速扫）

| 词 | 一句话 |
|---|---|
| 项目 | 可独立交付的整体，装全部任务 |
| 任务 | 开分支、过门禁、写记录的一次工作 |
| 会话 | agent 与人交互的媒介，多轮构成一个任务 |
| 工作项 | 在结构上流动的最小信息单元（不是结构层）|
| 共识 | agent 从工作项中提炼出、并被用户确认的理解 |
| 地点 | 事情发生或作用于哪里（不是文件存放处）|
| 分支（血缘）| 一组记录构成的一条来龙去脉（不是 git 分支）|
| 记录 | 一件事的完整留档，一个文件一条 |
| 索引 | 指向记录的定位表，只放定位信息 |
| 事件 | 六要素能补全的、已被记录的一个发生 |
| 来龙去脉 | 一件事的因果链，靠血缘走通 |
| 阶段 | 由出口门禁把关的工作段落 |
| 制品 | 阶段出口必须存在的固定产物 |
| 门禁 | 阶段出口的机械检查，不过不许前进 |
| git 分支 | 隔离一次任务改动的版本库分支（用完就合）|
| 版本 | 对外发布标识，只在合并进 main 时变 |
| 讨论 | 就一个待定判断点交换判断，让分歧显形 |
| 校准 | S2 对齐的两轮讨论，把意图对齐到能写 PRD（旧措辞见本词条修订记录）|
| 签字 | 使用者对阶段出口的明确确认，附原话 |
| 追问 | 紧接上一问、把含糊处逼具体的问 |
| 五元素 | 提问按需带的五个部件（从哪来/不问会怎样/怎么判断/选项后果/可能没问对）|
| 交付 | 交给使用者并让他能自己用起来 |
| 验收 | 使用者按自己的标准判断能不能用 |
