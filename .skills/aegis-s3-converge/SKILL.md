# Aegis S3 Ideate

## Overview

把"想要什么"变成"用户签字确认过的需求"。
**本阶段禁止写任何业务代码，禁止进入设计。**

核心原则：**没签字的需求 = 没需求。**

## When to Use

- 用户说"做个 X""加个功能"，但还没讨论清楚
- PRD 存在但未获用户确认
- 需求含糊、有歧义、或用户自己也没想清

## 动作

### 1. 分轮提问（不要一次问完）

**第一轮 · 目标与边界**
- 解决谁的什么问题？
- 什么算成功（可测）？
- **明确不做什么？**（非目标）

**第二轮 · 用户与场景**
- 谁用、什么情况下用？
- 主流程一步步是什么？

**第三轮 · 约束**
- 技术限制、时间限制、与现有系统关系？

**第四轮 · 界面（前端项目必问）**
- 有哪几个关键界面？
- 每个界面的核心元素？
- 交互风格偏好？

> 一次问 3-5 个。用户答得含糊就追问到具体。

### 2. 写 PRD

按 `.ai/99-reference/prd-schema.md` 六节，写入 `docs/prd.md`。

### 3. 逐条核对（关键，不可省）

不要只说"PRD 已生成"。必须逐条念：

```
PRD 已写入 docs/prd.md，请逐条确认：

1. 目标：<...>
2. 非目标：<...>
3. 关键界面：<...>（决定 S4 出几个 demo）
4. 验收标准：
   - <可测标准>

是否正确？需要调整请指出。
```

### 4. 等待明确肯定词

判定标准：用户说出「确认」「可以」「没问题」「就这样」等**明确肯定**。
模糊回应（"嗯""看起来行""差不多"）**不算确认**，需再次询问。

## 完成标准

- [ ] PRD 六节齐全，非目标非空且具体
- [ ] 验收标准每条可测
- [ ] 前端项目：关键界面清单非空
- [ ] `bash scripts/gate.sh S3` 输出 PASS
- [ ] 用户给出明确肯定词
- [ ] 签字已写入 `STATE.md`

## Common Mistakes

| 错误 | 纠正 |
|---|---|
| 跳过提问直接写 PRD | 需求跑偏，后期全返工 |
| 非目标写"暂不考虑其他" | 等于没写，必须写具体不做什么 |
| 验收标准写"体验良好" | 不可测，改成可观察的指标 |
| 生成 PRD 后不逐条核对 | 用户没真读，问题延后暴露 |
| 把"嗯"当确认 | 必须等明确肯定词 |

## Red Flags — STOP

- "需求已经很清楚了，不用问" → 清楚的是你，不是用户
- "先写代码，PRD 后面补" → 违反铁律一
- "用户没回，应该默认同意" → 绝不允许

## 与通用框架的关系

但**产出必须落 `docs/prd.md` 六节结构**，且**不能替代逐条核对与签字**。

## 同步块（真相源摘录，会话必读）

## 3. 七条铁律（不可违反）

### 铁律一：阶段不可跳

未通过当前阶段的全部出口门禁，**禁止**进入下一阶段。
用户要求跳步时，必须先说明"当前在 Sn，缺 X"，并获得用户**明确豁免**（记入 `STATE.md`）。

### 铁律二：设计前必须可视

**前端类项目的 S4 展开阶段，必须产出可在浏览器打开的 HTML demo，并获用户确认后，才能进入 S6 写业务代码。**
没有 demo 的前端设计 = 没有设计。

### 铁律三：完成必须留证

宣称"完成""修好""通过"时，**必须贴出验证输出**。
"我觉得可以""应该没问题"不算完成，视为未完成。

延伸到 S8：**交付说明里的步骤必须真的照抄跑过一遍。**
没跑过就写文档 = 交付假货。

### 铁律三之二：任务必须留档

**每个任务结束（合并进 main 前）必须写一条开发事件记录**，
记在 `dev/handoff/H-<编号>-<短名>.md`，并在 `dev/HANDOFF.md` 索引加一行。

七要素：时间 / 谁 / 事件 / 为什么这样处理 / 怎么处理的 / **试过什么（成没成）** / 下一步等谁。

- **「试过什么」不许空**：没走过弯路就写「本任务未走过弯路」
- **事实 / 推断 / 未知 分开标**：`〔推断〕`、`〔未知〕`，不标视为事实
- **过期不删**：划掉并指向新条目，因为下个 agent 读到旧结论会把新工作改回去

为什么必须有：**没有这一栏，下一个人（或三个月后的你）会把失败的路重走一遍。**

细则见 `.ai/99-reference/handoff-schema.md`。

### 铁律四：问题必须沉淀

任何调试超过 **15 分钟**、或试错 **2 次以上**、或发现"设计时没考虑到"的情况，
**必须**新建 `docs/incidents/INC-xxxx.md`。

其中 **「预防」一节为必填** —— 没有预防措施的 incident 不算闭环。

### 铁律五：单一真相源

`.ai/*.md` 是规矩的**唯一真相**。
`.skills/`、`adapters/`、`AGENTS.md` 内联段都是**派生物**，由 `make sync` 生成。
禁止手工维护两份内容 —— 这是 token 浪费的根源。

### 铁律六：讨论前置，禁止自作主张

**用户提出任何新要求后，禁止直接给出方案、计划或代码。**

必须先进入 S2 对齐，完成**至少两轮讨论**：

| 轮次 | 目的 | 强制 |
|---|---|---|
| R1 复述轮 | 用自己的话复述，让用户纠正 | ❌ 不可跳 |
| R2 深层轮 | 挖"为什么/什么算失败/什么情况例外" | ❌ 不可跳 |
| R3 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件 |

**每轮开始前必须先产出一份 checklist**，用户确认清单本身后再逐条讨论。
checklist 必须使用**日常语言**——判断标准是：不懂技术的人也能直接回答。

**写清单之前还有一步：调研前置（第七维）。**
顺序是「判定领域 → 征询是否联网调研 → 调研 → 生成清单」。
每个关键点下面必须写清依据来源（`[检索]` / `[推荐]` / `[无参照]`），
清单末尾必须有「未覆盖方向」一节。无联网能力时必须**先告知再询问**，不许静默降级，不许伪装成查过。
详见 `.ai/11-S2-align.md` 的「第零步：调研前置」。

**讨论结论必须落文档**（`docs/align/`），它是 S3 写 PRD 的唯一依据。

> 违反示例：用户说"帮我做个 X"，agent 回"好的，我的方案是……"。
> 正确反应：先建 checklist，复述理解，确认后再谈方案。

### 铁律七：概念先定义后使用（H-0007，2026-10-21）

**项目中反复使用的词，禁止在未定义的情况下当作已共识使用。**

概念固化的三个挂点（不新增阶段）：

| 挂点 | 动作 | 强制 |
|---|---|---|
| 校准（S2 对齐） | 列出本次工作的新词候选清单，逐个用五元素问用户「这个词你怎么理解」 | ❌ 不可跳 |
| 任务进行中 | 新词出现 → 先命名再讨论；达成一致理解后写入 `docs/CONCEPTS.md`，标 `暂定` | 随发生随做 |
| S7 固化 | 在 handoff 记录写「**新词**」一行（无则写「无」）；有新词的，词条状态要落实（升 `已定` 或保持 `暂定` 并注明待验收） | ❌ 不可跳 |

概念的出现不是在项目一开始就全部涌现（用户原话）——所以固化是常设动作，不是一次性工程。

## 3.2 修订留痕规则（设计被推翻时，三动作同时做）

**推翻或改造任何已成文的设计时，禁止只写新设计、不动旧设计。** 三动作缺一不可：

1. **旧文件头**加状态行：`> 状态：已作废（日期）→ 被〈新路径/新设计〉取代（见 H-xxxx）`
2. **INDEX**（`docs/INDEX.md`）状态列同步更新——agent 找文档先查索引，作废的在索引上显形
3. **handoff 记录**「怎么处理的」写明「旧设计 XX 已作废，指向 YY」

设计文档头部必须有状态行（`定稿` / `暂定` / `已作废→指向`），状态词沿用概念表四态。
门禁对「缺状态行」「已作废却无指向」告警（铁律五的配套，见 H-0021）。

## 3.1 分支铁律（配套铁律六）

**每个新任务或新要求，必须建立独立分支。**

```
main/master  ← 始终保持可运行
  └── feat/<任务短名>   新功能
  └── fix/<任务短名>    修问题
  └── docs/<任务短名>   文档
```

- 开始任务：`make branch NAME=<任务短名>`
- 完成任务：过完门禁 → `make branch-finish NAME=<任务短名>`
- **禁止**在 main 上直接改动（`gate.sh` 会拦截）
- 分支名不合规 → 门禁 FAIL

## 分工原则（最高约束，2026-10-21 定）

- **用户提供应用方向和需求，agent 基于这个展开设计，并用用户的要求设计验证场景去验证设计。**
- **禁止让用户既提要求、又去设计**——设计是 agent 的职责，用户不承担。
- agent 内部的机制选择（实现路径、内部命名、工具取舍）由 agent 自行裁决并记录理由，**不得包装成「请你裁决」上交**；需要用户拍板的，只提方案性问题（见「决策权归属」）。
- 用户说「不确定」时，agent 不得替用户拍板，也不得把问题原样扔回——正确动作：参考同行经验、或自行推演并自行设计场景验证后给答复。

## 分支与版本

- 每个新任务 / 新要求，**必须新建分支**，不直接改主分支。
- 完成任务后提交、走门禁、合并回主分支，并清理分支。
- 分支命名：`<类型>/<任务短名>`，短名用连字符。

---

## 决策权归属（重要）

**agent 不得替用户做以下决定**，必须停下来问：

- 技术栈选型（语言 / 框架 / 数据库）
- 是否引入新依赖
- 架构分层方式
- 前端视觉风格、布局、配色、交互方式
- 需求范围增减
- 是否删除/重写已有代码

> 这些是"方案性问题"，不是"实现细节"。方案由用户定，实现由 agent 做。

## 外部经验（参考同行）

- **先征询再调研**：不要自己决定要不要联网查。先说「我判断这是 X 领域，要不要查同类做法？」
- **不许静默降级**：没有联网能力时，必须**先告知**「我这边没联网，拿不到专业文献」，**再问**「要不要用训练数据里的印象给参照，还是这次不需要同行经验」。
- **四个标记要分清**：
  - `[检索]` 有出处的（必须写清哪个站点/文献/时间）
  - `[推荐]` 无出处的倾向（要写明"无出处"）
  - `[无参照]` 既无事实也无倾向
  - `[未覆盖]` 知道有但没列为选项 → 写进清单末尾「未覆盖方向」
- **禁止「业界普遍 / 通常认为 / 大家都」这类无出处断言**。这类话读起来像事实，其实是语气，用户无法反驳。
- **「未覆盖方向」不能是空的**。空等于声称选项已穷尽，而那几乎总是假的。想不出来就写实话：「我不确定是否还有别的方向」。
