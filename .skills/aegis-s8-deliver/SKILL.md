# Aegis S8 Deliver

## Overview

把"我做完的东西"变成"别人能用的东西"。

核心原则：**一个没参与开发的人，只看这份说明，能自己跑起来并用起来。**

S7 是给 agent 的归档，S8 是给使用者的交付。读者不同，写法就不同。

## When to Use

- S5 找破绽通过、S7 固化完成，准备交付
- 要写 RELEASE 说明
- 用户问"怎么用"

## 铁律：交付必须真跑一遍

**写 RELEASE 时禁止凭代码阅读想象步骤。**

必须做一次冒烟验证：干净环境 + 严格照抄文档命令 + 从零走到能用，把输出贴进文档。

冒烟失败 → **退回 S6 修**，不是改文档描述来迁就现状。
文档迁就现状 = 把 bug 写成特性。

## 动作

### 1. 先冒烟，后写文档（顺序不能反）

```bash
rm -rf /tmp/smoke && git clone . /tmp/smoke && cd /tmp/smoke
make setup            # 文档里写的安装命令
<文档里写的启动命令>
```

| 项目类型 | 验证什么 |
|---|---|
| Web 前端 | 打开首页 / 点主流程 / 刷新后状态还在 |
| 后端服务 | 启动 / 健康检查 / 一个真实业务请求 |
| 数据脚本 | 示例数据跑一遍 / 输出内容合理 |
| 库 SDK | `pip install -e .` / 跑示例代码 |

跑出来的输出才是文档的素材。

### 2. 写 `docs/release/RELEASE-v<X.Y.Z>.md`

强制五节：交付了什么 / 怎么用 / 已知限制 / 验证证据 / 签收。

「怎么用」三个硬要求：
1. 命令可直接复制粘贴（占位符单独列表，不混在命令里）
2. 写清前置条件（版本要求，缺了报什么错）
3. 写清成功的样子（"看到 XXX 就是成功"）

「已知限制」**至少 1 条**，写"无"通常说明没认真找。必须写具体场景：

| ❌ | ✅ |
|---|---|
| 性能一般 | 超过 1 万条时列表页加载约 5 秒 |
| 兼容性有限 | 只在 Chrome/Edge 测过，Safari 未验证 |

隐藏限制比限制本身更伤信任。

### 3. 检查"用户的第一分钟"

- 不知道这是什么 → 开头一句话说清用途
- 不知道从哪开始 → 给最小可跑步骤
- 跑失败了 → 给常见错误对照表
- 跑成功了 → 给"接下来可以试什么"

### 4. 请用户签收（要问"能用吗"，不问"满意吗"）

```
v1.3.0 交付完成。约 2 分钟可验证：
1. <命令>
2. <命令>
3. 打开 <地址>，应该看到 <预期>

已知限制 3 条，请特别看第 2 条。

能用请回"可以"；不能用请说现象，我修完重新交付。
```

满意是主观评价，能用是可验证事实。

### 5. 最后才合并分支

```bash
make branch-finish NAME=<任务短名>
```

顺序：过门禁 → 合并 → 打 tag → 清理。
不要先合再签收 —— 签收前发现不能用，main 已被污染。

## 完成标准

- [ ] RELEASE-v<X.Y.Z>.md 存在，五节非空
- [ ] 已知限制 ≥ 1 条且具体
- [ ] 第 5 节有真实输出（不是"已测试"）
- [ ] 第 2 节命令与冒烟一致（能照抄成功）
- [ ] 用户已签收（STATE.md 有 S8 记录）
- [ ] `bash scripts/gate.sh S8` PASS

## Common Mistakes

| 错误 | 纠正 |
|---|---|
| 没跑就写步骤 | 用户第一步就失败，信任归零 |
| 冒烟失败却改文档迁就 | 把 bug 写成特性，退回 S6 修 |
| 已知限制写"无" | 用户踩坑后不再信任其他说明 |
| 命令里混占位符 | 用户复制后报错 |
| 只说"已完成"不说怎么验 | 用户只能盲信 |
| 问"满意吗" | 得到的是客气话 |
| 先合并再签收 | main 被污染 |
| 交付说明写成技术总结 | 使用者不需要知道内部结构 |

## Red Flags — STOP

- "步骤肯定没问题，我看代码写的" → 看过 ≠ 跑过
- "用户很熟，不用写这么细" → 三个月后他自己也不熟了
- "没什么已知限制" → 没找到，通常是因为没测边界
- "先合并，签收回头再说" → 顺序反了
- "用户说'行'就够了" → 要问"你验证过了吗"
- "跑不通就在文档里写'可能需要注意'" → 这是掩盖问题

## 交付之后

新需求一律回 S2 对齐，哪怕只改一句文案。

深层含义（改哪句、给谁看、为什么改）恰恰最容易被误读。
唯一例外：用户明确说"不用讨论"，登记豁免后直接执行。

## 同步块（真相源摘录，会话必读）

## 3. 七条铁律（不可违反）

### 铁律一：阶段不可跳

未通过当前阶段的全部出口门禁，**禁止**进入下一阶段。
用户要求跳步时，必须先说明"当前在 Sn，缺 X"，并获得用户**明确豁免**（记入 `STATE.md`）。

### 铁律二：设计前必须可视

**前端类项目的 S4 展开阶段，必须产出可在浏览器打开的 HTML demo，并获用户确认后，才能进入 S6 写业务代码。**
没有 demo 的前端设计 = 没有设计。

### 铁律三：完成必须留证

宣称"完成""修好""通过"时，**必须贴出验证输出**。
"我觉得可以""应该没问题"不算完成，视为未完成。

延伸到 S8：**交付说明里的步骤必须真的照抄跑过一遍。**
没跑过就写文档 = 交付假货。

### 铁律三之二：任务必须留档

**每个任务结束（合并进 main 前）必须写一条开发事件记录**，
记在 `docs/internal/handoff/H-<编号>-<短名>.md`，并在 `docs/internal/handoff.md` 索引加一行。

七要素：时间 / 谁 / 事件 / 为什么这样处理 / 怎么处理的 / **试过什么（成没成）** / 下一步等谁。

- **「试过什么」不许空**：没走过弯路就写「本任务未走过弯路」
- **事实 / 推断 / 未知 分开标**：`〔推断〕`、`〔未知〕`，不标视为事实
- **过期不删**：划掉并指向新条目，因为下个 agent 读到旧结论会把新工作改回去

为什么必须有：**没有这一栏，下一个人（或三个月后的你）会把失败的路重走一遍。**

细则见 `.ai/99-reference/handoff-schema.md`。

### 铁律四：问题必须沉淀

任何调试超过 **15 分钟**、或试错 **2 次以上**、或发现"设计时没考虑到"的情况，
**必须**新建 `docs/incidents/INC-xxxx.md`。

其中 **「预防」一节为必填** —— 没有预防措施的 incident 不算闭环。

### 铁律五：单一真相源

`.ai/*.md` 是规矩的**唯一真相**。
`.skills/`、`adapters/`、`AGENTS.md` 内联段都是**派生物**，由 `make sync` 生成。
禁止手工维护两份内容 —— 这是 token 浪费的根源。

### 铁律六：讨论前置，禁止自作主张

**用户提出任何新要求后，禁止直接给出方案、计划或代码。**

必须先进入 S2 对齐，完成**至少两轮讨论**：

| 轮次 | 目的 | 强制 |
|---|---|---|
| R1 复述轮 | 用自己的话复述，让用户纠正 | ❌ 不可跳 |
| R2 深层轮 | 挖"为什么/什么算失败/什么情况例外" | ❌ 不可跳 |
| R3 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件 |

**每轮开始前必须先产出一份 checklist**，用户确认清单本身后再逐条讨论。
checklist 必须使用**日常语言**——判断标准是：不懂技术的人也能直接回答。

**写清单之前还有一步：调研前置（第七维）。**
顺序是「判定领域 → 征询是否联网调研 → 调研 → 生成清单」。
每个关键点下面必须写清依据来源（`[检索]` / `[推荐]` / `[无参照]`），
清单末尾必须有「未覆盖方向」一节。无联网能力时必须**先告知再询问**，不许静默降级，不许伪装成查过。
详见 `.ai/11-S2-align.md` 的「第零步：调研前置」。

**讨论结论必须落文档**（`docs/rfc/`），它是 S3 写 PRD 的唯一依据。

> 违反示例：用户说"帮我做个 X"，agent 回"好的，我的方案是……"。
> 正确反应：先建 checklist，复述理解，确认后再谈方案。

### 铁律七：概念先定义后使用

**项目中反复使用的词，禁止在未定义的情况下当作已共识使用。**

概念固化的三个挂点（不新增阶段）：

| 挂点 | 动作 | 强制 |
|---|---|---|
| 校准（S2 对齐） | 列出本次工作的新词候选清单，逐个用五元素问用户「这个词你怎么理解」 | ❌ 不可跳 |
| 任务进行中 | 新词出现 → 先命名再讨论；达成一致理解后写入 `docs/reference/concepts.md`，标 `暂定` | 随发生随做 |
| S7 固化 | 在 handoff 记录写「**新词**」一行（无则写「无」）；有新词的，词条状态要落实（升 `已定` 或保持 `暂定` 并注明待验收） | ❌ 不可跳 |

概念的出现不是在项目一开始就全部涌现（用户原话）——所以固化是常设动作，不是一次性工程。

## 3.2 修订留痕规则（设计被推翻时，三动作同时做）

**推翻或改造任何已成文的设计时，禁止只写新设计、不动旧设计。** 三动作缺一不可：

1. **旧文件头**加状态行：`> 状态：已作废（日期）→ 被〈新路径/新设计〉取代（见 H-xxxx）`
2. **INDEX**（`docs/README.md`）状态列同步更新——agent 找文档先查索引，作废的在索引上显形
3. **handoff 记录**「怎么处理的」写明「旧设计 XX 已作废，指向 YY」

设计文档头部必须有状态行（`定稿` / `暂定` / `已作废→指向`），状态词沿用概念表四态。

## 3.1 分支铁律（配套铁律六）

**每个新任务或新要求，必须建立独立分支。**

```
main/master  ← 始终保持可运行
  └── feat/<任务短名>   新功能
  └── fix/<任务短名>    修问题
  └── docs/<任务短名>   文档
```

- 开始任务：`make branch NAME=<任务短名>`
- 完成任务：过完门禁 → `make branch-finish NAME=<任务短名>`
- **禁止**在 main 上直接改动（`gate.sh` 会拦截）
- 分支名不合规 → 门禁 FAIL

## 分工原则（最高约束，2026-10-21 定）

- **用户提供应用方向和需求，agent 基于这个展开设计，并用用户的要求设计验证场景去验证设计。**
- **禁止让用户既提要求、又去设计**——设计是 agent 的职责，用户不承担。
- agent 内部的机制选择（实现路径、内部命名、工具取舍）由 agent 自行裁决并记录理由，**不得包装成「请你裁决」上交**；需要用户拍板的，只提方案性问题（见「决策权归属」）。
- 用户说「不确定」时，agent 不得替用户拍板，也不得把问题原样扔回——正确动作：参考同行经验、或自行推演并自行设计场景验证后给答复。

## 分支与版本

- 每个新任务 / 新要求，**必须新建分支**，不直接改主分支。
- 完成任务后提交、走门禁、合并回主分支，并清理分支。
- 分支命名：`<类型>/<任务短名>`，短名用连字符。

## 决策权归属（重要）

**agent 不得替用户做以下决定**，必须停下来问：

- 技术栈选型（语言 / 框架 / 数据库）
- 是否引入新依赖
- 架构分层方式
- 前端视觉风格、布局、配色、交互方式
- 需求范围增减
- 是否删除/重写已有代码

> 这些是"方案性问题"，不是"实现细节"。方案由用户定，实现由 agent 做。

## 外部经验（参考同行）

- **先征询再调研**：不要自己决定要不要联网查。先说「我判断这是 X 领域，要不要查同类做法？」
- **不许静默降级**：没有联网能力时，必须**先告知**「我这边没联网，拿不到专业文献」，**再问**「要不要用训练数据里的印象给参照，还是这次不需要同行经验」。
- **四个标记要分清**：
  - `[检索]` 有出处的（必须写清哪个站点/文献/时间）
  - `[推荐]` 无出处的倾向（要写明"无出处"）
  - `[无参照]` 既无事实也无倾向
  - `[未覆盖]` 知道有但没列为选项 → 写进清单末尾「未覆盖方向」
- **禁止「业界普遍 / 通常认为 / 大家都」这类无出处断言**。这类话读起来像事实，其实是语气，用户无法反驳。
- **「未覆盖方向」不能是空的**。空等于声称选项已穷尽，而那几乎总是假的。想不出来就写实话：「我不确定是否还有别的方向」。
