# Aegis P6 Archive

## Overview

把"这次干成了什么"固化成**下一次能直接用**的东西。

核心原则：**归档的读者是三个月后完全忘了这事的自己。**

P6 不产出新功能，只做一件事：让下一个会话、下一个任务能在 30 秒内接上。

## When to Use

- P5 三轮 review 已通过，Critical 清零
- 准备合并分支或发布版本
- 发现 STATE.md 写的阶段与实际不符

## 铁律：P6 只写文档，不改代码

P6 期间禁止修改 `src/` 和 `tests/`。

原因：P5 评审的是改前的代码。归档时再改一行，评审结论就失效了。

发现代码问题 → 记进 STATE.md「已知限制」，或另开分支修。

## 动作

### 1. 先看事实，再写字

```bash
git log --oneline main..HEAD          # 本分支做了什么
git diff --stat main...HEAD           # 改了哪些文件
git log --oneline main..HEAD -- docs/incidents/   # 涉及哪些 INC
```

凭记忆写 CHANGELOG 必然漏项。

### 2. 整体重写 STATE.md（最重要）

不是改阶段号。按 `.ai/99-reference/state-schema.md` 逐节过：

| 小节 | 做什么 |
|---|---|
| 当前迭代 | 改成这次的名字 |
| 已完成 | 追加本迭代，旧的压成一行 |
| 进行中 | 清空本迭代项 |
| 下一步 | 重写为可执行动作，不写"继续开发" |
| 门禁签字 | 补 P5 |
| 最近决策 | 追加 ADR / INC 编号，最多留 5 条 |
| 已知限制 | 从 P5 的 Major/Minor 登记搬进来 |

**全文仍 ≤ 40 行。** 细节进 CHANGELOG，STATE 只留大类。

### 3. 更新 CHANGELOG.md

语义化版本，分「新增 / 变更 / 修复 / 移除」。

每条必须可追溯到 ADR 或 INC 编号。禁止写"优化若干细节"。

### 4. INDEX 完整性检查

```bash
for f in $(find docs -name '*.md' -o -name '*.html' | sort); do
  grep -q "$(basename "$f")" docs/INDEX.md || echo "未登记: $f"
done
```

同时查可追溯性：ALIGN 被 PRD 引用？INC 被 STATE 引用？ADR 被 DESIGN 引用？
孤立文档 = 死了的文档。

### 5. 归档垃圾产物

- 一次性调试脚本 → `archive/scripts/`
- 大体积测试数据 → `archive/fixtures/`
- **demo 不要删**（用户确认过的设计证据）

源码、测试、正式文档不进 archive。

### 6. 打 tag（在 main 上，不在功能分支）

```bash
git tag -a v1.3.0 -m "v1.3.0 用户登录"
```

tag 版本号必须与 CHANGELOG 一致。

## 完成标准

- [ ] STATE.md 整体更新，≤ 40 行，「下一步」可执行
- [ ] CHANGELOG 有本版本条目，可追溯
- [ ] INDEX 无未登记文件
- [ ] tag 已打且在 HEAD
- [ ] **P6 提交里没有代码文件改动**
- [ ] `bash scripts/gate.sh P6` PASS

## 给用户的归档摘要

不要问"可以吗"，要问"有没有写错"：

```
P6 归档完成，v1.3.0。
本迭代交付：<功能 1>、<功能 2>
记录沉淀：INC 新增 3 条，ADR 新增 1 条
已更新 STATE / CHANGELOG / INDEX，tag v1.3.0
有哪里写错了请指出。没问题就可以进入 P7。
```

## Common Mistakes

| 错误 | 纠正 |
|---|---|
| STATE.md 只改阶段号 | 下个会话读到过期信息，白读 |
| STATE.md 越写越长 | 50 行 80 行，token 优势消失 |
| CHANGELOG 写"优化若干细节" | 三个月后查不到任何东西 |
| 忘记打 tag | 无法定位哪个 commit 是这版 |
| 在功能分支上打 tag | tag 指向未合并状态 |
| 归档时顺手改代码 | P5 结论失效 |
| 删掉 demo | 丢失设计证据 |

## Red Flags — STOP

- "STATE.md 改个阶段号就行" → 下个会话会被误导
- "CHANGELOG 发版时一起写" → 到那时细节全忘了
- "这个改动太小不用记" → 小改动堆起来就是"这功能哪来的"
- "顺手把这行也改了" → P6 禁止改代码
- "tag 下次补" → 下次就找不到这个 commit 了

## 同步块（真相源摘录，会话必读）

## 3. 七条铁律（不可违反）

### 铁律一：阶段不可跳

未通过当前阶段的全部出口门禁，**禁止**进入下一阶段。
用户要求跳步时，必须先说明"当前在 Pn，缺 X"，并获得用户**明确豁免**（记入 `STATE.md`）。

### 铁律二：设计前必须可视

**前端类项目的 P2 阶段，必须产出可在浏览器打开的 HTML demo，并获用户确认后，才能进入 P4 写业务代码。**
没有 demo 的前端设计 = 没有设计。

### 铁律三：完成必须留证

宣称"完成""修好""通过"时，**必须贴出验证输出**。
"我觉得可以""应该没问题"不算完成，视为未完成。

延伸到 P7：**交付说明里的步骤必须真的照抄跑过一遍。**
没跑过就写文档 = 交付假货。

### 铁律三之二：任务必须留档

**每个任务结束（合并进 main 前）必须写一条开发事件记录**，
记在 `dev/handoff/H-<编号>-<短名>.md`，并在 `dev/HANDOFF.md` 索引加一行。

七要素：时间 / 谁 / 事件 / 为什么这样处理 / 怎么处理的 / **试过什么（成没成）** / 下一步等谁。

- **「试过什么」不许空**：没走过弯路就写「本任务未走过弯路」
- **事实 / 推断 / 未知 分开标**：`〔推断〕`、`〔未知〕`，不标视为事实
- **过期不删**：划掉并指向新条目，因为下个 agent 读到旧结论会把新工作改回去

为什么必须有：**没有这一栏，下一个人（或三个月后的你）会把失败的路重走一遍。**

细则见 `.ai/99-reference/handoff-schema.md`。

### 铁律四：问题必须沉淀

任何调试超过 **15 分钟**、或试错 **2 次以上**、或发现"设计时没考虑到"的情况，
**必须**新建 `docs/incidents/INC-xxxx.md`。

其中 **「预防」一节为必填** —— 没有预防措施的 incident 不算闭环。

### 铁律五：单一真相源

`.ai/*.md` 是规矩的**唯一真相**。
`.skills/`、`adapters/`、`AGENTS.md` 内联段都是**派生物**，由 `make sync` 生成。
禁止手工维护两份内容 —— 这是 token 浪费的根源。

### 铁律六：讨论前置，禁止自作主张

**用户提出任何新要求后，禁止直接给出方案、计划或代码。**

必须先进入 P0.5 意图校准，完成**至少两轮讨论**：

| 轮次 | 目的 | 强制 |
|---|---|---|
| R1 复述轮 | 用自己的话复述，让用户纠正 | ❌ 不可跳 |
| R2 深层轮 | 挖"为什么/什么算失败/什么情况例外" | ❌ 不可跳 |
| R3 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件 |

**每轮开始前必须先产出一份 checklist**，用户确认清单本身后再逐条讨论。
checklist 必须使用**日常语言**——判断标准是：不懂技术的人也能直接回答。

**写清单之前还有一步：调研前置（第七维）。**
顺序是「判定领域 → 征询是否联网调研 → 调研 → 生成清单」。
每个关键点下面必须写清依据来源（`[检索]` / `[推荐]` / `[无参照]`），
清单末尾必须有「未覆盖方向」一节。无联网能力时必须**先告知再询问**，不许静默降级，不许伪装成查过。
详见 `.ai/015-P05-align.md` 的「第零步：调研前置」。

**讨论结论必须落文档**（`docs/align/`），它是 P1 写 PRD 的唯一依据。

> 违反示例：用户说"帮我做个 X"，agent 回"好的，我的方案是……"。
> 正确反应：先建 checklist，复述理解，确认后再谈方案。

### 铁律七：概念先定义后使用（H-0007，2026-10-21）

**项目中反复使用的词，禁止在未定义的情况下当作已共识使用。**

概念固化的三个挂点（不新增阶段）：

| 挂点 | 动作 | 强制 |
|---|---|---|
| 校准（现行 P05；八阶段定稿为 S2 对齐） | 列出本次工作的新词候选清单，逐个用五元素问用户「这个词你怎么理解」 | ❌ 不可跳 |
| 任务进行中 | 新词出现 → 先命名再讨论；达成一致理解后写入 `docs/CONCEPTS.md`，标 `暂定` | 随发生随做 |
| P6 归档 | 在 handoff 记录写「**新词**」一行（无则写「无」）；有新词的，词条状态要落实（升 `已定` 或保持 `暂定` 并注明待验收） | ❌ 不可跳 |

概念的出现不是在项目一开始就全部涌现（用户原话）——所以固化是常设动作，不是一次性工程。

## 3.2 修订留痕规则（设计被推翻时，三动作同时做）

**推翻或改造任何已成文的设计时，禁止只写新设计、不动旧设计。** 三动作缺一不可：

1. **旧文件头**加状态行：`> 状态：已作废（日期）→ 被〈新路径/新设计〉取代（见 H-xxxx）`
2. **INDEX**（`docs/INDEX.md`）状态列同步更新——agent 找文档先查索引，作废的在索引上显形
3. **handoff 记录**「怎么处理的」写明「旧设计 XX 已作废，指向 YY」

设计文档头部必须有状态行（`定稿` / `暂定` / `已作废→指向`），状态词沿用概念表四态。
门禁对「缺状态行」「已作废却无指向」告警（铁律五的配套，见 H-0021）。

## 3.1 分支铁律（配套铁律六）

**每个新任务或新要求，必须建立独立分支。**

```
main/master  ← 始终保持可运行
  └── feat/<任务短名>   新功能
  └── fix/<任务短名>    修问题
  └── docs/<任务短名>   文档
```

- 开始任务：`make branch NAME=<任务短名>`
- 完成任务：过完门禁 → `make branch-finish NAME=<任务短名>`
- **禁止**在 main 上直接改动（`gate.sh` 会拦截）
- 分支名不合规 → 门禁 FAIL

## 分工原则（最高约束，2026-10-21 定）

- **用户提供应用方向和需求，agent 基于这个展开设计，并用用户的要求设计验证场景去验证设计。**
- **禁止让用户既提要求、又去设计**——设计是 agent 的职责，用户不承担。
- agent 内部的机制选择（实现路径、内部命名、工具取舍）由 agent 自行裁决并记录理由，**不得包装成「请你裁决」上交**；需要用户拍板的，只提方案性问题（见「决策权归属」）。
- 用户说「不确定」时，agent 不得替用户拍板，也不得把问题原样扔回——正确动作：参考同行经验、或自行推演并自行设计场景验证后给答复。

## 分支与版本

- 每个新任务 / 新要求，**必须新建分支**，不直接改主分支。
- 完成任务后提交、走门禁、合并回主分支，并清理分支。
- 分支命名：`<类型>/<任务短名>`，短名用连字符。

## 决策权归属（重要）

**agent 不得替用户做以下决定**，必须停下来问：

- 技术栈选型（语言 / 框架 / 数据库）
- 是否引入新依赖
- 架构分层方式
- 前端视觉风格、布局、配色、交互方式
- 需求范围增减
- 是否删除/重写已有代码

> 这些是"方案性问题"，不是"实现细节"。方案由用户定，实现由 agent 做。

## 外部经验（参考同行）

- **先征询再调研**：不要自己决定要不要联网查。先说「我判断这是 X 领域，要不要查同类做法？」
- **不许静默降级**：没有联网能力时，必须**先告知**「我这边没联网，拿不到专业文献」，**再问**「要不要用训练数据里的印象给参照，还是这次不需要同行经验」。
- **四个标记要分清**：
  - `[检索]` 有出处的（必须写清哪个站点/文献/时间）
  - `[推荐]` 无出处的倾向（要写明"无出处"）
  - `[无参照]` 既无事实也无倾向
  - `[未覆盖]` 知道有但没列为选项 → 写进清单末尾「未覆盖方向」
- **禁止「业界普遍 / 通常认为 / 大家都」这类无出处断言**。这类话读起来像事实，其实是语气，用户无法反驳。
- **「未覆盖方向」不能是空的**。空等于声称选项已穷尽，而那几乎总是假的。想不出来就写实话：「我不确定是否还有别的方向」。
