# H-0007 概念定义应为 Aegis 的基石性环节（只记录，不设计）

- **时间**：2026-10-21
- **谁**：用户提出，agent 记录
- **事件**：用户指出「定义概念」这一环节对 Aegis 是**必须的基石性工作**，须作为重要环节对待，不能只当一次性任务
- **为什么这样处理**：本轮为解决鸡同鸭讲才临时引入概念定义，但用户判断这不是临时手段——**人类与 agent 协同开发的偏离程度，主要由「概念与认知的统一程度」决定**。若 Aegis 不把它固化成机制，下个项目、下个 agent 会重犯
- **怎么处理的**：**仅记录，本版不设计**。原因：正处暂停期，且形态取决于概念梳理的最终结果。记下三条已推演出的中间结论供下次直接用（见下）
- **试过什么**
  - ❌ 做成「阶段 P-1」置于 P0 前：用户指出**概念不是项目一开始全部涌现**，是在推进中不断出现或放弃的；阶段只能过一次，不能反复进入
  - ❌ 做成「第四条轴」（与阶段轴/制品轴/门禁轴并列）：轴是静态分类，而概念表是持续生长的；画成静态结构会失真
  - ✅〔推断〕更像「**常驻机制 + 检查点**」：随时可触发（任何阶段遇新词即补）、累积不重启（只增不改）、**必须有收口**（否则退化成「永远不补」——本轮即为实例）
  - ✅〔检索〕强制力同行无成熟机制：GB/T 1.1-2020 只强制「术语章必须存在，无内容也要写一句声明」；GB/T 10112 给收录判据与定义格式；ISO 24774 要求信息项有 name + characteristics；**各家 agent 工具均不检查概念一致性**
  - ✅〔推断〕三个可用杠杆：存在性（门禁 FAIL，可机械查）/ 覆盖性（门禁提醒，误报多）/ 提交前拦截（git hook，可绕过）
- **下一步 / 等谁**：**概念梳理全部完成后**再讨论本环节如何设计。届时用户拍板形态与强制力。用户明确要求记下此事的原因是「怕到需要设计时忘了这茬」
