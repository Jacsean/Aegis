## 一、价值提炼

Aegis 的价值分三层，**越往上越独有**：

| 层 | 价值 | 是否独有 | 依据 |
|---|---|---|:--:|
| **底层** | 把关键约束从「模型读的文本」搬到「模型外面执行的代码」 | ❌ **不独有** | `[检索]` 2026 年已有论文验证；Anthropic 官方也这么说 |
| **中层** | **让约束机制能长大**（失效记录 → 判据 → 问题 → 维度，并带修剪） | ✅ **独有** | `[检索]` 同行都是「设计者一次性写定」，没有生长+修剪机制 |
| **上层** | **把「思维模型」作为第二维度**（16 个模型 + 主动张 + 双环反思） | ✅ **独有** | `[检索]` BMAD 想「谁来做」，Superpowers 想「按什么流程」，没人想「怎么想」 |

**一句话**：Aegis 的价值不在「发现了该用规则」，而在「规则怎么长、以及多想一层」。

## 二、同行流调

### 2.1 四家主力（star 数据为 2026-10 快照，各源有出入，取中位）

| 项目 | Stars | 所属层 | 特点 | 已知弱点 |
|---|---:|---|---|---|
| **Superpowers**（obra/superpowers） | **约 30 万** | 行为层 | brainstorming → 计划 → 子 agent 执行 → 严格 TDD（先删掉测试前写的代码）；摩擦最低；官方 Anthropic 插件；跨 runtime | `[检索]` 只覆盖单 agent 的「文件内工作」，不解决项目级记忆 |
| **claude-flow → Ruflo**（ruvnet） | 约 **75–80k** | 编排层 | swarm、314 个 MCP 工具、向量记忆、跨机联邦 | `[检索]` 「庞大」、690 个 open issue、**benchmark 是厂商自报未独立复现**；单日 +830 star 是 spike 不是采纳 |
| **BMAD-METHOD** | 约 **55k** | 方法论层 | 19–21 个 agent 角色 + 34–50 个工作流，四阶段全生命周期 | `[检索]` 被评「过重」（外部评价直接写 Avoid — overkill）；**门禁是 LLM 散文判断，不是机器可查** |
| **Agent OS**（buildermethods） | 约 **5.5k**（增速已平） | 标准层 | 从代码库提取真实约定，按需注入；v3 主动砍掉自己的编排功能 | `[检索]` 单人维护（86% 提交来自一人），2026-01 后无新版本 |

**另有**：GitHub **Spec Kit**（`constitution.md` + 四阶段）、**OpenSpec**（delta spec，适合 brownfield）、**GSD**（长任务上下文管理）。

### 2.2 分层图 —— 它们不打架

```
治理层    Linear / 业务可追溯
编排层    Archon / Ruflo（swarm、多 agent）
方法论层  Spec Kit / BMAD / Agent OS（做对的东西）
基础层    Superpowers（agent 在文件里怎么干活）
```

`[检索]` 所有横评的共识：**这些不是竞品；最好的团队是偷做法，不是整体采纳一个框架。**

### 2.3 Aegis 的位置

**横跨基础层与方法论层之间的缝**：

- 往下：不跟 Superpowers 抢「怎么做 TDD / 计划」→ 让路
- 往中间：管「每个任务前后的约束检查」→ **没人明确占的位**
- 横向：加一维「思维模型」→ **完全空白**

## 三、头部企业各自的技术手段

| 企业 | 手段 | 关键设计 |
|---|---|---|
| **Anthropic** | Skills（三层披露）+ **hooks**（模型外执行）+ subagents（上下文隔离）+ memory（按需召回） | 核心是**「建议 vs 规则」的物理分离**：`CLAUDE.md` 是 advisory，hooks 是 deterministic |
| **AWS Kiro** | spec（requirements/design/tasks）+ **steering 文件**（四模式 always/fileMatch/manual/auto）+ **agent hooks**（`.kiro/hooks/*.json`） | steering 的**条件加载**比 Aegis 的「按阶段加载」更细 |
| **GitHub Spec Kit** | `constitution.md`（不可变原则，自动注入每条命令）+ 四阶段 | **constitution 优先** —— 与 Aegis 的 00-core 同构 |
| **OpenAI Codex** | `AGENTS.md` 约定 + 沙箱 | 最少约束、最多自由 |
| **Cursor** | `.cursor/rules/*.mdc`（description / globs / alwaysApply） | 路径作用域 |

**共同趋势**：`[检索]` **全部在把「约束」从文本往「可执行」搬**。Aegis 走同一条路，只是更彻底（约束清单 + hook + 生长机制）。

## 四、学术现状：Aegis 的主张已被验证，但组合没人做

| 论文 | 关键结论 | 与 Aegis 的关系 |
|---|---|---|
| **Guardrails Beat Guidance**（arXiv:2604.11088）<br>679 个规则文件、25,532 条规则、5,000+ 次 SWE-bench 运行 | 规则文件比无规则 **+7~14pp**；**随机规则 = 专家筛选规则**（上下文 priming 主导）；**负向约束是唯一单独有益的规则类型**；正向指令单独加反而有害 | ✅ 验证「建议 vs 规则」；且说明 **hook 只放 3 条硬约束是对的** |
| **Constraint Decay**（arXiv:2605.06445） | 结构性要求累积时 agent 性能**显著下降**；提出 Constraint Pinning（治理约束隔离出有损压缩），长任务违规率可降到 0% | ✅ 验证「上下文压缩会丢约束」→ 支持把约束放 hook |
| **ANCHOR**（arXiv:2610.16859）<br>10 类 / 78 叶 / 2,836 条原子约束，358 任务 | 最好系统 **70.1% 原子合规、63.7% 关系合规，但只有 19.0% 任务全项通过**；加约束只让完成度 **+0.7pp**；失败集中在**流程顺序、工具纪律、报告** | ✅✅ **最重要的一篇**：说明「约束合规」远低于「任务完成」，失败集中在流程纪律 —— 正是 Aegis 想管的 |
| **HANDBOOK.md**（arXiv:2607.25398）<br>824 条确定性标准 | 最好前沿模型严格评分只过 **36.2%**；失败模式含**跳过验证、检查了但忽略、环境覆盖、虚假合规报告** | ✅ 验证 Aegis 的「完成必须留证」 |
| **Gated Spec-Driven Workflow**（arXiv:2611.05094） | 门禁 + 审查子 agent + 执行器限定文件。9 feature 完成 5；**弱点是「编排者评判自己的检查」**——247 次阻断检查里 11 次记录到未声明变更，但只停了 4 次 | ✅✅ 验证 Aegis 的「审计+否决权」定位，并指出它也要面对的弱点 |
| **Skillware**（arXiv:2611.07652） | 类型化 JSON 契约 + 确定性 Python 替代 markdown skills；小模型装备后超过未装备的前沿模型，token 降 84.8% | ⚠️ 单厂商自报、未独立复现。方向与 Aegis 一致 |

**三条结论**：
1. `[检索]` Aegis 的核心主张（约束要外部化）**不是新发现**
2. `[检索]` Aegis 解决的问题（约束衰减、合规率低）**真实且被量化**
3. `[检索]` Aegis 的两个独有点（生长机制、思维模型）**没有任何论文覆盖**

## 五、战略评估

| # | 优势 | 强度 |
|:--:|---|:--:|
| 1 | 「约束会衰减」已被证实 → 解决的是真问题 | 🔥🔥🔥 |

| 4 | 思维模型这一维完全空白 | 🔥🔥🔥 |
| 5 | 生长机制没人做 | 🔥🔥 |

### 5.2 劣势（必须承认）

| # | 劣势 | 严重度 |
|:--:|---|:--:|
| 1 | 核心主张已被论文和 Anthropic 官方覆盖 —— **不是首创** | 🔴 高 |
| 2 | Superpowers 30 万 star 形成网络效应 —— 后发极难抢位 | 🔴 高 |
| 3 | **Aegis 至今没有实证数据**（只有一个贪吃蛇、一次 token 对比） | 🔴 高 |
| 4 | 思维模型维度**无法机械验证** —— 是特色，也是无法被证明的原因 | 🟡 中 |

### 5.3 战略判断

> **Aegis 占的位置是真的（约束执行层的缝），但它是「补缝者」不是「开创者」。**
> 差异化只有两条：**生长机制、思维模型**。**而这两条都还没被证明。**

## 六、GitHub 关注度预测

### 6.1 参照

| 项目 | Stars | 说明 |
|---|---:|---|
| Superpowers | 30 万 | 官方插件、跨 runtime、月增 17k |
| BMAD | 5.5 万 | 最完整的 SDLC |
| Ruflo | 8 万 | 但「单日 +830 是 spike 不是采纳」 |
| **Agent OS** | **5.5 千** | 最窄、最诚实、单人维护 |

### 6.2 现实落点

**1k–5k star 区间**（Agent OS 那一档）。

`[推荐]` 除非出现以下之一：

| 能大幅拉高关注的条件 | 现在有没有 |
|---|---|
| 一个惊艳的可视化 demo（hook 实时拦住 agent） | ❌ |
| 一个权威第三方的独立评测（像 ANCHOR 那样） | ❌ |
| 绑定热门生态（做成 Superpowers 插件而非替代） | ❌ 现在是对标关系 |
| 中文社区强传播 | 未知 |

### 6.3 最关键的一条

`[检索]` 行业共识是「**偷做法，不要整体采纳框架**」。

**这条对 Aegis 是致命的——因为它现在要求使用者整体替换现有 skills。**

> **建议：定位从「替代」改成「叠加」**（装在任何已有 skills 之上，只提供约束 + 生长层）。
> 这一改同时解决关注度和战略价值两个问题。
