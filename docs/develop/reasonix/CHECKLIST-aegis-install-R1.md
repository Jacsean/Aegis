### 第 2 条 · 改完之后，什么情况你会认为白改了

**结论**：用**结果**判定，不用过程判定。反向边界是——按 Aegis 的协助走完一个项目，**项目无法运作**，或**存在重大设计纰漏**，则判定 Aegis 失效、未能正向推动。

**用户原话**：「如何界定白改了，或者确定修改的合理的反向边界，是需要构建场景去验证模拟的；一般的表现是，在项目中，按照 aegis 的协助完成一个项目，发现项目无法运作，或存在重大设计纰漏。这说明 aegis 的协助是失效的，未能正向推动项目。」

**确认日期**：2026-11-02

**从这条提取的三点**：
1. **判定标准是结果导向的**：不看"过程有没有照做"，只看"做出来的项目能不能用"。我原来给的 A/B/C 全是过程指标（有没有打开、行为变没变、成本高不高），方向岔了。
2. **判定手段必须是场景验证**：不接受主观感觉"这次好多了"。这与第 1 条否定的"旧场景"不矛盾——否定的不是"用场景验证"这个方法，是**那一批场景设计和结果**（结果不一致且无法归因）。
3. **需要重新构建场景**：而且场景要能暴露"项目跑不起来 / 有重大设计纰漏"，不是走个流程就算过。

**由此产生的张力（记录下来，不在本条解决）**：要把"项目跑不起来"判成 Aegis 的责任，必须先排除"是助手实现能力不行"或"是需求本身就矛盾"。这个排除动作就是归因，与 G1 同源。见 G4。

### 第 3 条 · 改造过程怎么组织

**结论**：改造过程遵循固定五段闭环 ——
**发现问题 → 讨论问题（根源、表现、影响力、约束条件）→ 解决方案讨论 → 解决方式实施 → 验证解决方案的效果**

**用户原话**：「改造过程遵循（先发现问题-讨论问题（根源、表现、影响力、约束条件等）-解决方案讨论-解决方式实施-验证解决方案的效果）这样一个过程」

**确认日期**：2026-11-02

**用户同时提出的批评（已接受）**：我原来给的三个选项（分两段验／一次性验／不验）是**执行节奏**，不是**方法论**；设计选项时没有动用思维模型（如六顶思考帽、第一性原则）。这是选项设计层面的缺陷，不是答案问题。

**这个闭环与成熟模型的对照**（我识别的，请纠错）：
| 用户的环节 | 对应的成熟做法 |
|---|---|
| 发现问题 | Problem Identification |
| 讨论问题（根源/表现/影响力/约束条件） | 根因分析 + 影响面评估 + 约束识别（FMEA、5Why、约束理论） |
| 解决方案讨论 | 发散→收敛（六顶思考帽的绿帽/黑帽/黄帽） |
| 解决方式实施 | 执行 |
| 验证解决方案的效果 | 效果确认（与第 2 条"结果导向验收"对接） |

> 依据：`[推荐]` 上表对应关系是我的识别，无出处；其中"四分法（根源/表现/影响力/约束条件）"覆盖面很全，同时锁住了 why / what / how big / what limits 四个维度

**这条对本轮的结构性影响（重要）**：
按此闭环，**第 4 条（放哪个文件夹）属于"解决方案讨论"，在它之前必须先有"问题讨论"**——即"说明书找不到"的根源、表现、影响面、约束条件。因此第 4 条起，我的选项设计改为：先给问题讨论，再给方案选项，且选项用思维模型生成。

**结论（原则层）**：采用**两步走 + 统一指向**——
1. 为各主流助手设计它自己能识别的入口；
2. 各平台入口统一指向 Aegis 的内部入口。

`统一指向` 是**对入口技术原理的统称，描述 Aegis 控制流如何收口，不代表某一种实现技术**；每个平台的具体实现手段可以不同，按该平台能力选。

**用户原话**：「"说明书放进去之后，助手找不到它。"说明了 aegis 的入口设计问题，不具有通用性；可否考虑两步走：1.设计各个主流agent能识别的入口；2.各个主流agent入口统一指向aegis内部入口；」
「"统一指向"是对各个主流agent中，入口技术原理或实现的统称，可能不代表一种方法；只是从概念层面描述aegis控制流的机制，不代表实现技术」

**确认日期**：2026-11-02

**这个方案为什么成立（内部依据，不是外推）**：`adapters/README.md` 第 33-38 行已经定义了"新增一个平台适配"的四步（放入口文件 → sync 加一段 → 表加一行 → 验证）。该机制**已用于指令文件，唯独没用于说明书**。所以本结论是把既有机制补齐，不是新设计。

### 第 5 条 · Aegis 怎么被触发，穿插怎么处理

> 说明：本条原始问题是"先花半天试一下，还是全改完再说"，用户选择「其他」后，本条演化为"触发与穿插机制"。以下为完整确认内容。

**第 5 条之 A · 改造过程怎么组织**

结论：改造遵循固定五段闭环 —— **发现问题 → 讨论问题（根源、表现、影响力、约束条件）→ 解决方案讨论 → 解决方式实施 → 验证解决方案的效果**。
用户原话：「改造过程遵循（先发现问题-讨论问题（根源、表现、影响力、约束条件等）-解决方案讨论-解决方式实施-验证解决方案的效果）这样一个过程」
用户同时指出：我原先给的"分两段验／一次性验／不验"三个选项是执行节奏，不是方法论；设计选项时没有动用思维模型。此批评已接受。

**第 5 条之 B · Aegis 靠什么被触发**

结论：靠**对话关键字触发**（与 superpowers 同一机制）。用户明确使用方式：删除 superpowers 与自定义 rules.md，只装 Aegis，vibe coding 时由对话关键字触发相应机制。
用户原话：「我会删除superpowers和rules.md，然后安装Aegis，在vibe coding时，由对话关键字触发Aegis的相应机制」

**第 5 条之 C · 穿插怎么处理（核心）**

结论：**捕获与处置分离**。
- 捕获（agent 强项）：检测到偏离 → 立即复述列举成结构化条目 → 不判断、不丢
- 处置（人类强项）：用户决定 现在做 / 记下来 / 并入当前
- 不让 agent 判断优先级；判断不了就交人（对应四级降级链的"人工决定"级）
- 偏离分三档：小（同话题补充，直接并入）／中（同阶段另一件事，复述后问）／大（跨阶段跨目标，记入待办不打断）

用户原话：「针对人类灵感易忘的生理特征…一个会话中有穿插时，如果aegis或者agent无法同时处理或判断处理优先级时，充分利用agent会话机制，先将穿插内容用agent能理解的方式在会话中复述列举，然后让用户抉择优先级或处理方式，更具穿插内容和当前讨论主题的偏离幅度，利用md文档或checklist机制逐项处理」

**第 5 条之 D · 用什么存（流水账 + 摘要）**

结论：采用**事件流 + 派生视图**。
- **流水账**：只追加不改的流水账，是唯一真相
- **摘要**：由脚本从流水账**算出来的**（派生），不是手写的
- agent 平时只读摘要（小）；需要细节时去流水账里捞那一条
- 好处：流水账再长也不进上下文；摘要坏了可重算；不会出现两份数据打架

用户原话：「用双机制实现：1.索引…负责表达记录中执行到哪里，哪些未执行…允许每次aegis启动时读取，token增幅有限可控；2.记录，由索引选择性启动…每个问题构成一个节点，问题间的逻辑或因果关系构成节点间的联系」

**采纳的形态改进**：索引由手写改为**派生**。理由：手写的索引和记录是两份真相，会打架，且违反铁律五（禁止手工维护两份内容）。改成派生后与 `.skills/`、`adapters/` 的做法完全一致（都由脚本生成）。

**第 5 条之 E · 结构长什么样（树 → 森林 → 图）**

用户的演化景象：项目从一个模块开始（树）→ 新功能演变成新树 → 迭代入项目，两树成森林 → 更多树 → 森林变图。
与 git 分支演化同构（主干 / feature 分支 / 合并 / 多分支并行 / 交叉依赖），可借用既有语义。

- **节点粒度**：一个问题/决定 = 一个节点（方案 A）
- **容器**：树 → 森林 → 图，粒度不变，只换容器
- **同构边界**：结构与 git 同构，但"合并"这一步不能自动——代码冲突机器能查，想法冲突只能人判

**第 5 条之 F · 配套规则（对抗场景验证后得出的）**

| # | 规则 | 由来 |
|---|---|---|
| 1 | 轻量模式：单节点任务不建树 | 场景1暴露：改个样式也要建树=小题大做 |
| 2 | 摘要必须折叠：未结束的展开，已结束的折叠成一行+数量 | 场景4/6暴露：30 个模块时摘要必爆 |
| 3 | 搁置/悬置必须写理由，理由不被折叠 | 场景4暴露：否则三个月后捡不回来 |
| 4 | 返工必须记原因 | 场景5暴露：否则会被当成新问题重做 |

**第 5 条之 G · 原型（7 种事件）**

流水账只用 7 种事件：**建模块 / 建节点 / 状态 / 依赖 / 并入 / 否决 / 更正**。
状态值：进行中 / 已定 / 搁置（须理由）/ 悬置（讨论过没结论）/ 否决 / 当前。
摘要含五段：当前位置 / 森林（模块列表+状态+节点数+一句话说明）/ 公共（被多模块共用的）/ 关联（依赖）/ 折叠（已否决/已完成的汇总）。

对抗场景验证（10 个）暴露 3 个硬失败、3 个需修，已全部修补：
| 缺陷 | 修补 |
|---|---|
| 一物多属（统一登录服务三模块） | 摘要加「公共」层，从树里提出单独列 |
| 已否决/已完成堆积 | 折叠成一行 + 数量 |
| 交接看不懂 | 建模块必须写一句话说明 |
| 悬而未决没地方放 | 状态加 `[悬置]` 档（与"搁置"区分：搁置=等外部条件，悬置=内部没想清） |

**第 5 条之 H · 明确不做的事**

- 事件类型先不加"节点被拆成两个""两条线合并"两种——留给实测发现，不提前猜
- 原型暂不单独落盘，随本条一起写入
- 摘要不做拓扑排序，只做展示（避免循环依赖导致死循环）
