## 二、三个候选方向

### 方向 A · 约束清单的生长与修剪（最原创）

**题目（草稿）**：
> *Growing Constraint Sets: A Self-Revising Checklist Mechanism for Coding Agents*

**核心主张**：
现有工作的约束清单都是**设计者一次性写定**（Spec Kit 的 constitution、BMAD 的 workflow、Kiro 的 steering）。
Aegis 提出：**约束清单本身应该随使用生长与修剪**，并给出三层结构（判据 → 问题 → 维度）+ 上升/修剪判据。

**Novelty 在哪**：
- `[检索]` **没有任何一篇论文讨论「约束清单本身的演化」**
- 已有论文都在优化「给定清单下的合规率」（ANCHOR、Guardrails、HANDBOOK）
- Aegis 换了问题：**清单从哪来、怎么长、怎么瘦**

**最大风险**：
生长是**慢变量**——需要数周甚至数月的真实使用才能观察到。学术实验周期内很难造出「生长」的完整证据。

**可行做法**：**模拟演化**
- 用 ANCHOR 的 2,836 条约束作为「已知失效池」
- 把一部分藏起来，逐步暴露给 Aegis，观察它是否能把藏起来的重新发现
- 指标：重现率、误升率（把偶发失效错误升为核心维度）、修剪准确率

---

### 方向 B · 思维模型作为第二维度（最独特，最难测）

**题目（草稿）**：
> *A Second Dimension: Thinking Models as a Constraint Layer for Coding Agents*

**核心主张**：
现有 agent 框架只在「工程方法」一维工作（TDD、计划、评审）。
Aegis 引入第二维：**思维模型**（第一性原理、Kano、逆向、双环反思……），
并且**不靠模型自述**——要求"说了用 X，输出里要有 X 的痕迹"（一致性检查）。

**Novelty 在哪**：
- `[检索]` **完全空白**。BMAD 分角色，Superpowers 分流程，没人管「怎么想」
- 而且提出的验证方式（**一致性检查**：说了没做 = 当场露馅）是新的

**最大风险**：
「想得对不对」无法机械验证，只能验证「说的和做的一致」。
审稿人会问：**一致性 ≠ 质量，你怎么证明它有用？**

**必须准备的回答**：
用「**下游可测指标**」间接证明：
- 需求变更次数（对齐质量）
- 返工次数（方向性错误）
- 首次交付通过率

---

### 方向 C · 工程实证：把建议变成规则（最稳，但最不新）

**题目（草稿）**：
> *From Advisory to Deterministic: An Engineering Study of Constraint Externalization in Coding Agents*

**核心主张**：
把 9,720 字节的文本规范 vs 20 行 hook，做直接对照。

**已经有的证据**：
`[检索]` Aegis 自己的实测——全局 v2.0 规范（9,720 字节，要求"先讨论再动手"）**没拦住** agent 写文件；Aegis 的 20 行 hook **拦住了**。

**Novelty 问题**：
`[检索]` **这条已被覆盖**——Guardrails Beat Guidance、Constraint Decay、Anthropic 官方都在说同一件事。

**所以方向 C 只能当「补充证据」，不能当主贡献。**

## 三、绕不开的实验设计

不管选哪个方向，都得补这些：

### 3.1 任务集

| 要求 | 参照 |
|---|---|
| **20–30 个真实任务**（不是贪吃蛇） | ANCHOR 用了 358；workshop 可以少 |
| 覆盖不同难度：清晰问题 / 模糊需求 / 多文件改动 | — |
| **每个任务有明确的失败定义** | Aegis 自己的「项目跑不起来 / 有重大设计纰漏」 |

### 3.2 对照组（至少三组）

| 组 | 配置 | 测什么 |
|---|---|---|
| **A 基线** | 无约束 | 基线表现 |
| **B 静态约束** | 只有文本规则（模拟 Superpowers / BMAD） | 文本约束的效果 |
| **C Aegis** | 文本 + hook + 生长机制 | Aegis 的增量 |

> `[检索]` Guardrails Beat Guidance 用了「随机规则」这个第四组做安慰剂对照——这是审稿人一定会问的，**建议照做**。

### 3.3 指标（三层，缺一不可）

| 层 | 指标 | 参照 |
|---|---|---|
| **结果** | 任务完成率、测试通过率 | 常规 |
| **合规** | 原子约束合规率、关系约束合规率、**全项通过率** | `[检索]` ANCHOR：最好系统 70.1% / 63.7% / **19.0%** |
| **过程** | 轨迹分析：跳过验证次数、虚假合规报告次数、返工次数 | `[检索]` HANDBOOK.md 的失败模式分类 |
| **成本** | token、耗时、调用次数 | Aegis 已有一次数据（42,799 vs 31,905 cache_miss） |

### 3.4 统计

- 每任务每配置 **至少 3 次**运行（LLM 有随机性）
- 报告 **中位数 + 置信区间**，不能只报均值
- 20 任务 × 3 组 × 3 次 = **180 次运行**（workshop 可接受的下限）

## 四、目标场所与时间线

| 阶段 | 产出 | 预估 |
|---|---|---|
| **现在** | arXiv preprint（tool paper 风格） | 2 周（有代码 + demo + 初步数据） |
| **1 个月后** | Workshop paper（方向 A 或 B） | 需补 180 次运行 |
| **3–6 个月后** | 顶会投稿 | 需 300+ 次运行 + 跨平台 |

**推荐先做**：**arXiv tool paper**。
理由：门槛低、能立时间戳、能被引用、能作为 GitHub 的引流。

## 六、我的建议

| 判断 | 结论 |
|---|---|
| **能不能写论文** | ✅ 能，但**不是现在这个状态**——缺 5 个前置 |
| **写哪个方向** | **方向 A（生长机制）**最原创；方向 B 最独特但最难测 |
| **先发哪里** | **arXiv tool paper**，2 周可成 |
| **最大的坑** | 生长机制是慢变量，实验周期内造不出完整证据 → **用模拟演化绕过** |

**一句话**：

> Aegis **够格写一篇 workshop paper，但不够格写顶会**。
> 差距不在想法，在**数据量差三个数量级**（1 个任务 vs 358 个）。
