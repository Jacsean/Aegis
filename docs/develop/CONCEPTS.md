# CONCEPTS · 全局概念表（术语表）

> **本表是全项目唯一的概念定义处。** 任何文档里出现的概念词，含义以本表为准。
> 文档开头若有「本文用词」节，只放一句话 + 指向本表锚点；**定义只在本表写一次。**
>
> **收录判据**（GB/T 10112-2019 / ISO 704，三条同时满足才收）：
> 1. 文件中至少使用两次
> 2. 专业使用者在不同语境中理解不一致
> 3. 尚无定义，或已有定义需改写
>
> **条目写法**：
> - 内涵定义 = **上位概念 + 区别特征**（不用否定式定义，不循环定义）
> - 记叙文六要素为上限、**按需取用**，用不上不硬凑
> - **「不是什么」必填**，至少一条
> - 单条 100~150 字；超了说明该拆
> - 附真实例句（词义由语境圈定，无例句的定义是悬空的）

## 本表是什么 / 不是什么

| 本表**是** | 本表**不是** |
|---|---|
| 把**已达成的共识**固化成词条的地方 | 会议记录、过程档案（那些进 `handoff/H-*.md`）|
| 让不同会话里的不同 agent 拿到**同一理解** | 通用词典（只收项目内不可再分的词）|
| 项目语言的锚点 | 项目结构本身（结构是它描述的对象）|
| 只增不删、改要留痕的活文档 | 一次性写死的规范 |

## 使用方式（三个场景）

| 谁 | 什么时候 | 读多少 |
|---|---|---|
| 梳理中的 agent 和用户 | 逐词定案 | 完整条目 |
| 新会话的 agent | 会话启动 | 只读本页目录（一句话列）|
| 查文档的人 | 遇到生词 | 按锚点跳到该词条目 |

> **本表为什么存在**（详见 `handoff/H-0007`）：
> 人类与 agent 协同开发的偏离程度，主要由**概念与认知的统一程度**决定。
> 会话一结束上下文就没了；只有固化下来的词条能跨过去，让下个 agent 不必重问一遍。

## 梳理计划：五域

> **域是「先定义谁、后定义谁」的排序工具，不是项目内容的分类图。**
> 为什么需要排序：定义「地点」不能引用还没定义的「记录」；定义「记录」不能引用还没定义的「事件」。
> 顺序倒了，定义就会引用未定词，鸡同鸭讲原样重现。
> 所以域的名字必须是**范围名**（组织、骨架、文档记录…），不能是内容名——否则每层的填充物都和层名重叠。

| 域 | 含哪些词 | 状态 |
|---|---|---|
| ① 组织 | 维度一 结构：项目 / 任务 / 会话<br>维度二 信息：工作项 / 共识 | **维度一已定**<br>维度二部分已定 |
| ② 骨架 | 阶段 / 制品 / 门禁 / git 分支 / 版本 | 未开始 |
| ③ 文档记录 | 记录 / 索引 / 树 / 分支（血缘）/ 节点 / 来龙去脉 / 事件 | 未开始 |
| ④ 协作 | 讨论 / 校准 / 签字 / 追问 / 五元素 | 未开始 |
| ⑤ 交付 | 交付 / 验收 / 缺陷 / 复发 / 预防 | 未开始 |

## ① 组织域 · 维度一 结构（已定）

> **结构（谁包含谁）与信息（在里面流动什么）是两个维度，不能用「三层还是四层」去想。**
> 依据（用户原话）：「三层结构是行业共性，没有工作项不影响三层结构的完整性；
> 工作项是三层结构传递的信息，不是三层结构本身。」

```
维度一 · 结构                    维度二 · 信息
项目（Project）                   工作项（Work item）
 └─ 任务（Task）                   共识（Consensus）
     └─ 会话（Session）
```

**维度一由 Aegis 定义，不对齐任何具体 agent 工具。**

> 检索对照：Codex 叫 Project → Thread → Task，Cosine 叫 Project → Task → Session → Turn，
> 各家对「任务与会话谁包谁」没有共识——**这正是 Aegis 必须自己定死的原因**。

### 项目（Project）

**上位概念 + 区别特征**：可独立交付的一个整体，持有它的全部任务与制品。

- **语境**：宿主工具层面的工作区（仓库根 / 本地目录）。Aegis 约定：项目根含 `AGENTS.md`
- **谁创建**：用户
- **不是什么**：
  - 不是任务（项目装任务，任务是它的一段工作）
  - 不是文件夹（文件夹只是物理位置，换位置不换项目）

**例句**：「Aegis 这个项目从 v1.0.0 做到 v1.3.2」——指整体，含全部任务与制品。

### 任务（Task）

**上位概念 + 区别特征**：有明确目标、开独立分支、过阶段门禁、结束时写一条开发事件记录的一次工作。

- **语境**：项目内。任务的边界由「分支 + 门禁 + 记录」三件事锚定
- **谁创建**：用户发起，或 agent 提议后用户确认
- **不是什么**：
  - 不是项目（任务装不下项目）
  - 不是会话（会话是它的**组成**手段，一个任务通常由多轮会话构成）
  - 不是工作项（工作项是**信息**，不是结构层）

**例句**：
1. 「本次任务：梳理概念命名」——有目标、有分支、做完要写一条记录。
2. 「上一个任务做完 handoff 机制，这个任务在做概念梳理」——两个任务，两个分支，两条记录。

### 会话（Session）

**上位概念 + 区别特征**：agent 与人交互的手段、工具、媒介，是结构的第三层。

- **语境**：存在于每个任务里。**多轮会话构成一个任务**
- **角色**：既是交互的载体，也是**工作项产生与共识形成**的场合
- **不是什么**：
  - 不是任务（会话是任务的组成，不是任务本身）
  - 不是「一次发言」（一次发言是会话内的一轮）

**例句**：
1. 「这次会话窗口被重置了，但任务还在」——会话可中断，任务不因会话中断而消失。
2. 「这个任务跨了三个会话才做完」——多轮会话构成一个任务。

## ① 组织域 · 维度二 信息（部分已定）

### 工作项（Work item）

**上位概念 + 区别特征**：在三级结构上**被承载、传递的最小信息单元**，承载一个具体目标或交互动向。

- **语境**：任务进行中产生，可能来自会话、文档、缺陷单
- **类型（开放集合）**：概念（议题）/ 要求 / 缺陷 / 决定 / 变更请求 / 评审
  - 注：这里的「概念」指**议题**（关于某个词该怎么理解的一次讨论），不是固化的词条
- **判据**：**能否给它一个可追踪的状态**（待办 / 进行 / 完成 / 废弃）
- **不是什么**：
  - **不是结构层**——它不属于项目/任务/会话中的任何一层，是流动在它们之间的信息
  - **不是事件**——事件 = 六要素可在语境中补全的、已被记录下来的工作项；**事件 ⊂ 工作项**（见③文档记录域）
  - 不是「事 / 东西」（口语，不进术语表）

> 命名依据：〔检索〕VS ALM 术语表 work item 类型 = task / change request / risk / review / requirement / bug；
> EndlessWiki 定义 work item = "the smallest trackable unit of work"。

**例句**：
1. 「这次任务里提到了『地点』『分支』『树』三个词」——三个概念（议题）型工作项。
2. 「决定暂停项目」——一个决定型工作项，同时也是事件。
3. 「嗯，对」——无语义承载，给不出状态，不是工作项。

### 共识（Consensus）

**上位概念 + 区别特征**：agent 从工作项中提炼出的、双方此后按同一理解行事的一致理解。

- **语境**：会话中形成。**可能已固化，也可能没有**
- **来源**：工作项
- **判据**：此后双方不再需要重新解释这件事；按同一理解行事
- **不是什么**：
  - **不是元概念**——元概念的作用域尚未梳理清楚（见下「待重新梳理」），本表不预设两者关系
  - **不是会议纪要**——纪要是过程记录（进 handoff），共识是提炼出的结论
  - 不是「一致同意所有细节」——只要在**当下需要判断的那一点上**一致即可

**例句**：
1. 「六要素是上限、按需取用，不硬凑」——从用户的一次纠正中提炼出的共识。
2. 「元概念到底是层还是类型」——讨论过三轮，直到 H-0009 才形成共识（结论是：作用域待重新梳理）。

## 待重新梳理：元概念

> **当前不给定义。** 这个词从本轮讨论开始就被双方各自按推测在使用，定义域不清、作用域不明。
> 用「共识」暂代其在实际讨论中的功能后，元概念本身需重新梳理以下四项，梳理完再定是否收录、如何定义。

| 待答 | 说明 |
|---|---|
| **起因** | 当初为什么提出这个词？要解决什么具体问题？ |
| **范围** | 它泛指全项目所有不可再分的概念名词，还是只指某一类？ |
| **约束** | 什么算、什么不算？与「共识」「工作项」的边界在哪？ |
| **作用对象** | 它对谁起作用（人 / agent / 文档 / 流程）？在哪个环节被使用？ |

**已有线索**（未验证，不得当结论用）：
- 用户最初的推测：它解决「会话中涉及概念、需要统一认知」的问题
- 用户看到五域计划后的判断：可能不止于此，「元概念可能是泛指，项目里所有不可再分的概念名词都要纳入梳理范畴」
