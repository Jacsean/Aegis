# CONCEPTS · 全局概念表（术语表）

> **本表是全项目唯一的概念定义处。** 任何文档里出现的概念词，含义以本表为准。
> 文档开头若有「本文用词」节，只放一句话 + 指向本表锚点；**定义只在本表写一次。**
>
> **收录判据**（GB/T 10112-2019 / ISO 704，三条同时满足才收）：
> 1. 文件中至少使用两次
> 2. 专业使用者在不同语境中理解不一致
> 3. 尚无定义，或已有定义需改写
>
> **条目写法**：
> - 内涵定义 = **上位概念 + 区别特征**（不用否定式定义，不循环定义）
> - 记叙文六要素为上限、**按需取用**，用不上不硬凑
> - **「不是什么」必填**，至少一条
> - 单条 100~150 字；超了说明该拆
> - 附真实例句（词义由语境圈定，无例句的定义是悬空的）

## 本表是什么 / 不是什么

| 本表**是** | 本表**不是** |
|---|---|
| 把**已达成的共识**固化成词条的地方 | 会议记录、过程档案（那些进 `handoff/H-*.md`）|
| 让不同会话里的不同 agent 拿到**同一理解** | 通用词典（只收项目内不可再分的词）|
| 项目语言的锚点 | 项目结构本身（结构是它描述的对象）|
| 只增不删、改要留痕的活文档 | 一次性写死的规范 |

## 使用方式（三个场景）

| 谁 | 什么时候 | 读多少 |
|---|---|---|
| 梳理中的 agent 和用户 | 逐词定案 | 完整条目 |
| 新会话的 agent | 会话启动 | 只读本页目录（一句话列）|
| 查文档的人 | 遇到生词 | 按锚点跳到该词条目 |

> **本表为什么存在**（详见 `handoff/H-0007`）：
> 人类与 agent 协同开发的偏离程度，主要由**概念与认知的统一程度**决定。
> 会话一结束上下文就没了；只有固化下来的词条能跨过去，让下个 agent 不必重问一遍。

## 梳理计划：五域

> **域是「先定义谁、后定义谁」的排序工具，不是项目内容的分类图。**
> 为什么需要排序：定义「地点」不能引用还没定义的「记录」；定义「记录」不能引用还没定义的「事件」。
> 顺序倒了，定义就会引用未定词，鸡同鸭讲原样重现。
> 所以域的名字必须是**范围名**（组织、骨架、文档记录…），不能是内容名——否则每层的填充物都和层名重叠。

| 域 | 含哪些词 | 状态 |
|---|---|---|
| ① 组织 | 维度一 结构：项目 / 任务 / 会话<br>维度二 信息：工作项 / 共识 | **维度一已定**<br>维度二部分已定 |
| ② 骨架 | 阶段 / 制品 / 门禁 / git 分支 / 版本 | **已定** |
| ③ 文档记录 | 记录 / 索引 / 事件 / 来龙去脉 / 地点 / 分支（血缘）| 首轮已查，待验收 |
| ④ 协作 | 讨论 / 校准 / 签字 / 追问 / 五元素 | **已定**（2026-10-21 用户验收 10/10）|
| ⑤ 交付 | 交付 / 验收 / 缺陷 / 复发 / 预防 | **已定**（2026-10-21 用户验收 10/10）|

**状态四态**（每个词条、每个域必带其一）：`已定`（用户验收过）｜`暂定`（提了但未正式确认）｜`已修订`（定义变过，保留旧定义 + 日期）｜`已作废`（划掉并指向新词）。
**只增不删**：过期的词条划掉并指向新词，不删除——旧结论被删，下个 agent 会按旧结论重做一遍。

## ① 组织域 · 维度一 结构（已定）

> **结构（谁包含谁）与信息（在里面流动什么）是两个维度，不能用「三层还是四层」去想。**
> 依据（用户原话）：「三层结构是行业共性，没有工作项不影响三层结构的完整性；
> 工作项是三层结构传递的信息，不是三层结构本身。」

```
维度一 · 结构                    维度二 · 信息
项目（Project）                   工作项（Work item）
 └─ 任务（Task）                   共识（Consensus）
     └─ 会话（Session）
```

**维度一由 Aegis 定义，不对齐任何具体 agent 工具。**

> 检索对照：Codex 叫 Project → Thread → Task，Cosine 叫 Project → Task → Session → Turn，
> 各家对「任务与会话谁包谁」没有共识——**这正是 Aegis 必须自己定死的原因**。

### 项目（Project）

**上位概念 + 区别特征**：可独立交付的一个整体，持有它的全部任务与制品。

- **语境**：宿主工具层面的工作区（仓库根 / 本地目录）。Aegis 约定：项目根含 `AGENTS.md`
- **谁创建**：用户
- **不是什么**：
  - 不是任务（项目装任务，任务是它的一段工作）
  - 不是文件夹（文件夹只是物理位置，换位置不换项目）

**例句**：「Aegis 这个项目从 v1.0.0 做到 v1.3.2」——指整体，含全部任务与制品。

### 任务（Task）

**上位概念 + 区别特征**：有明确目标、开独立分支、过阶段门禁、结束时写一条开发事件记录的一次工作。

- **语境**：项目内。任务的边界由「分支 + 门禁 + 记录」三件事锚定
- **谁创建**：用户发起，或 agent 提议后用户确认
- **不是什么**：
  - 不是项目（任务装不下项目）
  - 不是会话（会话是它的**组成**手段，一个任务通常由多轮会话构成）
  - 不是工作项（工作项是**信息**，不是结构层）

**例句**：
1. 「本次任务：梳理概念命名」——有目标、有分支、做完要写一条记录。
2. 「上一个任务做完 handoff 机制，这个任务在做概念梳理」——两个任务，两个分支，两条记录。

### 会话（Session）

**上位概念 + 区别特征**：agent 与人交互的手段、工具、媒介，是结构的第三层。

- **语境**：存在于每个任务里。**多轮会话构成一个任务**
- **角色**：既是交互的载体，也是**工作项产生与共识形成**的场合
- **不是什么**：
  - 不是任务（会话是任务的组成，不是任务本身）
  - 不是「一次发言」（一次发言是会话内的一轮）

**例句**：
1. 「这次会话窗口被重置了，但任务还在」——会话可中断，任务不因会话中断而消失。
2. 「这个任务跨了三个会话才做完」——多轮会话构成一个任务。

## ① 组织域 · 维度二 信息（部分已定）

### 工作项（Work item）

**上位概念 + 区别特征**：在三级结构上**被承载、传递的最小信息单元**，承载一个具体目标或交互动向。

- **语境**：任务进行中产生，可能来自会话、文档、缺陷单
- **类型（开放集合）**：概念（议题）/ 要求 / 缺陷 / 决定 / 变更请求 / 评审
  - 注：这里的「概念」指**议题**（关于某个词该怎么理解的一次讨论），不是固化的词条
- **判据**：**能否给它一个可追踪的状态**（待办 / 进行 / 完成 / 废弃）
- **驻留**：工作项不单独建档。跨会话未闭合的，必须列在 `STATE.md`「进行中」，并在该任务 handoff 记录的「下一步 / 等谁」点名
- **不是什么**：
  - **不是结构层**——它不属于项目/任务/会话中的任何一层，是流动在它们之间的信息
  - **不是事件**——事件 = 六要素可在语境中补全的、已被记录下来的工作项；**事件 ⊂ 工作项**（见③文档记录域）
  - 不是「事 / 东西」（口语，不进术语表）

> 命名依据：〔检索〕VS ALM 术语表 work item 类型 = task / change request / risk / review / requirement / bug；
> EndlessWiki 定义 work item = "the smallest trackable unit of work"。

**例句**：
1. 「这次任务里提到了『地点』『分支』『树』三个词」——三个概念（议题）型工作项。
2. 「决定暂停项目」——一个决定型工作项，同时也是事件。
3. 「嗯，对」——无语义承载，给不出状态，不是工作项。

### 共识（Consensus）

**上位概念 + 区别特征**：agent 从工作项中提炼出的、双方此后按同一理解行事的一致理解。

- **语境**：会话中形成。**可能已固化，也可能没有**
- **来源**：工作项
- **判据**：此后双方不再需要重新解释这件事；按同一理解行事
- **生效条件**：必须注明确认者。**未经用户确认的，只能标 `暂定`；agent 之间达成的理解不得自行升为共识**
- **修订 / 作废**：定义变了标 `已修订` 并保留旧定义；不再成立标 `已作废` 并指向新词
- **不是什么**：
  - **不是元概念**——元概念的作用域尚未梳理清楚（见下「待重新梳理」），本表不预设两者关系
  - **不是会议纪要**——纪要是过程记录（进 handoff），共识是提炼出的结论
  - 不是「一致同意所有细节」——只要在**当下需要判断的那一点上**一致即可

**例句**：
1. 「六要素是上限、按需取用，不硬凑」——从用户的一次纠正中提炼出的共识。
2. 「元概念到底是层还是类型」——讨论过三轮，直到 H-0009 才形成共识（结论是：作用域待重新梳理）。

## ② 骨架域（5 个词，全部 `已定`）

> 前两个词（阶段 / 制品 / 门禁）是 Aegis 的内部实现，用户不介入设计，只看结果能否撑住应用场景。
> 后两个词（git 分支 / 版本）直接进用户的操作习惯，用他「建分支做事 → 合并 → 打 tag」的流程验。

### 阶段

**上位概念 + 区别特征**：一个由出口门禁把关的工作段落，有固定的输入与必备制品。`已定`

- **判据**：当前阶段由 `STATE.md` 记录；阶段的**出口**由 `gate.sh` 判
- **不是什么**：
  - 不是时间划分（不是「第几天」）
  - **不是可以随便跳过的环节**——跳过必须写明豁免并记入 `STATE.md`
- **场景验**：「代码写完了但没写测试」→ P4 出不去，因为制品缺；不是靠 agent 自称

### 制品

**上位概念 + 区别特征**：阶段出口必须存在的固定产物——固定路径、固定 schema、登记索引。`已定`

- **判据**：文件在约定路径上、字段齐、已登记 `docs/INDEX.md`；三者缺一不算
- **不是什么**：
  - 不是「任何产出」（口头说明、聊天里的结论都不算）
  - 不限于代码（代码是 P4 制品之一，文档也是制品）
- **场景验**：「agent 说做完了」→ 没有制品就是没做完（铁律三）

### 门禁

**上位概念 + 区别特征**：阶段出口的机械检查，脚本执行，不过就拒绝进入下一阶段。`已定`

- **判据**：`bash scripts/gate.sh <阶段>` 返回 PASS / FAIL；FAIL 不许前进
- **不是什么**：
  - **不是人的评审**（评审是 P3/P5 的另一件事，门禁只查「有没有、合不合格式」）
  - **不是建议**（FAIL 即阻断，没有「先跳过回头补」）
- **场景验**：在 main 上跑 P6 会报「当前不在任务分支」——这是设计行为，不是 bug

### git 分支

**上位概念 + 区别特征**：版本库中隔离一次任务改动的一条线，任务完成合回 main。`已定`

- **判据**：`git branch --show-current` 能查到；一个任务一条，任务结束即合并并删除
- **不是什么**：
  - **不是「分支（血缘）」**——那个是记录之间的关系，与版本库无关
  - 不是长期存在的开发线（本套流程里分支是任务级的，用完就合）
- **场景验**：用户习惯「建分支做事 → 合并 main → 打 tag」；本定义与之一致

### 版本

**上位概念 + 区别特征**：对外的发布标识，语义化三段，只在合并进 main 时变。`已定`

- **判据**：`VERSION` 文件 + `CHANGELOG.md` 顶部条目 + `git tag` 三者同时存在且一致
- **不是什么**：
  - 不是每次提交都变（分支上不变）
  - 不是分支名
- **场景验**：修索引 → PATCH（1.3.0→1.3.1）；加新功能 → MINOR；改阶段骨架或铁律 → MAJOR

## ③ 文档记录域（6 个词，全部 `已定`）

> 来源：A 轨道首轮（H-0012、H-0013）。验收场景全部取自用户原话，不取 agent 想象。
> 六个词全部 `已定`（用户 2026-10-21 两次确认）。

### 地点

**上位概念 + 区别特征**：事情发生或作用于哪里。`已定`

- **怎么填**：粒度由「查的时候靠什么定位」决定，不按写得细不细
- **三种场景**（用户原话给的）：
  - 代码问题 → **代码文件 + 行号**（不是 commit）
  - 需求变更 → **变更发生在哪**（办公室 / 客户现场 / 线上会议）
  - 文档结论 → **文档 + 章节**
- **不是什么**：
  - **不是文件存放目录**（「这条记录存在哪」是另一回事）
  - **不是 commit 号**——commit 是可追溯凭据，写在「怎么处理的」里
- **验不过的旧写法**：`handoff-schema.md` 现在写「Where 位置 = 代码任务由 git 记录 / `src/export/csv.py`，commit `a1b2c3d`」——**只覆盖代码类**，遇到「客户现场改需求」这类事，这个定义填不出来

### 分支（血缘）

**上位概念 + 区别特征**：一组记录构成的一条来龙去脉。`已定`

- **怎么用**：从某条记录起，沿「上接」往上、沿「下接」往下，走到头就是一根完整枝
- **不是什么**：
  - **不是 git 分支**——凡指版本库分支，一律写「git 分支」
  - **不是「树」**——「树」是整张图，不是一条枝；本表不再用「树」指代记录结构
- **旧写法的问题**：`handoff-schema.md` 只允许**一个**上接、一个下接 → 只能表达直线。两条线汇到一处就断（例：H-0009 同时接 H-0008 与你那句原话，只能挂一个）
- **修法**：上接允许写多个（逗号分隔）；分叉处写一句「因何分开」

### 记录

**上位概念 + 区别特征**：一件事的完整书面留档，一个文件一条。`已定`

- **在哪**：`dev/handoff/H-<编号>-<短名>.md`
- **判据**：一条记录 = 一个事件（六要素在语境里补得齐）
- **不是什么**：
  - **不是索引里的一行**——那行只是入口，只放定位信息
  - **不是「记录」这个动作**
  - 不是流水账的连续段落（一条一个文件，不许混装两件事）
- **旧歧义**：用户曾说「搜索…定位文档内容的位置行」，把记录当成了「行」。两层结构下，「行」是索引，「记录」是文件——这一点以前没写明

### 索引

**上位概念 + 区别特征**：指向记录的定位表，一行一条，只放定位信息、不复制内容。`已定`

- **在哪**：`dev/HANDOFF.md`
- **用途**：扫、grep、找线索
- **不是什么**：
  - **不是摘要**（不替代记录；看懂了索引不等于看懂了事）
  - **不是目录**（不按主题组织，按时间倒序）
  - **不是副本**（内容只有一份，在记录里）
- **为什么不浪费**：10 条时读索引约 180 tokens，全读记录约 3900；300 条时索引约 5500，全读记录 11 万——超上限，根本读不了。**索引的作用是让「不读正文」成立**

### 事件

**上位概念 + 区别特征**：能用六要素（时间 / 地点 / 人 / 起因 / 经过 / 结果）在语境里补全的、已被记录的一个发生。`已定`

- **判据**：六要素补得齐 = 一个事件；补不齐 = 太细，并进邻近的；要两套 = 拆成两个
- **不是什么**：
  - 不是任务（任务是结构层的容器；一个任务含多个事件）
  - **不等于工作项**——事件 ⊂ 工作项，工作项还包括还没被记录的要求、缺陷、决定
- **例句**：「地点和分支两个词查出错，给出新定义」是一个事件；「嗯，对」不是

### 来龙去脉

**上位概念 + 区别特征**：一件事的因果链——从起因到当前状态，靠血缘（上接／下接）走通。`已定`

- **判据**：能沿上接走到起因、沿下接走到现状，中途不断线
- **不是什么**：
  - **不是时间顺序**——相邻两条未必相关，时间先后只是线索
  - **不是全部历史**——只跟这件事有关的那条枝，不是整个项目
  - **不是看一遍索引的结果**——索引给线索，链条在记录里

### 不收：节点

出现 3 次，全是 agent 自造（H-0009 的「三节点链」、五域计划、待查清单），**用户从未使用，项目里也没有真实场景需要它**；它要表达的东西就是「记录」。

- **处理**：从计划里删掉。凡需指血缘图上的一个点，直接写「记录」
- **依据**：GB/T 10112 判据一不成立（无真实使用）；用户「精简必要」原则

## ④ 协作域（5 个词，`已定`）

> 这一域决定「你和 agent 怎么对话、什么时候算谈完了」。验收场景取自本轮的真实争执，不取自想象。

### 讨论

**上位概念 + 区别特征**：双方就一个**待定判断点**交换判断，目的是让分歧显形。`已定`

- **判据**：谈完能指出「原先的分歧在哪、现在定了哪个」
- **不是什么**：
  - 不是汇报（单向输出，没有待定点）
  - 不是辩论（目标是赢，不是让分歧显形）
  - 不是聊天（没有待定的判断点）
- **场景验**：本轮「探明」那次被批评「脱离项目实际」——当时双方都在讲，但没有一个待定点被显形，那是失败的一次讨论

### 校准

**上位概念 + 区别特征**：对齐意图的两轮讨论，把「要解决什么问题」对齐到能写需求文档的程度。`已修订`（2026-10-21，H-0021）

> ~~旧定义：「P0.5 的两轮讨论，对齐到能写 PRD」~~ ——「P0.5」是被八阶段定稿（S1~S8）推翻的九阶段旧编号；
> 定义去阶段编号化。现行流程编号 P05；八阶段落地后为 S2 对齐。

- **判据**：R1 复述 + R2 挖「什么算失败」，两轮都留档（`docs/align/ALIGN-*.md`）
- **不是什么**：
  - **不是需求评审**——校准的对象是还没写出来的意图，评审的对象是已写好的文档
  - 不是一次问答（复述轮与深层轮不可合并）
- **场景验**：本轮用「五要素」重问一次「共识要解决什么」后，才暴露出「元概念的动机有两个」——那是校准在起作用

### 签字

**上位概念 + 区别特征**：使用者对某个阶段出口的明确确认，记在 `STATE.md` 并附原话。`已定`

- **判据**：`STATE.md` 里有「总确认原话：<非空>」；门禁据此放行
- **不是什么**：
  - **不是「没反对」**——沉默、点头、「看着还行」都不算
  - 不是 agent 的自我声明（agent 说「已完成」永远不等于签字）
- **场景验**：本轮你说「对」= 签字；说「下一步」= 只是让我继续，不是签字

### 追问

**上位概念 + 区别特征**：紧接上一问、为把含糊处逼具体而加的问。`已定`

- **判据**：追问之后，原先含糊的那个点有了可判对错的答案
- **不是什么**：
  - 不是换个说法重问（那是没听懂，不是追问）
  - 不是另起话题
- **场景验**：你说「分支」时，正确的追问是「指记录间的血缘，还是版本库分支？」——一句话就能定，而我当时没问，直接按 git 分支答了

### 五元素

**上位概念 + 区别特征**：提一个问题时按需带的五个部件——从哪来 / 不问会怎样 / 你该怎么判断 / 选项+后果 / 我可能没问对。`已定`

- **判据**：按需取用；省了必须写明理由；标准是「非专家能否判断对错」
- **不是什么**：
  - **不是必须五个都写**（写全了反而啰嗦，你已经指出过）
  - 不是话术（它解决的是「判断依据缺不缺」，不是「话说得好不好听」）

## ⑤ 交付域（5 个词，`已定`）

### 交付

**上位概念 + 区别特征**：把做好的东西交给使用者，并让他能自己用起来。`已定`

- **判据**：有交付说明 + 步骤真跑过一遍 + 写明已知限制
- **不是什么**：
  - 不是「代码能跑」（只有写它的人会跑，不算交付）
  - **不是 P6 归档**——归档给下一个 agent，交付给使用者，混写两头失败
- **场景验**：这次给的是 `aegis-git-v1.4.1.tar.gz` + 一页验收说明，你解压后自己跑通——那才叫交付

### 验收

**上位概念 + 区别特征**：使用者按**自己的标准**判断这东西能不能用。`已定`

- **判据**：使用者能独立完成一次真实使用，不需要 agent 在旁边解说
- **不是什么**：
  - **不是 agent 自测**（自己测自己不算验收）
  - 不是「跑通了」（跑通只说明没崩）
- **场景验**：本次真机验收——不给 Reasonix 任何前情，它答对了「地点怎么填」「共识是什么」。**这就是验收该有的样子：换个人（或 agent）也能用**

### 缺陷

**上位概念 + 区别特征**：做出来的东西与应有行为不符，且能被复现。`已定`

- **判据**：能写出复现步骤；写不出的叫疑点，不叫缺陷
- **不是什么**：
  - 不是「我觉得不好用」（那是改进建议）
  - 不是还没做的功能（那是没实现，不是做错）

### 复发

**上位概念 + 区别特征**：同一个缺陷在修好之后又出现。`已定`

- **判据**：与历史 `INC` 记录的根因相同
- **不是什么**：不是新缺陷碰巧症状相似（症状像不等于根因同）
- **场景验**：`06-P5-verify.md` 说「跳过第三轮，历史缺陷必然复发」——那句话就是在防复发

### 预防

**上位概念 + 区别特征**：为阻止某个缺陷再发生而加的机制（门禁 / 模板 / 检查 / 禁令）。`已定`

- **判据**：写得出「下次靠什么拦住它」；拦不住的叫提醒，不叫预防
- **不是什么**：
  - **不是「下次注意」**（靠人不靠机制，必然复发）
  - 不是补一个测试就完（那只覆盖这一例）
- **场景验**：本次改 `gate.sh` 加「概念表存在 + 目录非空」，防的是「概念表做了没人读」——这才是预防

## 元概念 `已作废`（2026-10-21 结案）

**结论：不收进本表，作为历史说明保留。** 凡原先想用「元概念」表达的地方，分两种情况写：
—— 指**已固化的词条**，写「词条」；指**会话里达成的一致理解**，写「共识」。

**四问的答案（这就是它为什么该作废）**：

| 待答 | 结论 |
|---|---|
| 起因 | agent 为「让定义有底」自造，不是用户提出的需求；同时用户曾推测它解决「会话中概念统一」，两个动机不同 |
| 范围 | 从未界定。实际用途被两样东西分担了：`共识`（会话内的理解）+ `词条`（固化后的定义）|
| 约束 | 无法界定——判据一（项目内有 ≥2 次真实使用）不成立：全仓出现处几乎都是 agent 自造与讨论本身 |
| 作用对象 | 无。没有任何流程、门禁或文档真正依赖它 |

**保留这段的理由**：防止以后有人（或 agent）重新造出这个词。
