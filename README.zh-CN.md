# Aegis

**让 AI 助手说的和做的对得上。**

换个会话它接得上，交付时有据可查，破坏规矩的动作会被拦下。

装进任何项目，60 秒生效。**不覆盖**你已有的 skills、规则和工具。

`v3.0.0` · 当前支持 Reasonix（Claude Code / Trae 适配中）

## 这些场景你熟悉吗

不是你的问题——这是现在 AI 编程助手普遍存在的现象。

| 你会遇到的 | 代价 |
|---|---|
| **换个会话，它全忘了** | 你要重新解释一遍项目背景、技术选型、已经否掉的方案 |
| **它说"用了第一性原理分析"，你找不到分析在哪** | 方法成了口号。你说不出哪里不对，但就是不放心 |
| **它说"做完了"，你一检查发现有遗漏** | 你得自己逐条核对，比自己做还累 |
| **它自作主张改了你没让改的地方** | 出了问题你分不清是它干的还是原来就这样 |
| **同一个坑踩第二次** | 上次讨论过、否掉了，这次它又提出来 |

### 这不是个别现象，业内已经量化过

- **824 条**确定性标准，最好的前沿模型在严格评分下只通过 **36.2%**。失败模式包括「跳过验证」「检查了但忽略」「虚假报告合规」。
- **679 份**真实项目规则文件、**5,000+ 次**运行测出：**负向约束**（"不许做什么"）是唯一单独有效的规则类型。正向指令单独添加反而**有害**。
- 结构化要求累积时，AI 助手表现会**显著下降**——约束会随上下文增长而衰减。

**结论很直接**：写更多的规范文档不管用。
**关键约束必须放在模型外面强制执行。**

## 装上之后，会有什么变化

### 1️⃣ 每个决定都有记录，换会话 30 秒接上

它往 `NOTES.md` 里写：用了什么方法、判断是什么、排除了什么、
**你明确否定过什么**、什么情况能说明它错了。

新会话开口前先读这份记录。实测：换一个全新会话，只给它一句 *「接着做，把那个功能写完」*——

> 它主动读了记录，直接接上进度，**没有重提你之前否掉的任何方案**。

### 2️⃣ 说的和做的一致

四个维度逐条核对——**任何一项不过，就不算完成**：

| 维度 | 它查什么 |
|---|---|
| **认知** | 声称用了某个方法，输出里有没有对应的痕迹？ |
| **事实** | 标了「有出处」，有没有真给出处？ |
| **语义** | 有没有自造术语、和你项目的词对不上？ |
| **时间** | 该记的记了没？下次能不能接上？ |

### 3️⃣ 关键动作自动拦下，不靠自觉

```
写文件时   → 没有 NOTES.md 就拦下        ← 强制留下记录
主干上提交 → 拦下，要求先建分支          ← 强制任务隔离
```

不是提示，不是建议，**真的拦住**。它会说明原因，并告诉你怎样才能解开。

### 4️⃣ 16 个思维模型，只在需求含糊时出场

第一性原理、逆向思考、事前验尸、Kano、双环反思……另外还有 11 个。
需求含糊 → 它多想一层；需求明确 → **它不打扰你**（每轮常驻约 40 token）。

## 用它之前 vs 之后

| | 之前 | 之后 |
|---|---|---|
| 换会话 | 从零解释一遍 | 读记录，接上进度 |
| 交付检查 | 你自己逐条核对 | 四个维度先跑一遍，**没过会点名说哪里没过** |
| 关键动作 | 靠它自觉 | 自动拦下，附原因和解法 |
| 同一个坑 | 可能踩第二次 | 否定过的会留在记录里，下次不会再提 |
| 你对它的信任 | 靠感觉 | 每一条都能查证 |

## 60 秒开始用

```bash
git clone https://github.com/Jacsean/Aegis.git
cd Aegis
bash scripts/install-v3.sh /path/to/your-project
```

**不会覆盖你的任何东西**：

- 已有的 `AGENTS.md` / `CLAUDE.md` → **标记内追加**，原文完整保留
- 已有的 hooks 配置 → **合并进去**，你原有的不动
- 已有的 skills → 只新增 Aegis 的

装完重开一次会话。Windows 上 Git Bash 冷启动慢，超时已给到 15 秒。

**卸载**：删掉追加的那一段 + `.reasonix/hooks/aegis-*.sh` 四个文件，其余无残留。

## 它管什么，不管什么

**明确分工，避免你误判它的能力边界：**

| Aegis 管 | Aegis 不管 |
|---|---|
| 有没有留下记录 | 你的代码写得好不好 |
| 说的和做的是否一致 | 你的技术选型对不对 |
| 关键动作是否守规矩 | 你的测试够不够 |
| 交付前四个维度过没过 | 你的架构合不合理 |
| 什么被否定过、有没有再犯 | 你可能没想到的事 |

> **它是一道安全带，不是一位军师。** 它保证你说得出、记下来、接得上。
> 但决定什么、怎么想——那仍然是你的事。

**也不适合**：一次性小脚本（装了反而是负担）、纯探索性的技术预研（不需要留档）。

## 和你已有的工具什么关系

**装在任何已有工具之上，不替换任何东西。**

| 你已有的 | 怎么共处 |
|---|---|
| 测试、调试、写计划、分支管理、workflow 类 skills | **完全不碰**，Aegis 只做自己那四件事 |
| 代码评审 / 安全评审 | **各查各的**——它们评内容，Aegis 查记录和一致性 |
| 需求发散类 | **前后串联**——Aegis 先问"你要的是不是他真需要的"，它再发散 |

装完会生成 `AEGIS-分工.md`，**自动扫描你已装的能力**并列出关系，
还会指出你的全局规则和项目规则之间**有哪些潜在冲突**。

**外接能力预算**：单个任务最多同时用 **2 个**。
依据：同时激活的技能越多，遵循率按乘法下降（4 个各 90% → 合计 66%）。

## 实测记录

| 场景 | 结果 |
|---|---|
| 没有记录时写文件 | 被拦下，文件确实没被创建 |
| 主干上提交 | 被拦下，并给出「先建分支」的解法 |
| 四个维度检查 | 各自抓到真实缺陷：说了没做 / 标了没给来源 / 自造术语 / 没留记录 |
| 全新会话接手 | 主动读记录、接上进度、没重提被否定的方案 |
| 被拦之后的行为 | 去读规则脚本搞清楚原因，然后自己补齐前置条件 |

## 文档结构

```
docs/
├── guides/         怎么装、怎么用
├── reference/      术语表（唯一概念定义处）
```
