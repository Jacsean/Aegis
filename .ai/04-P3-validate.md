# 04 · P3 验证（Validate Design）

> 目的：**设计做完先自查，再进实现。**
> 在纸上改，成本是改代码的 1/10。
>
> 本阶段不写代码、不改设计内容 —— 只做**审查与判定**。

---

## 为什么单独一个阶段

通用框架里"设计完就直接实现"，问题在纸上发现不了，等写出来才发现，返工成本十倍。

更隐蔽的问题是：**之前犯过的错会再犯**，因为没有机制把历史教训带进新设计。

P3 就是补这两个缺口：
1. 强制自查（12 项清单）
2. 强制历史回灌（对照 incidents 库）

---

## 输入

- `docs/design/DESIGN.md`

## 动作清单

### 1. 逐条过 12 项清单

清单全文见 `.ai/99-reference/design-review-checklist.md`。

**不是打勾了事** —— 每一项都要写下：
- 检查了什么
- 结论是什么
- 发现问题 → 怎么处理

### 2. 意图一致性复核（本阶段特有）

除了 12 项技术清单，额外做一次**意图比对**：

| 对照项 | 检查什么 |
|---|---|
| ALIGN 第 4 节「这次做什么」 | DESIGN 是否全都覆盖 |
| ALIGN 第 5 节「这次不做什么」 | DESIGN 是否偷偷做了 |
| ALIGN 第 5 节「绝对不要」 | DESIGN 是否踩了红线 |
| ALIGN 第 6 节「什么算搞砸」 | DESIGN 是否会导致那些情形 |

> 这一步比技术清单更容易发现问题。技术都对，但做的不是用户要的 —— 这才是最贵的错。

### 3. 历史缺陷回灌

打开 `docs/incidents/`，**逐条**问：

> 「这个设计会不会让 INC-xxxx 再发生一次？」

记录格式：

| INC | 现象 | 会不会再犯 | 依据 |
|---|---|---|---|
| INC-0001 | 时区导致日期偏移 | 否 | DESIGN 3.4 统一用 UTC 存储 |
| INC-0002 | 空数据崩溃 | **是** | DESIGN 未定义空状态 → 已补 |

「会不会再犯=是」的，必须当场补设计或登记为已知限制。

### 4. 写评审记录

`docs/design/REVIEW-DESIGN.md`，按模板逐项记录。

### 5. 给出结论（三选一）

| 结论 | 条件 | 下一步 |
|---|---|---|
| **通过** | 12 项全绿，无 Critical | 进 P4 |
| **修正后通过** | 1-2 项小问题，已现场修正 | 进 P4 |
| **退回 P2** | 3 项以上问题，或涉及架构/意图偏差 | 回 P2 重新设计 |

## 出口门禁

- [ ] `REVIEW-DESIGN.md` 存在，且勾选条目 ≥ 12
- [ ] 每项都有结论，不是空勾
- [ ] 有「意图一致性复核」一节，对照了 ALIGN 的四节
- [ ] 有「历史缺陷回灌」一节，逐条对照了 incidents
- [ ] 结论明确（通过 / 修正后通过 / 退回 P2）
- [ ] 若「退回 P2」，则**不得进入 P4**
- [ ] `bash scripts/gate.sh P3` 输出 PASS

## 人工确认

⚠️ **建议确认，但不强制**。

- 小改动：agent 自查通过即可进 P4
- 涉及架构 / 用户可见行为变化：**必须**给用户看结论摘要

给用户的摘要格式（不要贴全文）：

```
P3 设计评审完成，结论：<通过 / 修正后通过 / 退回 P2>

发现的问题：
1. <问题> → <处理>
2. <问题> → <处理>

历史故障回灌：检查了 N 条历史问题，其中 1 条可能重犯，已补设计。

是否可以进入实现？（Y / 先看 REVIEW-DESIGN.md）
```

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **只打勾不写结论** | 等于没查，自欺 | 每项必须写"查了什么、结论是什么" |
| **跳过意图复核，只看技术** | 技术都对但做的不是用户要的 | 必须对照 ALIGN |
| **不回灌历史故障** | 老毛病反复出现 | 逐条对照 incidents |
| **发现问题但"先实现再说"** | 返工成本 ×10 | 当场修或退回 P2 |
| **沉没成本心态**：已经写了很多，不忍推翻 | 带着缺陷进实现 | 已写的不是保留理由 |
| **自己审自己做的设计还自我说服** | 自证无效 | 按清单机械执行，不靠感觉 |

---

## 关键判断：什么时候该退回 P2

不要因为"已经写了不少"而勉强通过。以下任一情况，**退回 P2**：

- 发现需求理解错了（→ 其实该回 P0.5 或 P1）
- 架构方向不对（分层错了、依赖成环）
- 缺少关键模块，要新增
- 前端 demo 无法支撑 PRD 的关键界面
- 3 项以上清单不过

> 退回不是失败，是省钱。设计阶段推翻的成本是实现的 1/10。
