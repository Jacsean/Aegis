# S8 · 交付（手法细则）


> 目的：把"我做完的东西"变成"别人能用的东西"。
>
> S7 是给自己/给 agent 的归档；**S8 是给使用者的交付**。
> 两者读者不同，写法就不同。

---

## 为什么"跑通了"不等于"交付了"

代码能跑，只有写它的人知道怎么跑。交付的门槛是：

> **一个没参与开发的人，只看这份说明，能自己跑起来并用起来。**

所以 S8 的核心不是"总结做了什么"，而是**验证这份说明真的能走通**。

- 不是"写了安装步骤"，而是**照着重装了一遍，装成功了**
- 不是"说明了怎么用"，而是**照着命令敲了一遍，输出了预期结果**
- 不是"列了已知限制"，而是**把限制一个个试了一遍，确认描述准确**

---

## 铁律：交付必须真跑一遍

**写 RELEASE 时禁止凭代码阅读想象步骤。**

必须做一次**冒烟验证（Smoke Test）**：在一个干净环境里，严格照着 `RELEASE` 里的命令，从零走到能用，把过程输出贴进文档。

| 假交付 | 真交付 |
|---|---|
| 写了 `pip install -r requirements.txt` | 在干净 venv 里跑了这条，贴了输出 |
| 写了"访问 localhost:8000 即可" | 真的启动、真的打开、贴了截图或返回内容 |
| 写"支持导出 CSV" | 真的导了一个文件，贴了前 3 行内容 |

> 冒烟验证失败 → **退回 S6 修**，不是改文档描述来迁就现状。
> 文档迁就现状 = 把 bug 写成特性。

---

## 输入

- `CHANGELOG.md`（本版本改了什么）
- `STATE.md`（当前状态、已知限制）
- `docs/reviews/REVIEW-CODE-*.md`（S5 登记的 Major/Minor）
- `docs/incidents/INC-*.md`（本版本的坑，可能要写进"已知限制"）
- `docs/design/DESIGN.md`（架构概览，交付说明里要一句话说清这是什么）

---

## 动作清单

### 1. 先做冒烟验证，再写文档

顺序不能反。先跑，跑出来的输出才是文档的素材。

**最小冒烟清单**（按项目类型取用）：

```bash
# 通用：干净环境重建
rm -rf /tmp/smoke && git clone . /tmp/smoke && cd /tmp/smoke
make setup                      # 或文档里写的安装命令
<文档里写的启动命令>
```

| 项目类型 | 冒烟要验证什么 |
|---|---|
| Web 前端 | 打开首页 / 点一个主流程 / 刷新后状态还在 |
| 后端服务 | 启动成功 / 打一个健康检查 / 打一个真实业务请求 |
| 数据脚本 | 用示例数据跑一遍 / 输出文件存在且内容合理 |
| 库 SDK | 在临时目录里 `pip install -e .` / 跑示例代码 |

**冒烟结果三种：**

| 结果 | 处理 |
|---|---|
| 全通 | 把输出贴进 RELEASE 第 5 节 |
| 有步骤跑不通 | **退回 S6 修**（先改代码或改脚本，不改文档描述） |
| 文档里少写了步骤 | 补文档，重跑，直到能照抄成功 |

### 2. 写 `docs/release/RELEASE-v<X.Y.Z>.md`

模板见 `docs/release/RELEASE-template.md`。六节，其中**四节强制**：

| 节 | 强制 | 判断标准 |
|---|---|---|
| 1 本次交付了什么 | ✅ | 使用者能看懂"这东西对我有什么用" |
| 2 怎么用 | ✅ | **照抄能成功**（冒烟验证过） |
| 3 已知限制 | ✅ | 至少 1 条。写"无"通常说明没认真找 |
| 5 验证证据 | ✅ | 有真实输出，不是"已测试" |
| 4 下一步 | ⚠️ 可选 | 有明确规划才写，不要凑 |
| 6 签收 | ✅ | 用户填 |

**第 2 节「怎么用」的三个硬要求：**

1. **命令可直接复制粘贴**（不要 `<>` 占位符混在命令里，占位符单独列成表）
2. **写清前置条件**（需要什么版本的语言/工具，缺了会报什么错）
3. **写清成功的样子**（"看到 XXX 字样就是成功"，否则用户不知道对不对）

**第 3 节「已知限制」为什么强制：**

> 隐藏限制比限制本身更伤信任。
> 用户踩到一个你没说的限制，他会怀疑所有你说过的话。

限制必须写**具体场景**，不写抽象：

| ❌ | ✅ |
|---|---|
| 性能一般 | 数据超过 1 万条时，列表页加载约 5 秒 |
| 兼容性有限 | 只在 Chrome / Edge 测试过，Safari 未验证 |
| 功能不完整 | 不支持批量导入；一次只能加一条 |

### 3. 检查"用户的第一分钟"

站在使用者角度走一遍：

- [ ] 我不知道这是什么 → 文档开头有没有一句话说清用途
- [ ] 我不知道从哪开始 → 有没有"最快跑起来"的最小步骤
- [ ] 我跑失败了 → 有没有常见错误对照表
- [ ] 我跑成功了但不知道下一步 → 有没有"接下来可以试什么"

**常见错误对照表**（推荐加在第 2 节末尾，非常实用）：

| 现象 | 原因 | 解决 |
|---|---|---|
| `ModuleNotFoundError` | 没用 `.venv` | `make setup` 后用 `.venv/bin/python` |
| 端口被占用 | 8000 已被占用 | 换端口或 `lsof -i:8000` 杀掉 |

### 4. 请用户签收

交付的最后一步是**用户说"能用"**，不是 agent 说"已交付"。

要问的：

```
v1.3.0 交付完成。

快速验证方式（约 2 分钟）：
1. <第一条命令>
2. <第二条命令>
3. 打开 <地址>，应该看到 <预期>

验证输出我在 RELEASE 第 5 节贴了。

已知限制 3 条，请特别看第 3 节第 2 条（<最关键的那条>）。

能用的话请回一句"可以"；不能用请说现象，我修完重新交付。
```

**不要问"满意吗"** —— 要问"能用吗"。满意是主观评价，能用是可验证事实。

签字由用户给，agent 记入 `STATE.md`：

```bash
bash scripts/state.sh sign S8 "可以，能用"
```

### 5. 合并分支（最后一个动作）

```bash
make branch-finish NAME=<任务短名>
```

顺序：**过门禁 → 合并 → 打 tag（若 S7 未打）→ 清理分支**。

不要先合再签收 —— 签收前发现不能用，已经合并进 main 就麻烦了。

## 必备制品

| 制品 | 路径 | 要求 |
|---|---|---|
| 交付说明 | `docs/release/RELEASE-v<X.Y.Z>.md` | 六节，四节强制，含真实冒烟输出 |
| 索引登记 | `docs/README.md` | 已登记 |
| 用户签收 | `STATE.md` | `S8 确认：... ✅「原话」` |
| 版本标签 | git tag | 已合并到 main 并打 tag |

---

## 出口门禁

- [ ] `docs/release/RELEASE-v<X.Y.Z>.md` 存在
- [ ] 六节齐全，第 1/2/3/5/6 节非空
- [ ] **第 3 节「已知限制」至少 1 条**（写"无"会被拦）
- [ ] **第 5 节有真实输出**（不是"已测试"、"正常"）
- [ ] 第 2 节的命令与冒烟验证一致（能照抄成功）
- [ ] 用户已签收（`STATE.md` 有 S8 记录）
- [ ] `bash scripts/gate.sh S8` 输出 PASS

---

## 人工确认

✅ **强制**。这是整个流程的终点了。

签收必须是**用户真的验证过**，不是用户出于信任说"行"。

给用户的验证方式是**一条命令 + 一个预期结果**，越短越好。3 分钟能验完的交付，用户才会真的验。

---

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **没跑就写步骤** | 用户第一步就失败，信任归零 | 先冒烟，再写文档 |
| **冒烟失败却改文档迁就** | 把 bug 写成特性 | 退回 S6 修 |
| **已知限制写"无"** | 用户踩坑后不再信任其他说明 | 至少写 1 条具体的 |
| **命令里混占位符** | 用户复制后报错 | 占位符单独列表 |
| **只说"已完成"不说怎么验** | 用户无法确认，只能盲信 | 给一条命令 + 预期结果 |
| **问"满意吗"** | 得到的是客气话 | 问"能用吗" |
| **先合并再签收** | 不能用时 main 已被污染 | 签收后再合 |
| **交付说明写成技术总结** | 使用者看不懂（他不需要知道内部结构） | 写"怎么用"，不写"怎么实现" |

---

## Red Flags — STOP

- "步骤肯定没问题，我看代码写的" → 看过 ≠ 跑过
- "用户很熟，不用写这么细" → 三个月后他自己也不熟了
- "已知限制没什么好写的" → 没找到限制，通常是因为没测边界
- "先合并，签收回头再说" → 顺序反了
- "用户说'行'就够了" → 要问"你验证过了吗"
- "冒烟跑不通，文档里写'可能需要注意'就行" → 这是掩盖问题

---

## 与 S7 的区别（最容易混）

| | S7 固化 | S8 交付 |
|---|---|---|
| 读者 | **下一个会话的 agent** | **使用这个项目的人** |
| 回答 | 现在在哪、接下来干什么 | 这是什么、怎么用、有什么毛病 |
| 风格 | 极简、指针式、可跳转 | 完整、可照抄、可自助排错 |
| 位置 | `STATE.md` / `CHANGELOG.md` | `docs/release/RELEASE-*.md` |
| 强制签字 | ❌ | ✅ |

**混写会两头失败**：STATE 写太详细 → token 浪费；RELEASE 写太简略 → 用户看不懂。

---

## 交付完成之后

交付不是终点，是下一次的起点：

```
S8 完成 → 用户签收 → 合并 main → 打 tag
                              ↓
                    下一个需求来了
                              ↓
              建新分支 → 回 S2 对齐
```

**新需求一律回 S2**，哪怕只是"改个文案"。

不是形式主义：改文案的深层含义（改哪句、给谁看、为什么改）恰恰最容易被误读，
而误读的成本远高于两轮讨论的成本。

> 唯一例外：用户明确说"不用讨论了，就改这一个字"，可在 `STATE.md` 豁免记录里登记后直接执行。
