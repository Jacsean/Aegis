# 参考 · Incident Schema（故障与问题库）

> 按需加载。P4 调试、P5 校验、任何踩坑时使用。
> **这是"防止老毛病反复出现"的核心机制。**

---

## 什么时候必须记录

满足任一条件，必须新建 INC 文件：

- 调试时间超过 **15 分钟**
- 试错超过 **2 次**
- 发现"设计时没考虑到"的情况
- 用户指出的问题（尤其是设计遗漏）
- 依赖/环境导致的非预期行为

> 不必是"大事故"。**任何让你停下来想了一会儿的问题，都值得记。**

---

## 模板

```markdown
# INC-0001: <一句话现象>

- 日期：<YYYY-MM-DD>
- 阶段：P2 / P4 / P5
- 严重度：高 / 中 / 低
- 状态：已解决 / 已规避 / 已知限制

---

## 1. 现象

<怎么发现的？报错原文、异常表现、用户反馈。粘贴原文，不要转述。>

```
<报错原文>
```

---

## 2. 复现

<最小复现步骤。能写成命令或点击路径最好。>

1. <...>
2. <...>
3. 结果：<...>

---

## 3. 根因

<真正的原因，不是表面现象。>

> 用 5 Whys 挖到机制层：
> - 为什么报错？→ A
> - 为什么会有 A？→ B
> - 为什么会有 B？→ C（到这一层通常才是真因）

**真因：** <...>

---

## 4. 解决

<改了什么。具体到文件与行。>

- 文件：`src/xxx.py:42`
- 改动：<...>

---

## 5. 预防（必填）

> **没有这一节，incident 不算闭环。**
> 这一节决定下次会不会再犯。

至少选一项并写具体：

- [ ] 加了测试：`tests/test_xxx.py::test_yyy`
- [ ] 加了检查：`scripts/gate.sh` 第 N 条 / lint 规则
- [ ] 改了规范：`.ai/0X-Pn.md` 第 N 节增加 <...>
- [ ] 改了设计：`docs/design/DESIGN.md` 增加 <...>
- [ ] 加了监控/断言：<...>

**具体内容：** <...>

---

## 6. 关联

- 相关 ADR：ADR-0002
- 相关设计：`docs/design/DESIGN.md` 第 3 节
- 相关代码：`src/xxx.py`
- 是否同类问题再次发生：是 / 否（若是，说明为什么之前预防失效）
```

---

## 编号规则

- 全局递增：`INC-0001`、`INC-0002`……
- 不复用、不删除。作废的标注「已作废」并说明原因。

---

## 在 P5 校验中的用法（关键）

P5 的第三轮 review 是「历史缺陷回灌」：

1. 打开 `docs/incidents/`，列出全部 INC
2. 逐条问：「本次改动会不会让它再发生？」
3. 逐条在 REVIEW 记录中打勾确认

这让经验真正累积 —— 每次 review 都是一次全历史回归。
