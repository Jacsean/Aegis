# 参考 · P3 设计评审清单（12 项）

> 按需加载。P3 阶段逐条执行，结果写入 `docs/design/REVIEW-DESIGN.md`。
> **设计做完先自查，再进实现。在纸上改，成本是改代码的 1/10。**

---

## 清单

### A. 需求符合性

**1. 是否覆盖 PRD 全部验收标准？**
逐条列出 PRD 验收标准 → 对应设计中的哪个部分。
有遗漏 → 设计不完整。

**2. 是否实现了 PRD 的「非目标」？**
检查设计里有没有悄悄做了"说好不做"的东西。范围蔓延往往在设计中发生。

### B. 架构合理性

**3. 模块边界是否清晰，有无循环依赖？**
画依赖图，检查是否单向。

**4. 数据流是否单向、可追踪？**
数据从入口到存储到展示，能否一眼看清路径。

**5. 状态管理是否有单一真相源？**
同一个数据是否在多处各存一份？（重复状态 = 不一致的根源）

### C. 健壮性

**6. 错误路径是否设计（不只是 happy path）？**
网络失败、空数据、权限不足、并发冲突 —— 是否都有明确处理？

**7. 是否引入不必要依赖？**（奥卡姆剃刀）
每个依赖问一句：不用它行不行？

### D. 经验回灌

**8. 是否与历史事故同类？**
打开 `docs/incidents/`，逐条问"这个设计会不会让它再发生"。

### E. 前端专项（前端项目必做）

**9. 交互反馈是否明确？**
loading / empty / error / success 四态是否都有视觉反馈？
操作是否有即时响应（哪怕只是按钮变灰）？

**10. 响应式与无障碍是否考虑？**
小屏怎么显示？键盘能否操作？对比度够不够？

### F. 质量属性

**11. 是否有性能隐患？**
N+1 查询、全量重渲染、大列表无虚拟化、同步阻塞 IO。

**12. 是否可测试？**
依赖是否可注入？是否有难以测试的全局状态或隐藏副作用？

---

## 使用方式

在 `docs/design/REVIEW-DESIGN.md` 中逐条记录：

```markdown
## 第 1 项：是否覆盖 PRD 全部验收标准？

- [x] PRD-1 用户可登录 → DESIGN 3.2 认证模块
- [x] PRD-2 密码可找回 → DESIGN 3.3 找回流程
- [ ] PRD-3 支持多设备 → **设计缺失** → 已补 DESIGN 3.5

结论：发现问题 1 项，已修正。
```

---

## 判定标准

- **12 项全绿** → 可进 P4
- **有 1-2 项小问题** → 现场修正后可进 P4，记录在 REVIEW
- **有 3 项以上或涉及架构** → 退回 P2 重新设计

> **警惕沉没成本**：设计已写了很多不是保留的理由。
> 发现方向错了，推倒重来的总成本通常低于带着缺陷实现。
