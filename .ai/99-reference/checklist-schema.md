# 参考 · Checklist 写作规范（选项式）

> 状态：定稿（状态行规则见 00-core 3.2，

> 按需加载。S2 对齐每轮讨论前写 checklist 时使用。
> **核心：agent 提供选项，用户只做选择。用户的成本从"表达"降为"识别"。**

---

## 一、为什么用选项式

开放式提问（"你希望怎么处理？"）的问题：
- 用户要自己组织语言 → 表达过程本身就是歧义的来源
- 用户不知道 agent 有哪些可能的理解 → 无法针对性纠正
- 回答质量取决于用户的表达能力，而非理解是否到位

选项式把用户的工作从**创造**降为**识别**：
看到四个选项，一眼就知道哪个对，或者"都不是，是第五种"。

---

## 二、两个必须遵守的原则

### 原则一：先给描述或标准，用户据此回复

每个关键点**必须先给出上下文或判断标准**，再让用户选。

没有上下文的选项是无根之木——用户不知道这话从哪来、也不知道凭什么选。

> ❌ 直接问：你想要哪种数据处理方式？
> ✅ 先说标准：如果数据量大（超过 1 万条），一次全读进内存会卡。
> 　　　　　　 如果数据量小（几百条），全读最简单。
> 　　　　　　 你的数据大概多少？

### 原则二：agent 列出可能存在的理解偏差，用户确定正确方向

每个关键点**必须枚举"我可能理解错的方向"**，由用户指认。

这是最有价值的一步：**它把"猜错"提前暴露在讨论阶段，而不是在交付时。**

## 三、单条 checklist 的结构（五元素，按需取用）

```markdown
## <编号>. <问题本身，用用户的话问，不用术语>

**从哪来：** <用户说的哪句话 / 上下文里哪个缺口，让这个问题必须存在>

**不问会怎样：** <不决定的话会错在哪，错在哪一步才暴露>

**你该怎么判断：** <回想什么事 / 对照什么场景 / 看什么数字——给可操作的动作>

> 依据：[检索]/[推荐]/[无参照] ...

**我可能理解错的地方：**
  A. <一种理解> → 后果：<选了这个会怎样>
  B. <另一种理解> → 后果：<...>
  C. <第三种理解> → 后果：<...>
  D. 其他：_______________

**我可能根本没问对：** <如果这个问题的方向就错了，请直接说>

**我的倾向：** <A/B/C，一句话理由>
```

### 五个元素：不强制全有，但必须够用

| 元素 | 作用 | 什么时候必须有 |
|---|---|---|
| ① 从哪来 | 建立上下文，让用户能代入 | **几乎总是**（除非是紧随上一条的追问）|
| ② 不问会怎样 | 说明利害，让用户知道该认真还是随便答 | 有取舍的问题 |
| ③ 你该怎么判断 | 给可操作的判断动作 | 用户可能缺专业背景时 |
| ④ 选项 + 后果 | 让用户能挑 | **总是**（含「其他」）|
| ⑤ 我可能没问对 | 留出「问题本身错了」的口子 | 问题方向没把握时 |
| ⑥ 依据行（第七维） | 说明信息从哪来 | **总是**（无参照也要写 `[无参照]`）|

### 规则：允许省略，不许悄悄省略

**判断标准不是「问题大小」，而是「用户判断错的代价」。**

| 问题类型 | 至少要给 |
|---|---|
| 紧随上一问的追问 | ④ + ⑥ |
| 简单事实确认（"是不是这个意思"） | ① + ④ + ⑥ |
| 有取舍的选择（"先做 A 还是 B"） | ① + ② + ④ + ⑥ |
| 用户可能有不同理解 | ① + ② + ③ + ④ + ⑤ + ⑥ |
| 涉及技术方案、用户无专业背景 | 六项全给 |

**省略某一段时，必须写明理由**，例如：

> （本条不问「不问会怎样」，因为这只是个名词确认，选错当场就能看出来。）

**不许静默省略。** 悄悄省掉 = 用户不知道自己少了判断信息。

### 为什么要加「从哪来」和「你该怎么判断」

这两条是这套机制从「问得清」升级到「可判断」的关键。

**只有判断依据 + 选项时**，用户面对的是：
> 「A. 后写覆盖 B. 逐段落合 C. CRDT」

用户的问题：这三个词我不认识，不知道跟我有什么关系。

**加了「从哪来」和「你该怎么判断」后**：
> **从哪来**：你说「手机和电脑要同步」，但同步有两种意思——先后同步，和两边同时改。
> **你该怎么判断**：回想一下，你有没有过「手机上改一半、电脑上也开着同一条」的经历？

用户能**直接对照自己的经历回答**，不需要先懂那三个词。

### 常见错误：把「表达清晰」当成「可判断」

写得清楚 ≠ 能回答。检查方法：

> 把这条问题读给一个完全不懂这行的人听，看他能不能回答。
> 如果他反问「这跟我有什么关系」，说明缺 ① 或 ②。
> 如果他说「我不知道怎么选」，说明缺 ③。

## 四、选项设计规则

### 规则 1：必须含「其他 _______」

**任何一条都不能省。** 省了就变成"逼迫选择"，比开放式更糟。

写法固定为 `其他：_______________`

### 规则 2：实选项 3-4 个

| 选项数 | 问题 |
|---|---|
| 1 个 | 不是选择题，是通知 |
| 2 个 | 两个都不完美时被迫选错 |
| 3-4 个 | ✅ 覆盖主要方向 |
| 5 个以上 | 认知负担反超开放式提问 |

### 规则 3：选项必须互斥、不重叠

如果 B 包含了 C 的一部分，用户就没法选。

> ❌ B. 支持导出 Excel　C. 支持导出表格
> ✅ B. 导出成 Excel 文件　C. 直接在页面上复制粘贴

### 规则 4：选项是"理解方向"，不是"实现方案"

| ❌ 实现方案型 | ✅ 理解方向型 |
|---|---|
| A. 用 React　B. 用 Vue　C. 用原生 | A. 你希望它像手机 App 一样切换流畅　B. 你只要能看就行，用不着花哨 |
| A. 加缓存　B. 不加缓存 | A. 数据不常变，慢一点没关系　B. 数据常变，必须每次最新 |

**原因**：实现方案是你的决定权（见 `90-preferences.md`），agent 只在理解层面列选项。

### 规则 5：每个选项要写"后果"

让用户知道选了这个会怎样，否则无法判断。

### 规则 6：至少一条问"为什么"、一条问"什么算失败"、一条问"什么情况例外"

全是要不要支持 X 的 checklist，等于没讨论。

## 五、完整示例

```markdown
- [ ] 2. 数据多久变一次？

      **从哪来：** 你说了要做「每周汇总」，那数据本身多久变一次，决定了能不能提前算好。

      **你该怎么判断：** 想一下最近的实际情况：这条数据是一直在动，还是每周才更新一批。

      **不问会怎样：** 我会按「每次重新取」的保守做法写，结果每周汇总要跑十几分钟。

      **我可能理解错的地方：**
        A. 每天甚至更频繁地变 → 后果：不能存，每次都要重新取，会慢一些
        B. 一周到一个月变一次 → 后果：可以每天更新一次缓存，够用
        C. 基本不变，写完就不动了 → 后果：可以全部提前算好，最快
        D. 其他：_______________

      **我的倾向：** B。你提到是「每周汇总」，所以应该是按周更新。
```

## 六、更高效的形式（可选，但须满足两原则）

如果某个点用选项表达反而累赘，可以用以下形式，但**仍须满足"先给判据"和"列出偏差"**：

**形式一：是非 + 偏差说明**
```
- [ ] 3. 未登录的人能看到首页内容吗？

      **从哪来：** 你说了「先让人试用再决定要不要注册」，这句话本身已经把答案说了一半，我确认一下是不是这个意思。

      **不问会怎样：** 我会默认全部要登录，那样「先试用」这条就不成立了。

      **我可能理解错的地方：**
        A. 能看全部（只是不能操作）→ 后果：新用户容易上手
        B. 只能看一部分（比如标题，看不到正文）→ 后果：有吸引力又不泄露
        C. 完全看不到，必须先登录 → 后果：用户会流失
        D. 其他：_______________
```

**形式二：给具体场景让用户判断**
```
- [ ] 4. 这样处理你满意吗？

      场景：你在手机上点「导出」，等了 3 秒才出来。
      **从哪来：** 你说「导出要能忍」，但没说多久算忍得了。
      **为什么问：** 超过 3 秒一般会让人以为卡住了。

      A. 能接受，3 秒可以 → 后果：不做优化
      B. 太快了，希望 1 秒内 → 后果：要加进度提示和分片处理
      C. 无所谓，反正用得少 → 后果：暂不优化
      D. 其他：_______________
```

## 七、外部参照的四级标注（第七维）

> 每个关键点在选项之前，写「依据行」。
> **没有依据也要写 `[无参照]`，不许留空**——留空等于假装这个问题不需要依据。

### 四级标记

| 级别 | 含义 | 写法示例 |
|---|---|---|
| `[检索]` | 联网检索到的具体来源 | `[检索] 少数派 2025-03 八款笔记应用横评 —— 7 款默认本地存储` |
| `[推荐]` | 无出处的建议 / 倾向 | `[推荐] 单人使用倾向本地优先（无出处，基于复杂度判断）` |
| `[无参照]` | 既无事实也无倾向 | `[无参照] 未找到可参考的公开资料，以下选项为推断` |
| `[未覆盖]` | 知道有但没列为选项 | 不写进依据行，写进清单末尾「未覆盖方向」一节 |

### 降级链（不许跳级）

```
[检索]  有出处的同行经验
   ↓ 查不到
[推荐]  无出处的推荐 / 倾向
   ↓ 连倾向都没有
[无参照] 明说没有，用户自由发挥
```

**允许同一关键点混用**：一部分有据（`[检索]`）、一部分是倾向（`[推荐]`）。
这正是用户需要知道的——哪部分是硬的，哪部分是软的。

### 无联网能力时（顺序不可调换）

1. **先告知**：「我这边没有联网，拿不到专业文献。」
2. **再问**：「要不要我用训练数据里的印象给一些参照？（无出处，可能过时）还是这次不需要同行经验？」
3. 同意 → 用 `[推荐]`，**禁止**伪装 `[检索]`
4. 不要 → 全用 `[无参照]`

### 绝对禁止的三种写法

| 写法 | 为什么禁 |
|---|---|
| 没查却说「我查到了」 | 欺骗，不是失误 |
| 给 3 个选项不说「还有别的方向没列」 | 用户会在两个月后才发现漏了 |
| 「业界普遍 / 通常认为 / 大家都」但不给具体出处 | 读起来像事实，其实是语气 |

### 未覆盖方向（清单末尾必备一节）

```markdown
## 未覆盖方向

| 方向 | 为什么没列为选项 | 要采用还需了解什么 |
|---|---|---|
| CRDT 本地优先 + P2P 同步 | 复杂度高，不适合 1 人 2 周项目 | 冲突合并算法、移动端后台同步限制 |
```

**三列都要写**。第三列是给用户判断「要不要回头去补」用的。

想不出漏了什么，就写一句实话：

> 本次调研未发现其他主流方向。

不确定就写：

> 我不确定是否还有别的方向。

**这一节不能是空的**——空等于声称「选项已穷尽」，而那几乎总是假的。

## 八、技术词黑名单（gate.sh 会检查）

以下词出现在 checklist 中且**未解释**，视为不合格：

```
API    接口    数据库    schema   token
鉴权   认证    授权      JWT      session
并发   事务    缓存      中间件   队列
微服务 容器    部署      负载均衡  CDN
状态管理 Redux  ORM      MVC      序列化
```

允许出现的情况：
1. 用户本人先用了这个词
2. 用户明确要求技术描述
3. 词后紧跟「（就是 <大白话解释>）」

## 九、自检清单

写完每一条后逐项过：

- [ ] 有「从哪来」或「不问会怎样」（至少其一）
- [ ] 有 3-4 个实选项
- [ ] **有「其他：___」**
- [ ] 选项之间互斥不重叠
- [ ] 选项是理解方向，不是实现方案
- [ ] 每个选项写了后果
- [ ] 有「我的倾向」
- [ ] 不含未解释的技术词
- [ ] 有「依据」行（无参照也要写 `[无参照]`，不许留空）
- [ ] 依据行不出现「业界普遍/通常认为」这类无出处断言

整份 checklist 再过一遍：

- [ ] 每条都能被非技术人员看懂
- [ ] 至少一条在问"为什么"
- [ ] 至少一条在问"什么算失败"
- [ ] 至少一条在问"什么情况例外"
- [ ] 条目数 5-8 条（不要一次问 20 条）
- [ ] 末尾有「未覆盖方向」一节，且三列都有内容
