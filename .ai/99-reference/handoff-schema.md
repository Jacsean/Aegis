# 参考 · HANDOFF Schema（开发事件记录）

> 状态：定稿（状态行规则见 00-core 3.2，

> 按需加载。**每个任务结束时必写。**
> 目的：让「不在场的人或 agent」能读懂这件事的来龙去脉，并能据此继续干活。
> **本文件里的词，含义以 `docs/reference/concepts.md` 为准**（尤其：地点、分支（血缘）、记录、索引、事件、来龙去脉）。


---

## 零、为什么是这一套要素

**问题不是「写多少行」，是「要素缺不缺」。**
行数取决于内容多少，要素才决定信息是否完整。

本规范的四类来源：

| 来源 | 提供了什么 |
|---|---|
| 用户的 5W2H / 记叙文六要素思路 | **要素完整性判据**——不靠感觉定详略，靠规则定要有哪些 |
| 事故交接模板（行业固定项）| 补上「试过什么、成没成」——**这是最省下一轮时间的一栏** |
| 事故复盘设计原则 | 「事实 / 推断 / 未知」必须分开标；不许单根因收口 |
| 决策日志 vs 决策记录（两层结构）| 索引一行 + 记录一节；**引用不复制** |

## 一、两层结构（不要再纠结「流水账还是树」）

| 层 | 路径 | 形态 | 干什么用 |
|---|---|---|---|
| **索引层** | `docs/internal/handoff.md` | **每条一行**，按时间倒序（最新在上）| 扫、grep、找线索 |
| **记录层** | `docs/internal/handoff/H-<编号>-<短名>.md` | 完整要素 + 上下游链接 | 读懂一件事的来龙去脉 |

**为什么是两层，不是纯流水账也不是纯树：**

- 纯流水账：单条太浅，跨条太散。查「导出为什么没做成」要读中间夹着的十几条不相干记录。
- 纯目录树：一件事可能横跨两个任务，目录只能放一个位置。
- **两层 + 血缘链接**：索引快，记录全，上下游能走。

> 依据：[检索] Decision Log vs Decision Record ——「log 是目录，record 是章节，两层不是替代品」
> 依据：[检索] Append-Only Decision Ledger ——「血缘感知：每条引用父决策与子决策，图就是架构」

### 索引层格式（一行一条，不许换行）

```markdown
| 编号 | 时间 | 谁 | 事件 | 结果 | 链接 |
|---|---|---|---|---|---|
|  | 2026-10-05 | agent | 暂停导出功能 | 待用户确认 | [](handoff/-导出功能暂停.md) |
```

**表头不许删。** 门禁按列检查。

## 二、记录层七要素（必填，缺一不可）

| # | 要素 | 写什么 | 为什么不能省 |
|---|---|---|---|
| 1 | **When 时间** | 日期，精确到天 | 判断这条还准不准；先后顺序决定因果 |
| 2 | **Who 谁** | 人还是 agent；哪个会话 | 出错时知道问谁；区分「用户定的」和「agent 猜的」 |
| 3 | **What 事件** | 做了什么，一句话，动词开头 | 这是记录的主体 |
| 4 | **Why 为什么这样处理** | 决定的理由 | 只写「做了什么」等于没写；三个月后必问「当时为什么」 |
| 5 | **How 怎么处理的** | 具体做法 / 改了哪些文件 | 让接手的人能照着复现或修改 |
| 6 | **What was tried 试过什么、成没成** | 逐条列，标明成功/失败 | **最省时间的一栏**；不写，下一个人会重试一遍 |
| 7 | **Next 下一步 / 等谁确认** | 具体动作，或「等谁回什么」 | 没有这一栏，读的人知道发生了什么但不知道该怎么办 |

### 可省略的两项（省了必须写理由）+ 新词（S7 必填）

| 要素 | 什么时候可以省 | 省略时怎么写 |
|---|---|---|
| **Where 地点** | 只有确实无地点可言时才省（如纯内部重构）| 「地点：本机，无外部场所」 |
| **How much 影响面** | 单人项目，无量化意义 | 「影响面不量化：单人项目」 |

> 依据：[检索] 5W2H 使用注意 ——「Why 可未知，不许为填格子编动机」
> 依据：[检索] 事故交接固定项 ——「现状 / 试过什么 / 成没成 / 当前怀疑 / 下一步」

**新词（第 8 项，S7 固化时必填）**：本任务产生的新词及词条状态（升 `已定` / `暂定` 待验收）；无新词写「无」。依据铁律七。平时任务可省。

## 三、三态标注：事实 / 推断 / 未知

**每条陈述后面可选标一个状态。不标视为「事实」。**

| 标记 | 含义 | 例子 |
|---|---|---|
| （无标记）| 事实：亲眼看到、命令输出、文件内容 | 「跑 `pytest` 得到 3 failed」 |
| `〔推断〕` | 我的判断，可能有错 | 「〔推断〕失败原因大概是超时」 |
| `〔未知〕` | 明确不知道 | 「〔未知〕用户是否接受 CSV 丢格式」 |

**为什么必须标：** agent 交接时最危险的不是没写，是**把猜的写成了就是这样的**，下一个 agent 当真了。

> 依据：[检索] 事故复盘设计原则 ——「一个不可变记录里的时间戳是证据；『缓存可能过载了』在被证实前是假设。要标出区别。」

**禁止写法：**

| 写法 | 为什么禁 |
|---|---|
| 「应该是 X 的问题」但不标〔推断〕 | 读的人会当结论 |
| 只写「未解决」不写〔未知〕的具体内容 | 等于没写 |

## 四、上下游链接（一条「来龙去脉」）

记录开头必须有两个字段：

```markdown
- **上接**：（改用 CSV 而非 Excel）／无
- **下接**：（恢复开发）／暂无
```

- **上接**：这件事是从哪条记录演化来的。**允许多个，逗号分隔**（一件事常常同时接着两条线）
- **下接**：这条之后又发生了什么。**允许多个，逗号分隔**
- 没有就写「无」/「暂无」，**不许留空**

多值的写法：

```markdown
- **上接**：（定下两维度）、（暂停决定；本条在暂停期内产生）
```

**沿上接往上走到起因、沿下接往下走到现状，走通的那条链就是这件事的「来龙去脉」。**
不用目录树，因为一件事常常被两条线引用（导出功能 10-03 开始，10-06 因权限问题重开）。

## 五、过期不删，划掉并指向新的

**这是最容易出事的一条。**

```markdown
| ~~~~ | 2026-09-20 | agent | 用 SQLite 存日志 | **已废止** | [](handoff/-...md) →  |
```

记录文件本身**不删、不改结论**，只在开头加一行：

```markdown
> ⚠️ **本条已废止（2026-10-12）**：仅限限流计数器场景改用 Redis，。
```

**为什么：** 下一个 agent 读到旧结论，会把新工作又改回去。这是真实发生过的故障模式。

> 依据：[检索] 「2024 年写『不用 Redis』，2026 年加了 Redis，新人读到旧条目把新工作改回去了。做法：永远不删，划掉并向前指。」

## 六、写多细：靠要素，不靠行数

**不要把「写几行」当标准。** 同一套要素，简单的事两行写完，复杂的事写十行，都合规。

判断标准只有两个：

1. **七个要素齐不齐**
2. **拿掉任何一条，读的人会不会问「然后呢」或「为什么」**

会问 → 要素没写透，补充；不会问 → 已经够了，不用凑。

## 七、完整样例

```markdown
#  导出功能暂停

- **时间**：2026-10-05
- **谁**：agent（会话 12）
- **事件**：暂停导出功能开发，等用户确认
- **为什么现在停**：CSV 导出会丢格式（表格线、颜色），而用户原话是「导出的表格要能直接发给客户」
- **怎么处理的**：已实现 CSV 导出（`src/export/csv.py`），Excel 导出未实现
- **试过什么**
  - ❌ Excel 方案：手机上打不开 → 放弃
  - ❌ CSV + 样式说明文字：用户要的是能直接发，说明文字反而多余 → 放弃
  - ✅ CSV 基础导出：能跑通，但丢格式
- **下一步 / 等谁**：〔未知〕用户是否接受「CSV 丢格式」；若不接受，需要评估 xlsx 库在移动端的兼容性
- **上接**：（改用 CSV 而非 Excel）
- **下接**：暂无
- **地点**：`src/export/csv.py:42`（行号）；commit `a1b2c3d` 记在「怎么处理的」里
```

**读一遍检验**：任何 agent 读完，都知道「做到了哪一步、为什么停、试过什么别再试、下一步等什么」。

## 八、什么时候写

| 时机 | 必须写吗 |
|---|---|
| 任务结束（合并进 main 前）| **必须** |
| 会话结束但任务没完 | **必须**（写「进行中」状态）|
| 中途判断改判（场景决断变了）| **必须**（单独一条，说明为什么改）|
| 一次只读查询、没有改动 | 不必 |

## 九、常见失败

| 失败 | 后果 | 纠正 |
|---|---|---|
| 只写「完成了 X」 | 三个月后不知道 X 是什么、为什么这么做 | 补 Why |
| 「试过什么」写「没试什么特别的」 | 等于没写，下一个人照样重试 | 写「本任务未走过弯路」，不许空 |
| 把推断写成结论 | 下个 agent 当真，基于错的前提继续做 | 标〔推断〕 |
| 索引层写多行 | 破坏了「一行一扫」的设计 | 详情进记录层，索引只留一行 |
| 废止的记录直接删掉 | 历史断裂，不知道现在为什么是这样 | 划掉 + 指向新条目 |
| 行数对齐当质量标准 | 简单的事硬凑，复杂的事写不下 | 按七要素判断，不看行数 |
