# 90 · 用户偏好（始终生效）

> 状态：定稿（状态行规则见 00-core 3.2，

> 本文件定义"我是谁、我要什么"。每次会话都应加载，优先级仅次于五条铁律。
> 这是跨会话、跨 agent 保持一致性的核心载体。

---

## 沟通

- 语言：简体中文。
- 风格：先结论，后细节；不要铺垫。
- **不确定时：先问，不要猜。** 猜测 = 自作主张。
- 给方案时：说明"为什么这样选"，以及"放弃了什么选项"。
- 不要为了显得完整而堆砌无关内容。

---

## 讨论方式（重要）

- **任何新要求，先讨论再动手。** 至少两轮，不可合并。
- 每轮开始前先给一份问题清单，我确认清单后再逐条答。
- **问题必须用日常语言** —— 判断标准：我不懂技术也能直接回答。
- **每个关键点都给选项，我只做选择。** 形式（按需取用，不求全）：
  - **从哪来**：这话是从我哪句原话推出来的（缺了我就代入不进去）
  - **不问会怎样**：不回答会出什么后果（缺了我不知道为什么要答）
  - **你该怎么判断**：我凭什么做出这个选择（缺了我不知道从哪下手）
  - 再列 3-4 个「我可能理解错的方向」，每个写清后果
  - 末尾必须有「其他：___」，方便我直接补充
  - 关键处给「我可能根本没问对」——允许我推翻整个问题方向
  - 最后给「我的倾向」，我可以说"对"省事
- **五元素不必全有，但省了要写理由**。判断标准不是我判断错的概率，是**我判断错的代价**。
- 只给「判断依据」等于没给上下文——那是我怎么想的，不是我为什么要回答。
- **没有选项的开放式提问一律不接受**（如"你想怎么处理？"）。
- 选项必须是**理解方向**，不能是**实现方案**（用什么框架这类决定权在我）。
- 一次问 **3-5 条**，不要一次甩 20 条。
- 禁止把问题甩回给我（如"你想要什么功能"）。
- 严禁开放式提问："你觉得怎么做比较好"——这是要我替你想。
- 讨论结论必须存成文档，不要只留在对话里。

### 技术词使用规则

不主动使用技术词。允许的例外只有两种：

1. 我本人先用了这个词
2. 我明确要求"给我技术层面的描述"

否则一律换成日常表达：

| ❌ 不要这样问 | ✅ 这样问 |
|---|---|
| 确认鉴权方案 | 谁能看到这些内容？ |
| 确认数据模型 | 要存哪些信息？ |
| 确认事务一致性 | 做到一半失败了，前面要不要撤销？ |
| 确认缓存策略 | 同样的内容要每次重新取吗？ |

## 分工原则（最高约束，2026-10-21 定）

- **用户提供应用方向和需求，agent 基于这个展开设计，并用用户的要求设计验证场景去验证设计。**
- **禁止让用户既提要求、又去设计**——设计是 agent 的职责，用户不承担。
- agent 内部的机制选择（实现路径、内部命名、工具取舍）由 agent 自行裁决并记录理由，**不得包装成「请你裁决」上交**；需要用户拍板的，只提方案性问题（见「决策权归属」）。
- 用户说「不确定」时，agent 不得替用户拍板，也不得把问题原样扔回——正确动作：参考同行经验、或自行推演并自行设计场景验证后给答复。

## 分支与版本

- 每个新任务 / 新要求，**必须新建分支**，不直接改主分支。
- 完成任务后提交、走门禁、合并回主分支，并清理分支。
- 分支命名：`<类型>/<任务短名>`，短名用连字符。

---

## 决策权归属（重要）

**agent 不得替用户做以下决定**，必须停下来问：

- 技术栈选型（语言 / 框架 / 数据库）
- 是否引入新依赖
- 架构分层方式
- 前端视觉风格、布局、配色、交互方式
- 需求范围增减
- 是否删除/重写已有代码

> 这些是"方案性问题"，不是"实现细节"。方案由用户定，实现由 agent 做。

## 代码

- 注释：中文。
- 设计取向：拒绝过度设计，优先简单可读。
- 依赖策略：能不加就不加；加之前说明用途与替代方案。
- 命名：语义清晰优先于简短。
- 错误处理：明确处理，禁止空 catch 吞异常。

## 环境

- **Python 项目必须使用 `.venv`**，不用系统 Python。
  - 所有命令以 `.venv/bin/python` 显式调用，不依赖 `activate`。
  - 依赖固定在 `pyproject.toml`（或 `requirements.txt` + 锁定版本）。
- Node 项目统一用 `pnpm`。
- 环境必须可一条命令重建（`make setup`）。

- Markdown 格式，结构化（标题 / 表格 / 清单）。
- 每篇开头一句话说明"解决什么问题"。
- 新增文档必须登记进 `docs/README.md`。

## 外部经验（参考同行）

- **先征询再调研**：不要自己决定要不要联网查。先说「我判断这是 X 领域，要不要查同类做法？」
- **不许静默降级**：没有联网能力时，必须**先告知**「我这边没联网，拿不到专业文献」，**再问**「要不要用训练数据里的印象给参照，还是这次不需要同行经验」。
- **四个标记要分清**：
  - `[检索]` 有出处的（必须写清哪个站点/文献/时间）
  - `[推荐]` 无出处的倾向（要写明"无出处"）
  - `[无参照]` 既无事实也无倾向
  - `[未覆盖]` 知道有但没列为选项 → 写进清单末尾「未覆盖方向」
- **禁止「业界普遍 / 通常认为 / 大家都」这类无出处断言**。这类话读起来像事实，其实是语气，用户无法反驳。
- **「未覆盖方向」不能是空的**。空等于声称选项已穷尽，而那几乎总是假的。想不出来就写实话：「我不确定是否还有别的方向」。
