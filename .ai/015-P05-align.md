# 01.5 · P0.5 意图校准（Align）

> 状态：定稿（现行编号 P05）· 八阶段定稿中为 S2 对齐（状态行规则见 00-core 3.2，H-0021）

> 目的：在写任何需求文档、任何方案之前，**先确认我到底想要什么**。
> 本阶段产出 `docs/align/ALIGN-<任务名>.md`，作为 P1 写 PRD 的**唯一依据**。

---

## 为什么单独一个阶段

因为「讨论」不是 P1 的一部分。
P1 是"把确认过的意图写成 PRD"；而 P0.5 是"**确认意图本身**"。

把讨论塞进 P1 会导致：agent 一边讨论一边写 PRD，写着写着就变成"我理解的版本"。

**顺序不能乱：先校准意图，再写需求。**

---

## 核心规则（五条硬规则）

### 规则零：先调研，再列清单

**顺序：判定领域 → 征询 → 调研 → 生成清单。**
不许先问一堆问题再去调研（方向已偏，白花 token），也不许不征询就烧 token 搜。
细则见下文「第零步：调研前置」。

### 规则一：至少两轮讨论，且不能合并

| 轮次 | 名称 | 目的 | 能否跳过 |
|---|---|---|---|
| R1 | 复述轮 | agent 用自己的话复述，你纠正 | ❌ 不可跳 |
| R2 | 深层轮 | 逐条挖"为什么/如果/什么算失败" | ❌ 不可跳 |
| R3 | 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件触发 |

**禁止：**
- 一轮问完所有问题，然后说"两轮完成了"
- R1 和 R2 合并成一次对话
- 用"你还有补充吗"代替正常轮次

### 规则二：每轮开始前必须先建 checklist

**顺序是：建 checklist → 你确认 checklist → 逐条讨论。**

不能边讨论边想问题，也不能讨论完了再补 checklist。

checklist 存为 `docs/align/CHECKLIST-<任务名>-R<n>.md`。

### 规则三：选项式，不是开放式

**每个关键点都由 agent 提供描述与选项，你只做选择。**

单条结构（五元素，**按需取用**，详见下文「五元素」一节）：

```markdown
## <编号>. <关键点，日常语言>

**从哪来：** <这句话是从用户哪句原话推出来的>
**不问会怎样：** <如果不问，会出什么后果>
**你该怎么判断：** <用户凭什么做出选择>
> 依据：[检索]/[推荐]/[无参照] <出处或无出处理由>

**选项：**
      A. <一种理解> → 后果：<...>
      B. <另一种理解> → 后果：<...>
      C. <第三种理解> → 后果：<...>
      D. 其他：_______________   ← 必须有

**我可能根本没问对：** <允许用户推翻整个问题方向>   ← 低频，但关键处必须有
**我的倾向：** <A/B/C>
```

两条原则：

1. **先给描述或标准** —— 用户据此回复，而不是凭空想
2. **列出可能的理解偏差** —— 用户指认正确方向，把"猜错"提前暴露

**必须遵守：**
- 每条 **必须含「其他：___」**（省了就变成逼迫选择）
- 实选项 **3-4 个**（2 个易被迫选错，5 个以上认知负担反超开放式）
- 选项 **互斥不重叠**
- 选项是**理解方向**，不是**实现方案**（实现是你的决定权）
- 每个选项写清**后果**
- **每条至少要有「从哪来」或「不问会怎样」其中之一**——一个都不给，用户就不知道自己为什么在被问这个

### 规则四：checklist 必须用小白语言

**判定标准：每一条都必须能让你在"不需要任何技术知识"的前提下做出选择。**

做不到就是不达标，必须重写。具体替换规则见下方。

## 小白语言规则（关键）

### 自检方法

写完一条 checklist，问自己三个问题：

1. 一个完全不懂编程的人能看懂这条吗？
2. 这条需要我先解释某个技术名词才能回答吗？
3. 我的答案会是"我不确定这什么意思"吗？

**任一答案为"是" → 重写这条。**

### 替换表

| ❌ 不要这样写 | ✅ 要这样写 |
|---|---|
| 确认鉴权方案 | 谁能看到这些内容？没登录的人能看到吗？ |
| 确认数据模型 / 表结构 | 要存哪些信息？每条信息大概长什么样？ |
| 确认状态管理方案 | 页面上这个数字变了，别的地方要不要跟着变？ |
| 确认 API 契约 | 这两部分之间怎么传话？传什么内容？ |
| 确认并发处理 | 两个人同时改同一个东西，会发生什么？ |
| 确认缓存策略 | 同样的内容，每次都要重新取吗，还是可以先存着？ |
| 确认错误码规范 | 出错的时候，要给用户看到什么提示？ |
| 确认技术栈 | （这类属于 P0，不在此阶段）|
| 是否支持响应式 | 在手机上看，样子要不要变？ |
| 确认路由方案 | 点不同链接，页面怎么切换？ |
| 确认事务一致性 | 如果做到一半失败了，前面的要不要撤销？ |
| 确认分页策略 | 东西很多的时候，是一次全显示还是分几页？ |

### 允许使用技术词的情况

只有两种：

1. **你自己先用了**这个词（说明你懂，可以跟上）
2. **你明确要求**"给我技术层面的描述"

否则一律用日常语言。技术词不是专业，是门槛。

## 三轮详细设计

### 第零步：调研前置（R1 之前，第七维「参考同行」）

**为什么在 R1 之前**：等问过一堆问题再去调研，方向已经跑偏了，白花 token。
先确认领域 → 再调研 → 调研结果作为写清单的依据。

#### 顺序（不可调换）

```
1. 判定领域     → 从上下文判断这属于什么问题域 / 行业
2. 征询         → 告诉用户「我判断这是 X 领域，要不要联网查同类做法？」
3. 调研         → 用户同意才做，不同意的见下面的降级链
4. 生成清单     → 调研结果进「依据」行与「未覆盖方向」
```

#### 第 1 步：判定领域

从用户的话里提炼，写成一句可反驳的判断：

> 「我理解这是一个**个人知识管理工具**（本地笔记 / 双向链接 / 单人多设备）。对吗？」

领域判定要足够具体到「能搜」。写「软件」搜不到东西，写「个人知识管理工具」能搜到。

#### 第 2 步：征询（不许跳过）

> 「这类工具同类产品不少，联网查一下主流做法通常能让方案更实。
> 要不要我查？（会多花一点时间）」

**用户可能回答三种**，对应三条路：

| 用户回答 | 怎么走 |
|---|---|
| 要 | 进第 3 步调研 |
| 不要 | 直接跳到「降级链」第二级 `[推荐]` |
| 不回答 / 反问 | 不要自己决定，再问一次，说明差别：「查了能给你有出处的参照，不查我只能凭印象」 |

#### 第 3 步：调研与标注

**能联网时**，检索结果按下面四级标注，写进清单每个关键点的「依据」行。

#### 四级标注（降级链）

| 级别 | 含义 | 怎么写 |
|---|---|---|
| `[检索]` | 来自联网检索的具体来源 | `[检索] <站点/文献> <时间> —— <一句话结论>` |
| `[推荐]` | 无出处的建议 / 倾向 | `[推荐] <倾向>（无出处，基于常识判断）` |
| `[无参照]` | 既无事实也无倾向 | `[无参照] 未找到可参考的公开资料，以下选项为推断` |
| `[未覆盖]` | 知道有但没列为选项 | 写进清单末尾「未覆盖方向」一节，不写进依据行 |

**降级顺序**：`[检索]` → `[推荐]` → `[无参照]`，逐层降，不许跳级。
有 `[检索]` 就不要同时写「我不知道」，但**允许**在同一关键点同时出现 `[检索]` 和 `[推荐]`（一部分有据、一部分是倾向）。

**没有联网能力时**（必须照这个顺序）：

1. **先告知**：「我这边没有联网，拿不到专业文献。」
2. **再问**：「要不要我用训练数据里的印象给你一些参照？（这类信息没有出处，可能过时）还是这次不需要同行经验？」
3. 用户同意 → 用 `[推荐]` 标注，**禁止**伪装成 `[检索]`
4. 用户不要 → 全用 `[无参照]`，明说「这次没有同行参照」

**绝对禁止的三种写法**：

| 写法 | 为什么禁 |
|---|---|
| 没查却说「我查到了」 | 这是欺骗，不是失误 |
| 给 3 个选项不说「还有别的方向没列」 | 用户会在两个月后才发现漏了 |
| 用「业界普遍 / 通常认为 / 大家都」但不给具体出处 | 读起来像事实，其实是语气，用户无法反驳 |

#### 第 4 步：写进清单的两处

**依据行** —— 每个关键点下面，选项之前：

```markdown
## 3. 数据存在哪里？

> 依据：[检索] 少数派 2025-03 八款笔记应用横评 —— 7 款默认本地存储
> 依据：[训练] 常见默认是 SQLite 单文件，无具体出处
> 依据：[推荐] 单人使用倾向本地优先（无出处，基于复杂度判断）

A. 存本地文件 ...
```

可以多行，一行一个标记。**没有依据也要写 `[无参照]`，不许留空**——留空等于假装这个问题不需要依据。

**未覆盖方向** —— 清单末尾，独立一节：

```markdown
## 未覆盖方向

| 方向 | 为什么没列为选项 | 要采用还需了解什么 |
|---|---|---|
| CRDT 本地优先 + P2P 同步 | 复杂度高，不适合 1 人 2 周项目 | 冲突合并算法、移动端后台同步限制 |
| 纯云端 + 服务端合并 | 需要后端，超出「本地工具」定位 | 服务端成本、离线可用性 |
```

三列都要写。第三列是给用户判断「**要不要回头去补**」用的，不能省。

**这一节不能是空的**。真的想不出漏了什么，就写一行：

> 本次调研未发现其他主流方向。（如果这是真的，说明这项技术已经很收敛；如果不确定，写「我不确定是否还有别的方向」。）

### R1 复述轮

**目的：让用户确认"我理解的他"和"真实的他"是否一致。**

**checklist 模板（选项式）：**

```markdown
# CHECKLIST R1 — <任务名>（复述轮）

> 每条都尽量给全「从哪来 / 不问会怎样 / 你该怎么判断 / 选项后果」。
> 请直接回编号 + 字母，或选「其他」补充。也可以只说「都对」或指出哪条不对。

## 1. 我这样理解你的要求，对吗？

**从哪来：** 你刚才说的是「<原话>」。我把它读成了下面这句。

**不问会怎样：** 如果我复述偏了，后面所有设计都会按偏的方向做，越做越远。

> 依据：[推荐] 先把理解写出来再确认，比边做边猜省时间（无出处）

**我这样理解：** <用一句大白话说出核心>

**我可能理解错的地方：**
      A. 完全对 → 后果：继续下一题
      B. 大方向对，但有一处偏了 → 后果：请指出哪一处，我改
      C. 偏得比较多 → 后果：请重新说一下重点，我重写
      D. 其他：_______________

**我可能根本没问对：** 如果我连"你想要什么"这个方向都搞错了，请直接说。

**我的倾向：** A

---

## 2. 你想解决的是这个麻烦吗？

**从哪来：** 你说「<原话>」时，我判断背后的麻烦是这个。但同样一句话，背后可能是不同的麻烦。

**不问会怎样：** 麻烦判断错了，方案会解决一个你其实不在意的问题。

> 依据：[推荐] 多数返工源于"需求没对齐"而非"技术不过关"（无出处）

**你该怎么判断：** 回想最近一次你因为这件事烦的时候，烦的到底是什么。

**我可能理解错的地方：**
      A. 是，主要是这个麻烦 → 后果：方案重点放在"解决它"
      B. 是，但还有一个更重要的麻烦 → 后果：请补充，我重排优先级
      C. 不是，真正的麻烦是别的 → 后果：请说明，我重新理解
      D. 其他：_______________

**我可能根本没问对：** 如果我问的这个"麻烦"你从来没觉得是麻烦，那说明我理解错方向了。

**我的倾向：** A

---

## 3. 做完之后，你希望看到什么？

**从哪来：** 这决定我按什么标准判断"做对了"。你不说，我就只能按我觉得对的标准。

**不问会怎样：** 做完你说"不是我要的"，但我不知道差在哪，因为我从来没有过标准。

> 依据：[无参照] 成功标准因人而异

**你该怎么判断：** 想象东西做出来了，你会拿它做的第一件事是什么。

**我可能理解错的地方：**
      A. <我能做一件之前做不到的事> → 后果：<...>
      B. <我不用再做某个麻烦步骤> → 后果：<...>
      C. <我能看到之前看不到的信息> → 后果：<...>
      D. 其他：_______________

**我的倾向：** <A/B/C>

---

## 4. 这次明确不要的是什么？

**从哪来：** 你只说了要什么，没说不要什么。而"顺手多做"是范围失控最常见的原因。

**不问会怎样：** 我会按"尽量完整"做，做完你发现多了很多不需要的东西，还得删。

> 依据：[推荐] 按最小范围先跑通（无出处，基于原型开发惯例）

**你该怎么判断：** 回想你以前用类似东西时，最烦的是哪部分。那部分就是"这次不要"。

**我可能理解错的地方：**
      A. <我猜你不想要的东西一> → 后果：如果是，我就不做
      B. <我猜你不想要的东西二> → 后果：...
      C. 没有特别不要的，看着办 → 后果：我会按最小范围做
      D. 其他：_______________

**我的倾向：** C

---

## 5. 我猜这些不在这次范围内，对吗？

**从哪来：** 我在你的话里听出了几个"可能相关但你没提"的东西。列出确认，避免我自己决定。

**不问会怎样：** 我自己判断"做不做"，就会做出你没打算要的东西，或者漏掉你其实想要的东西。

> 依据：[无参照] 范围边界由你的处境决定

**我可能理解错的地方：**
      A. 对，这些都不做 → 后果：我不碰
      B. 其中 <某一个> 要做 → 后果：请指出，我加进来
      C. 都不是，范围应该更大 → 后果：请说明，我重划
      D. 其他：_______________

**我的倾向：** A
```
**R1 通过标准：** 用户回"都对"，或指出偏差后 agent 修正，用户再确认。

**R1 常见失败：**
- 复述里塞满技术词（等于没复述）
- 只复述表面要求，没复述"为什么"
- 不敢写"我猜你不要的"，导致边界不清
- **选项全是"是/否"两个** → 被迫二选一，应给 3-4 个方向
- **只写"判断依据"，不写"从哪来"** → 用户不知道这话是从他哪句话推出来的，无法代入

### 五元素：按问题的判断难度递增

上面的模板给了全套五元素。实际写时**不要求每条都有全部**，但必须够用：

| 问题类型 | 至少给 | 例子 |
|---|---|---|
| 紧随上一问的追问 | 选项 + 依据 | 「那用哪种格式？」（上下文已经在了）|
| 简单名词确认 | 从哪来 + 选项 + 依据 | 「你说的'报告'是 PDF 还是网页？」|
| 有取舍的选择 | 从哪来 + 不问会怎样 + 选项后果 + 依据 | 「先做记录还是先做统计」|
| 用户可能有不同理解 | 加上「你该怎么判断」 | 「你说的'简单'是指几个按钮」|
| 涉及技术方案、用户无背景 | 六项全给（含「我可能没问对」） | 「同步冲突怎么处理」|

**省略某一段时，必须写明理由**：

> （本条不问「不问会怎样」，因为这只是个名词确认，选错当场就能看出来。）

**不许静默省略**——悄悄省掉等于让用户不知道自己少了什么判断信息。

### 判断标准：不是"问题大小"，是"用户判断错的代价"

判断错的代价越高，越要多给元素。

**自检方法**：把这条念给一个完全不懂这行的人听——

- 他反问「这跟我有什么关系」→ 缺「从哪来」或「不问会怎样」
- 他说「我不知道怎么选」→ 缺「你该怎么判断」
- 他说「你问的这件事我压根没想过」→ 缺「我可能没问对」，或者问题方向本身就错了

**最后一条最重要**。问题本身错了，比答案错了代价更大——因为用户会被迫在一个错误的框架里回答。

### R2 深层轮

**目的：挖出用户没说出口的意图。**

四类问题，每类挑 2-3 个：

**A. 为什么（动机）**
**B. 什么时候算成功 / 什么时候算失败**
**C. 边界与例外**
**D. 优先级**

**checklist 模板（选项式，五元素按需取用）：**

```markdown
# CHECKLIST R2 — <任务名>（深层轮）

> 每条尽量给全「从哪来 / 不问会怎样 / 你该怎么判断 / 选项后果」。
> 请直接回编号 + 字母，或选「其他」补充。也可以只说「都对」或指出哪条不对。

## A. 为什么

## A1. 这件事为什么现在要做？

**从哪来：** 你提到要「<原话>」，但没说为什么是现在。同一件事，急和不急做法完全不同。

**不问会怎样：** 我会按最省事的方式做，结果是能跑但经不起用；等你要用它扛事时才发现不够。

**你该怎么判断：** 想一下，如果三个月后才做，会有什么不同。

> 依据：[推荐] 时间压力决定该做「能用的」还是「扎实的」（无出处）

      A. 现在有明确的时间点必须完成 → 后果：优先做能用的部分
      B. 不紧急，但拖下去会越来越麻烦 → 后果：可以做得扎实些
      C. 只是想到就做了，没有硬性要求 → 后果：可以先做最小版本试试
      D. 其他：_______________

      **我的倾向：** B

## A2. 不做的话，最坏会怎样？

**从哪来：** 这条和 A1 是一对——A1 问「为什么做」，这条问「不做行不行」。

**不问会怎样：** 我可能把一件可有可无的事当成大事来做，也可能把一件要紧的事做轻了。

> 依据：[无参照] 代价高低由你的处境决定

      A. 会持续浪费你的时间 → 后果：值得认真做
      B. 会出错但影响不大 → 后果：做够用就行
      C. 其实影响很小 → 后果：考虑用更轻的办法
      D. 其他：_______________

## B. 成功与失败

## B1. 什么情况你会说"这次做对了"？

**从哪来：** 你前面说的是「想要什么」，没说「做到什么程度算完」。

**不问会怎样：** 验收标准由我定。做完你觉得不对，但说不清哪不对，我也没法改。

**你该怎么判断：** 想象东西摆在你面前，你会拿它做的第一件事是什么。那件事能顺利完成，就算对了。

> 依据：[检索] 未检索（「满意标准」无通用文献，逐人不同）

      A. 我不用改任何东西，直接用 → 后果：按最高标准做
      B. 大体可以，改一点小地方 → 后果：按常规标准做
      C. 能用就行，不追求好用 → 后果：做最小可用版本
      D. 其他：_______________

## B2. 什么情况你会说"这不是我要的"？

**从哪来：** 这条比 B1 更重要——失败比成功常见，而失败的样子更容易被说清。

**不问会怎样：** 我可能精准地做出一个你完全不需要的东西，而且自我感觉良好。

> 依据：[推荐] 「什么算失败」比「什么算成功」更能约束范围（无出处）

      A. 方向做错了，得重来 → 后果：必须先把方向确认死
      B. 方向对，但细节不是想要的 → 后果：细节也要逐条确认
      C. 做多了，我要的没做 → 后果：严格控制范围
      D. 其他：_______________

**我可能根本没问对：** 如果「做对/做错」这个框架本身对你不适用（比如你其实只是想先试试看），请直接说，我换一种问法。

## C1. 遇到 <某个具体特殊情况> 时，你希望怎么办？

**从哪来：** 你的描述里没提这种情况，但它一定会遇到。

**不问会怎样：** 我自己定规则。你第一次碰到不合意时，会以为是我做错了，其实是我替你做了个你没同意的决定。

> 依据：[检索] 未检索（具体案例的处置偏好无法外部参照）

      A. <处理方式一> → 后果：<...>
      B. <处理方式二> → 后果：<...>
      C. 这种时候提醒我，让我自己决定 → 后果：会打断你
      D. 其他：_______________

## C2. 有没有"绝对不能这样做"的？

**从哪来：** 这一条不来自你说过的话，而是来自你没说的话——红线通常是默认的，不说就当不存在。

**不问会怎样：** 我一旦踩到，做得再好也没用。

> 依据：[无参照] 红线只存在于你的经验里

      A. 有，是 <...> → 后果：我会避开
      B. 暂时没有 → 后果：我按常理判断
      C. 有，但我要看到具体场景才说得出来 → 后果：后面遇到再确认
      D. 其他：_______________

## D. 优先级

## D1. 如果只能做一半，你希望先做哪一半？

**从哪来：** 你列了 <n> 件事，没排序。

**不问会怎样：** 我按自己的判断排序。万一时间不够，我砍掉的恰好是你最在意的那部分。

**你该怎么判断：** 假设明天就要用，你今天最想先有这个的哪部分。

> 依据：[推荐] 先做主线、后做分支，能把风险留在后半段（无出处）

      A. 先能跑起来，不完善没关系 → 后果：先做主线
      B. 先做完整的一部分，其它以后再说 → 后果：先做某个模块
      C. 先做最难的部分验证可行性 → 后果：先做风险高的
      D. 其他：_______________
```

**R2 通过标准：**
- 至少确认了一个"为什么"
- 至少明确了一条"什么算失败"
- 至少确认了一条边界

**R2 常见失败：**
- 问的问题用户一句话答完（说明太浅）
- 全是"要不要支持 X"的封闭问题，挖不出意图
- 没问"什么算失败"，导致做出来用户不满意却说不清哪不对
- **选项只列了 agent 想到的方向，漏了用户真正在意的那个** → 所以「其他」必须有
- **只写「判断依据」不写「从哪来」** → 「判断依据」回答的是"我怎么想的"，用户想知道的是"这话从哪冒出来的"，两回事
- **每条都硬凑五元素** → 名词确认类问题也写「不问会怎样」，读起来像凑字数，反而稀释了真正重要的问题

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **跳过讨论直接给方案** | 违反铁律六，方案全废 | 必须先建 checklist |
| **选项里没有「其他」** | 逼迫选择，比开放式更糟 | 每条必须有，`gate.sh` 会拦 |
| **只给 2 个选项** | 两个都不完美时被迫选错 | 给 3-4 个方向 |
| **选项是"用 React 还是 Vue"** | 变成替你决定实现方案 | 只列理解方向 |
| 一轮问完所有问题 | 等于没讨论 | 必须分轮，R2 基于 R1 |
| checklist 写"确认鉴权方案" | 你答不了，讨论失效 | 换成"谁能看到" |
| 讨论完不落文档 | 结论蒸发，P1 又跑偏 | 每轮必须写 ALIGN 记录 |
| 讨论完直接进 P2 设计 | 跳过了 PRD | 顺序是 P0.5 → P1 → P2 |
| 把"你没意见"当确认 | 你可能只是没看 | 必须逐条回复 |

## 与通用框架的关系

Superpowers 的 `brainstorming` 只做一轮开放式提问，且不要求 checklist 前置、不要求小白语言、不强制分轮。

**本阶段替代它**，理由：
- 分轮 → 防止一轮问完就走
- checklist 前置 → 防止 agent 边问边想
- 小白语言 → 防止用技术词掩盖理解空白
- 落文档 → 防止结论蒸发
