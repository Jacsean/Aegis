# 00 · 核心原则与状态机总览

> **本文件每次会话必读。** 读完再按当前阶段加载对应文件。
> 本套方案的代号：**Aegis**（守护）。

---

## 1. 一句话定位

Aegis 是一套**以状态机为骨架、以制品为中心、以门禁为强制力**的工程流程系统。
它不是"流程建议"，是"流程执行"。

> 与通用方法论框架（如 Superpowers）的区别：
> 那些是**心法**（告诉你该怎么做）；
> Aegis 是**心法 + 招式 + 规矩 + 门卫**（不做到就不让过）。

---

## 2. 三轴模型

任何任务都可以用三个坐标描述：

```
轴一 阶段（Phase）：P0 立项 → P1 构思 → P2 设计 → P3 验证 → P4 实现 → P5 校验 → P6 归档 → P7 交付
轴二 制品（Artifact）：每个阶段有且仅有规定的产物，固定路径、固定 schema、必须登记索引
轴三 门禁（Gate）：每个阶段出口有 Exit Criteria，不满足则状态机拒绝前进
```

---

## 3. 六条铁律（不可违反）

### 铁律一：阶段不可跳

未通过当前阶段的全部出口门禁，**禁止**进入下一阶段。
用户要求跳步时，必须先说明"当前在 Pn，缺 X"，并获得用户**明确豁免**（记入 `STATE.md`）。

### 铁律二：设计前必须可视

**前端类项目的 P2 阶段，必须产出可在浏览器打开的 HTML demo，并获用户确认后，才能进入 P4 写业务代码。**
没有 demo 的前端设计 = 没有设计。

### 铁律三：完成必须留证

宣称"完成""修好""通过"时，**必须贴出验证输出**。
"我觉得可以""应该没问题"不算完成，视为未完成。

延伸到 P7：**交付说明里的步骤必须真的照抄跑过一遍。**
没跑过就写文档 = 交付假货。

### 铁律三之二：任务必须留档

**每个任务结束（合并进 main 前）必须写一条开发事件记录**，
记在 `docs/develop/handoff/H-<编号>-<短名>.md`，并在 `docs/develop/HANDOFF.md` 索引加一行。

七要素：时间 / 谁 / 事件 / 为什么这样处理 / 怎么处理的 / **试过什么（成没成）** / 下一步等谁。

- **「试过什么」不许空**：没走过弯路就写「本任务未走过弯路」
- **事实 / 推断 / 未知 分开标**：`〔推断〕`、`〔未知〕`，不标视为事实
- **过期不删**：划掉并指向新条目，因为下个 agent 读到旧结论会把新工作改回去

为什么必须有：**没有这一栏，下一个人（或三个月后的你）会把失败的路重走一遍。**

细则见 `.ai/99-reference/handoff-schema.md`。

### 铁律四：问题必须沉淀

任何调试超过 **15 分钟**、或试错 **2 次以上**、或发现"设计时没考虑到"的情况，
**必须**新建 `docs/incidents/INC-xxxx.md`。

其中 **「预防」一节为必填** —— 没有预防措施的 incident 不算闭环。

### 铁律五：单一真相源

`.ai/*.md` 是规矩的**唯一真相**。
`.skills/`、`adapters/`、`AGENTS.md` 内联段都是**派生物**，由 `make sync` 生成。
禁止手工维护两份内容 —— 这是 token 浪费的根源。

### 铁律六：讨论前置，禁止自作主张

**用户提出任何新要求后，禁止直接给出方案、计划或代码。**

必须先进入 P0.5 意图校准，完成**至少两轮讨论**：

| 轮次 | 目的 | 强制 |
|---|---|---|
| R1 复述轮 | 用自己的话复述，让用户纠正 | ❌ 不可跳 |
| R2 深层轮 | 挖"为什么/什么算失败/什么情况例外" | ❌ 不可跳 |
| R3 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件 |

**每轮开始前必须先产出一份 checklist**，用户确认清单本身后再逐条讨论。
checklist 必须使用**日常语言**——判断标准是：不懂技术的人也能直接回答。

**写清单之前还有一步：调研前置（第七维）。**
顺序是「判定领域 → 征询是否联网调研 → 调研 → 生成清单」。
每个关键点下面必须写清依据来源（`[检索]` / `[推荐]` / `[无参照]`），
清单末尾必须有「未覆盖方向」一节。无联网能力时必须**先告知再询问**，不许静默降级，不许伪装成查过。
详见 `.ai/015-P05-align.md` 的「第零步：调研前置」。

**讨论结论必须落文档**（`docs/align/`），它是 P1 写 PRD 的唯一依据。

> 违反示例：用户说"帮我做个 X"，agent 回"好的，我的方案是……"。
> 正确反应：先建 checklist，复述理解，确认后再谈方案。

## 3.1 分支铁律（配套铁律六）

**每个新任务或新要求，必须建立独立分支。**

```
main/master  ← 始终保持可运行
  └── feat/<任务短名>   新功能
  └── fix/<任务短名>    修问题
  └── docs/<任务短名>   文档
```

- 开始任务：`make branch NAME=<任务短名>`
- 完成任务：过完门禁 → `make branch-finish NAME=<任务短名>`
- **禁止**在 main 上直接改动（`gate.sh` 会拦截）
- 分支名不合规 → 门禁 FAIL

## 4. 会话启动协议（每次新会话按序执行）

```
① 读 AGENTS.md            （20 行精华，含指针）
② 读 STATE.md             （30 行快照：当前在哪、有什么、下一步）
③ 读本文件 00-core.md     （六条铁律）
④ 读 90-preferences.md    （用户偏好，始终生效）
⑤ 按 STATE.md 的当前阶段，加载 .ai/0X-Pn-*.md
⑥ 声明："当前阶段 Pn，本次目标 X，将加载文件 Y"
```

> **总共约 850 tokens。** 不读全项目、不读全部文档。
> 新会话上手靠 `STATE.md`，这是解决"每次重新分析整个项目"的关键。

## 5. 制品总表（一图看清每阶段产出什么）

| 阶段 | 名称 | 必备制品 | 人工签字 |
|---|---|---|---|
| P0 | 立项 | `AGENTS.md`、`.ai/`、`STATE.md`、`.venv`、`docs/INDEX.md` | ✅ |
| **P0.5** | **意图校准** | **`docs/align/CHECKLIST-*-R1/R2.md`、`ALIGN-*-R1/R2.md`、`ALIGN-*.md`** | ✅ **强制** |
| P1 | 构思 | `docs/prd.md`（六节，含非目标） | ✅ **强制** |
| P2 | 设计 | `docs/design/DESIGN.md`、`STYLE.md`、`demo/*.html`、`adr/*.md` | ✅ **强制（看 demo 后）** |
| P3 | 验证 | `docs/design/REVIEW-DESIGN.md`（12 项清单 + 意图复核 + 历史回灌） | ⚠️ 建议 |
| P4 | 实现 | `src/`、`tests/`、`docs/incidents/INC-*.md` | ❌ |
| P5 | 校验 | `docs/reviews/REVIEW-CODE-*.md`（三轮，含 INC 对照表） | ✅ 强制 |
| P6 | 归档 | `STATE.md` 重写（≤40 行）、`CHANGELOG.md`、`INDEX` 完整、`git tag` | ❌ |
| P7 | 交付 | `docs/release/RELEASE-v*.md`（含真实冒烟输出） | ✅ 强制 |

> 每阶段防的是哪一种失控，见 `AGENTS.md` 的阶段表下方。
> P6 与 P7 的读者不同：P6 给下一个会话的 agent，P7 给使用者。**混写两头失败。**

## 6. 冲突仲裁

当多方规矩冲突时，按此优先级：

```
1. 用户当前明确指令
2. 本文件 00-core.md 的六条铁律（含分支铁律）
3. .ai/ 下当前阶段规范
4. .ai/90-preferences.md 用户偏好
5. 通用方法论框架（Superpowers 等）
6. agent 默认行为
```

**遇到无法判断的冲突：向用户指出，不自行裁决。**

## 7. 阶段流转图

```
               ┌────────────────────────────────────────┐
               ↓                                        │
  P0 ──→ P0.5 ──→ P1 ──→ P2 ──→ P3 ──→ P4 ──→ P5 ──→ P6 ──→ P7
 立项   意图校准  构思   设计   验证   实现   校验   归档   交付
         ↑                │      │      │      │
         │                │      │      └──────┴──────→ 回 P4 / P2
         │                │      └──── 设计有缺陷 → 回 P2
         │                └─────────── 需求不清 → 回 P1 或 P0.5
         └──────────────────────────── 意图变了 → 回 P0.5
```

**回退是正常流程，不是失败。** 在纸上改，成本是改代码的 1/10。

特别提示：**P1 写 PRD 时如果发现意图还没校准清楚，必须回 P0.5**，
不能在 PRD 里"边写边猜"。
