## 0. 八阶段状态机（当前生效 · v2.0.0，

**场景决断（入口分诊，非阶段）先行**：每次会话按关键字定场景，路由阶段组合（见 `.ai/09-scene-triage.md`）。

| 阶段 | 认知状态 | 出口（必须有） |
|---|---|---|
| S1 立题 | 这件事值不值得做 | 项目前提清单（假设显式化） |
| S2 对齐 | 我和你理解一致吗 | 用户签字（全流程唯一强制签字点）+ 前提清单顺带确认 |
| S3 收敛 | 问题边界在哪 | 范围声明 + 失败定义（PRD）；与 S2 一致时签字自动继承 |
| S4 展开 | 方案空间有多大 | 权衡矩阵 + 决策记录 + 可视 demo |
| S5 找破绽（可重复） | 这个方案哪里会崩 | 破绽清单非空且全部处置（对象=设计/代码两个检查点） |
| S6 实现 | 按已定方案落地 | 可运行 + 测试 + 偏离记录 |
| S7 固化 | 怎么让它下次能用 | 状态快照 + 归因记录 + 概念固化申报 |
| S8 交付 | 别人能用吗 | 交付说明 + 使用者签收 |

阶段规范：`.ai/10-S1` ~ `17-S8`；含 S1 裁剪（迭代场景）、S5 短路径形态、S7/S8 轻量收尾等场景规则。
**本骨架之前的旧阶段设计已作废**：旧文件仅设计者维度可回溯，交付包内不含，使用路径上不出现。

## 1. 一句话定位

Aegis 是一套**以状态机为骨架、以制品为中心、以门禁为强制力**的工程流程系统。
它不是"流程建议"，是"流程执行"。

> 与通用方法论框架（如 Superpowers）的区别：
> 那些是**心法**（告诉你该怎么做）；
> Aegis 是**心法 + 招式 + 规矩 + 门卫**（不做到就不让过）。

---

## 2. 三轴模型

任何任务都可以用三个坐标描述：

```
轴一 阶段（Phase）：S1 立题 → S2 对齐 → S3 收敛 → S4 展开 → S5 找破绽 → S6 实现 → S7 固化 → S8 交付
轴二 制品（Artifact）：每个阶段有且仅有规定的产物，固定路径、固定 schema、必须登记索引
轴三 门禁（Gate）：每个阶段出口有 Exit Criteria，不满足则状态机拒绝前进
```

## 3. 七条铁律（不可违反）

### 铁律一：阶段不可跳

未通过当前阶段的全部出口门禁，**禁止**进入下一阶段。
用户要求跳步时，必须先说明"当前在 Sn，缺 X"，并获得用户**明确豁免**（记入 `STATE.md`）。

### 铁律二：设计前必须可视

**前端类项目的 S4 展开阶段，必须产出可在浏览器打开的 HTML demo，并获用户确认后，才能进入 S6 写业务代码。**
没有 demo 的前端设计 = 没有设计。

### 铁律三：完成必须留证

宣称"完成""修好""通过"时，**必须贴出验证输出**。
"我觉得可以""应该没问题"不算完成，视为未完成。

延伸到 S8：**交付说明里的步骤必须真的照抄跑过一遍。**
没跑过就写文档 = 交付假货。

### 铁律三之二：任务必须留档

**每个任务结束（合并进 main 前）必须写一条开发事件记录**，
记在 `dev/handoff/H-<编号>-<短名>.md`，并在 `dev/HANDOFF.md` 索引加一行。

七要素：时间 / 谁 / 事件 / 为什么这样处理 / 怎么处理的 / **试过什么（成没成）** / 下一步等谁。

- **「试过什么」不许空**：没走过弯路就写「本任务未走过弯路」
- **事实 / 推断 / 未知 分开标**：`〔推断〕`、`〔未知〕`，不标视为事实
- **过期不删**：划掉并指向新条目，因为下个 agent 读到旧结论会把新工作改回去

为什么必须有：**没有这一栏，下一个人（或三个月后的你）会把失败的路重走一遍。**

细则见 `.ai/99-reference/handoff-schema.md`。

### 铁律四：问题必须沉淀

任何调试超过 **15 分钟**、或试错 **2 次以上**、或发现"设计时没考虑到"的情况，
**必须**新建 `docs/incidents/INC-xxxx.md`。

其中 **「预防」一节为必填** —— 没有预防措施的 incident 不算闭环。

### 铁律五：单一真相源

`.ai/*.md` 是规矩的**唯一真相**。
`.skills/`、`adapters/`、`AGENTS.md` 内联段都是**派生物**，由 `make sync` 生成。
禁止手工维护两份内容 —— 这是 token 浪费的根源。

### 铁律六：讨论前置，禁止自作主张

**用户提出任何新要求后，禁止直接给出方案、计划或代码。**

必须先进入 S2 对齐，完成**至少两轮讨论**：

| 轮次 | 目的 | 强制 |
|---|---|---|
| R1 复述轮 | 用自己的话复述，让用户纠正 | ❌ 不可跳 |
| R2 深层轮 | 挖"为什么/什么算失败/什么情况例外" | ❌ 不可跳 |
| R3 边界轮 | 只在前两轮发现重大歧义时触发 | ⚠️ 条件 |

**每轮开始前必须先产出一份 checklist**，用户确认清单本身后再逐条讨论。
checklist 必须使用**日常语言**——判断标准是：不懂技术的人也能直接回答。

**写清单之前还有一步：调研前置（第七维）。**
顺序是「判定领域 → 征询是否联网调研 → 调研 → 生成清单」。
每个关键点下面必须写清依据来源（`[检索]` / `[推荐]` / `[无参照]`），
清单末尾必须有「未覆盖方向」一节。无联网能力时必须**先告知再询问**，不许静默降级，不许伪装成查过。
详见 `.ai/11-S2-align.md` 的「第零步：调研前置」。

**讨论结论必须落文档**（`docs/align/`），它是 S3 写 PRD 的唯一依据。

> 违反示例：用户说"帮我做个 X"，agent 回"好的，我的方案是……"。
> 正确反应：先建 checklist，复述理解，确认后再谈方案。

### 铁律七：概念先定义后使用

**项目中反复使用的词，禁止在未定义的情况下当作已共识使用。**

概念固化的三个挂点（不新增阶段）：

| 挂点 | 动作 | 强制 |
|---|---|---|
| 校准（S2 对齐） | 列出本次工作的新词候选清单，逐个用五元素问用户「这个词你怎么理解」 | ❌ 不可跳 |
| 任务进行中 | 新词出现 → 先命名再讨论；达成一致理解后写入 `docs/CONCEPTS.md`，标 `暂定` | 随发生随做 |
| S7 固化 | 在 handoff 记录写「**新词**」一行（无则写「无」）；有新词的，词条状态要落实（升 `已定` 或保持 `暂定` 并注明待验收） | ❌ 不可跳 |

概念的出现不是在项目一开始就全部涌现（用户原话）——所以固化是常设动作，不是一次性工程。

## 3.2 修订留痕规则（设计被推翻时，三动作同时做）

**推翻或改造任何已成文的设计时，禁止只写新设计、不动旧设计。** 三动作缺一不可：

1. **旧文件头**加状态行：`> 状态：已作废（日期）→ 被〈新路径/新设计〉取代（见 H-xxxx）`
2. **INDEX**（`docs/INDEX.md`）状态列同步更新——agent 找文档先查索引，作废的在索引上显形
3. **handoff 记录**「怎么处理的」写明「旧设计 XX 已作废，指向 YY」

设计文档头部必须有状态行（`定稿` / `暂定` / `已作废→指向`），状态词沿用概念表四态。
门禁对「缺状态行」「已作废却无指向」告警（铁律五的配套，。

## 3.1 分支铁律（配套铁律六）

**每个新任务或新要求，必须建立独立分支。**

```
main/master  ← 始终保持可运行
  └── feat/<任务短名>   新功能
  └── fix/<任务短名>    修问题
  └── docs/<任务短名>   文档
```

- 开始任务：`make branch NAME=<任务短名>`
- 完成任务：过完门禁 → `make branch-finish NAME=<任务短名>`
- **禁止**在 main 上直接改动（`gate.sh` 会拦截）
- 分支名不合规 → 门禁 FAIL

## 4. 会话启动协议（每次新会话按序执行）

```
① 读 AGENTS.md            （20 行精华，含指针）
② 读 STATE.md             （30 行快照：当前在哪、有什么、下一步）
③ 读本文件 00-core.md     （七条铁律）
④ 读 90-preferences.md    （用户偏好，始终生效）
⑤ 读 docs/CONCEPTS.md 的「目录」节（约 200 tokens，只读一句话列）
⑥ 按 STATE.md 的当前阶段，加载 .ai/1X-Sn-*.md
⑦ 声明："当前阶段 Pn，本次目标 X，将加载文件 Y"
```

> **总共约 1050 tokens。** 不读全项目、不读全部文档。
> 新会话上手靠 `STATE.md`，这是解决"每次重新分析整个项目"的关键。

## 5. 制品总表（一图看清每阶段产出什么）

| 阶段 | 名称 | 必备制品 | 用户签字 |
|---|---|---|---|
| 场景决断 | 入口分诊 | 场景声明（点名 4 类之一 + 理由） | ❌ |

| **S2 对齐** | 意图校准 | `docs/align/CHECKLIST-*-R1/R2.md`、`ALIGN-*-R1/R2.md`、`ALIGN-*.md` | ✅ **强制（全流程唯一强制签字点）** |
| S3 收敛 | 划边界 | `docs/prd.md`（范围声明/失败定义/功能/非目标/成功判据/风险 六节） | ✅ 与 S2 一致时自动继承 |
| S4 展开 | 摊方案 | `docs/design/DESIGN.md`、`STYLE.md`、`demo/*.html`、`adr/*.md` | ✅ **强制（看 demo 后）** |
| S5 找破绽 | 查崩点 | `docs/design/REVIEW-DESIGN.md` 或 `docs/reviews/REVIEW-CODE-*.md`（按检查点） | ⚠️ 建议 |

| S7 固化 | 归档 | `STATE.md` 重写（≤40 行）、`CHANGELOG.md`、`INDEX` 完整、`git tag`、handoff | ❌ |
| S8 交付 | 出包 | `docs/release/RELEASE-v*.md`（含真实冒烟输出） | ✅ 强制 |

> 每阶段防的是哪一种失控，见 `AGENTS.md` 的阶段表下方。
> S7 与 S8 的读者不同：S7 给下一个会话的 agent，S8 给使用者。**混写两头失败。**

## 6. 冲突仲裁

当多方规矩冲突时，按此优先级：

```
1. 用户当前明确指令
2. 本文件 00-core.md 的七条铁律（含分支铁律）
3. .ai/ 下当前阶段规范
4. .ai/90-preferences.md 用户偏好
5. 通用方法论框架（Superpowers 等）
6. agent 默认行为
```

**遇到无法判断的冲突：向用户指出，不自行裁决。**
