# 06 · P5 校验（Verify）

> 状态：已作废（2026-10-21，八阶段定稿 H-0022 落地中）→ 由八阶段新文档「S5 找破绽（合并 04）」取代；本文件仅回溯可读，使用过程禁止引用

> 目的：交付前最后一关。**三轮独立 review，Critical 清零才放行。**
>
> 本阶段的灵魂是第三轮：**历史缺陷回灌** —— 让踩过的坑真正变成资产。

---

## 为什么是三轮，不是一轮

一轮 review 只能查出"眼前的问题"。你需要三种不同视角：

| 轮次 | 视角 | 回答的问题 | 谁容易漏 |
|---|---|---|---|
| 一 | 需求视角 | **对不对** | 光看代码好看，忘了需求 |
| 二 | 工程视角 | **好不好** | 光跑通，不管可维护性 |
| 三 | 历史视角 | **会不会再犯** | 几乎所有人都漏 |

---

## 铁律：三轮必须独立视角

**同一轮既写又审 = 自证，不算。**

| 情况 | 可否 |
|---|---|
| 写完后立刻自己审一遍就交 | ❌ 不算三轮 |
| 三轮连着做但每轮只看一个维度 | ✅ 可以（单人项目的现实做法） |
| 换一个 agent / 换一会话再审 | ✅ 最佳 |

单人项目无法换人时，**至少要求"分轮且不边看边改"**：
第一轮只记录问题不改代码，三轮全过才开始修。

---

## 输入

- `src/`、`tests/`
- `docs/prd.md`（验收标准）
- `docs/design/DESIGN.md`
- `docs/align/ALIGN-<任务>.md`（真实意图）
- `docs/incidents/`（历史故障库）
- `docs/design/REVIEW-DESIGN.md`（P3 遗留待验证项）

## 动作清单

### 第一轮：规格符合性（对不对）

**只看"做的是不是要的"，不看代码写得好不好。**

逐条对照 PRD 验收标准：

| PRD 标准 | 实现位置 | 符合 | 证据 |
|---|---|---|---|
| 用户可用邮箱登录 | `src/auth.py:88` | ✅ | `test_login_ok` 通过 |
| 密码错误有提示 | — | ❌ | 未实现 |

再对照 ALIGN 的边界：
- 「这次不做什么」有没有做
- 「绝对不要」有没有踩

**产出**：符合性表 + 偏差清单。

### 第二轮：代码质量（好不好）

**只看"写得好不好"，不看功能对不对。**

逐项检查：

- [ ] 命名清晰，无死代码
- [ ] 无硬编码 / 无调试残留
- [ ] 错误处理完整，无空 catch
- [ ] 依赖可注入，可测试
- [ ] 无性能隐患（N+1 / 全量渲染 / 同步阻塞）
- [ ] 注释解释"为什么"而非"做什么"
- [ ] 无未确认的新依赖
- [ ] 测试覆盖正常 + 边界

**产出**：问题清单（位置 + 问题 + 严重度）。

### 第三轮：历史缺陷回灌（会不会再犯）⭐

**这是本方案区别于通用框架的核心。**

打开 `docs/incidents/`，**逐条**做：

| INC | 现象 | 本次会再犯？ | 依据 |
|---|---|---|---|
| INC-0001 | 时区导致日期偏移 | 否 | 统一 UTC 存储，`test_tz` 覆盖 |
| INC-0002 | 空数据崩溃 | **是** | `src/list.py:42` 同类写法 → 已修 |
| INC-0003 | 未建 venv | 否 | gate.sh P0 已检查 |

规则：
- 「会再犯=是」→ **必须修**，不能只记
- 若确认无法修 → 登记为「已知限制」并在 RELEASE 说明

**产出一张完整的 INC 对照表，一条不落。**

### 四、汇总与判定

| 轮次 | Critical | Major | Minor |
|---|---|---|---|
| 一 | 0 | 0 | 1 |
| 二 | 0 | 2 | 3 |
| 三 | 1 | 0 | 0 |

**放行规则：**
- Critical 必须为 **0**
- Major 必须已修或登记
- Minor 可登记后放行

## 人工确认

✅ **必须**。用户验收，签字写入 `STATE.md`。

验收时给用户看的是**结论与证据**，不是代码：

```
P5 校验完成。

规格符合：PRD 8 条验收标准，7 条通过，1 条部分实现（详见文档）
代码质量：Critical 0，Major 2（已修），Minor 3（已登记）
历史回灌：检查 12 条历史问题，1 条有重犯风险，已修

测试输出：
<paste：42 passed>

是否可以进入归档？（Y / 先看 REVIEW-CODE 详情）
```

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **三轮合成一轮** | 视角混淆，漏检严重 | 分轮，每轮只关注一个维度 |
| **跳过第三轮** | 历史缺陷必然复发 | 这是最重要的一轮 |
| **INC 对照表只写"无风险"** | 等于没查 | 每条都要写依据 |
| **发现问题边审边改** | 后面的轮次审的是改后的代码，前后不一致 | 三轮全记录完再统一修 |
| Critical 不为 0 就放行 | 带病交付 | 硬性要求清零 |
| 只跑测试不看测试内容 | 测试本身可能有错 | 第二轮要检查测试质量 |

## 与 P3 的区别

| | P3 设计评审 | P5 代码评审 |
|---|---|---|
| 对象 | 设计文档 + demo | 源码 + 测试 |
| 时机 | 写代码前 | 交付前 |
| 视野 | 架构合理性 | 实现正确性 + 质量 |
| 历史回灌 | ✅ 也做 | ✅ **重点做** |

两处都做历史回灌，是刻意的：设计阶段防"设计层面重蹈覆辙"，实现阶段防"代码层面重蹈覆辙"。
