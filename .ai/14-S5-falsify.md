## 认知状态

## 可重复：两个检查点（M7，合并九阶段 P3+P5）
1. **对象 = 设计**（S4 之后）：反证 + 失败模式分析；有破绽 → 回 S4 改
2. **对象 = 代码**（S6 之后）：同一套手法查实现；必须真跑、贴验证输出；有破绽 → 回 S6 改

## 出口（U8）

退回不是失败，是省钱。需求理解错→回 S2/S3；架构方向不对→回 S4；3 项以上清单不过→回 S4。

没有 S4 方案可查：S5 查对象降为 **复现 + 根因假设 + 修复方案的破绽检查**。

## 门禁要点
破绽清单存在且非空、每条有处置、（代码检查点）验证输出已贴。

# 04 · P3 验证（Validate Design）


> 目的：**设计做完先自查，再进实现。**
> 在纸上改，成本是改代码的 1/10。
>
> 本阶段不写代码、不改设计内容 —— 只做**审查与判定**。

---

## 为什么单独一个阶段

通用框架里"设计完就直接实现"，问题在纸上发现不了，等写出来才发现，返工成本十倍。

更隐蔽的问题是：**之前犯过的错会再犯**，因为没有机制把历史教训带进新设计。

P3 就是补这两个缺口：
1. 强制自查（12 项清单）
2. 强制历史回灌（对照 incidents 库）

---

## 输入

- `docs/design/DESIGN.md`
- `docs/design/STYLE.md`
- `docs/design/demo/*.html`
- `docs/adr/*.md`
- `docs/prd.md`（验收标准，用于对照）
- `docs/align/ALIGN-<任务>.md`（**真实意图，最高依据**）
- `docs/incidents/`（历史故障库）

---

## 动作清单

### 1. 逐条过 12 项清单

清单全文见 `.ai/99-reference/design-review-checklist.md`。

**不是打勾了事** —— 每一项都要写下：
- 检查了什么
- 结论是什么
- 发现问题 → 怎么处理

### 2. 意图一致性复核（本阶段特有）

除了 12 项技术清单，额外做一次**意图比对**：

| 对照项 | 检查什么 |
|---|---|
| ALIGN 第 4 节「这次做什么」 | DESIGN 是否全都覆盖 |
| ALIGN 第 5 节「这次不做什么」 | DESIGN 是否偷偷做了 |
| ALIGN 第 5 节「绝对不要」 | DESIGN 是否踩了红线 |
| ALIGN 第 6 节「什么算搞砸」 | DESIGN 是否会导致那些情形 |

> 这一步比技术清单更容易发现问题。技术都对，但做的不是用户要的 —— 这才是最贵的错。

### 3. 历史缺陷回灌

打开 `docs/incidents/`，**逐条**问：

> 「这个设计会不会让 INC-xxxx 再发生一次？」

记录格式：

| INC | 现象 | 会不会再犯 | 依据 |
|---|---|---|---|
| INC-0001 | 时区导致日期偏移 | 否 | DESIGN 3.4 统一用 UTC 存储 |
| INC-0002 | 空数据崩溃 | **是** | DESIGN 未定义空状态 → 已补 |

「会不会再犯=是」的，必须当场补设计或登记为已知限制。

### 4. 写评审记录

`docs/design/REVIEW-DESIGN.md`，按模板逐项记录。

### 5. 给出结论（三选一）

| 结论 | 条件 | 下一步 |
|---|---|---|
| **通过** | 12 项全绿，无 Critical | 进 P4 |
| **修正后通过** | 1-2 项小问题，已现场修正 | 进 P4 |
| **退回 P2** | 3 项以上问题，或涉及架构/意图偏差 | 回 P2 重新设计 |

---

## 必备制品

| 制品 | 路径 | 要求 |
|---|---|---|
| 设计评审记录 | `docs/design/REVIEW-DESIGN.md` | 12 项逐条有结论 + 意图复核 + 历史回灌 |
| 索引登记 | `docs/INDEX.md` | 已登记 |
| 状态更新 | `STATE.md` | 阶段 = P3，结论已记录 |

---

## 出口门禁

- [ ] `REVIEW-DESIGN.md` 存在，且勾选条目 ≥ 12
- [ ] 每项都有结论，不是空勾
- [ ] 有「意图一致性复核」一节，对照了 ALIGN 的四节
- [ ] 有「历史缺陷回灌」一节，逐条对照了 incidents
- [ ] 结论明确（通过 / 修正后通过 / 退回 P2）
- [ ] 若「退回 P2」，则**不得进入 P4**
- [ ] `bash scripts/gate.sh P3` 输出 PASS

---

## 人工确认

⚠️ **建议确认，但不强制**。

- 小改动：agent 自查通过即可进 P4
- 涉及架构 / 用户可见行为变化：**必须**给用户看结论摘要

给用户的摘要格式（不要贴全文）：

```
P3 设计评审完成，结论：<通过 / 修正后通过 / 退回 P2>

发现的问题：
1. <问题> → <处理>
2. <问题> → <处理>

历史故障回灌：检查了 N 条历史问题，其中 1 条可能重犯，已补设计。

是否可以进入实现？（Y / 先看 REVIEW-DESIGN.md）
```

---

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **只打勾不写结论** | 等于没查，自欺 | 每项必须写"查了什么、结论是什么" |
| **跳过意图复核，只看技术** | 技术都对但做的不是用户要的 | 必须对照 ALIGN |
| **不回灌历史故障** | 老毛病反复出现 | 逐条对照 incidents |
| **发现问题但"先实现再说"** | 返工成本 ×10 | 当场修或退回 P2 |
| **沉没成本心态**：已经写了很多，不忍推翻 | 带着缺陷进实现 | 已写的不是保留理由 |
| **自己审自己做的设计还自我说服** | 自证无效 | 按清单机械执行，不靠感觉 |

---

## 关键判断：什么时候该退回 P2

不要因为"已经写了不少"而勉强通过。以下任一情况，**退回 P2**：

- 发现需求理解错了（→ 其实该回 P0.5 或 P1）
- 架构方向不对（分层错了、依赖成环）
- 缺少关键模块，要新增
- 前端 demo 无法支撑 PRD 的关键界面
- 3 项以上清单不过

> 退回不是失败，是省钱。设计阶段推翻的成本是实现的 1/10。

# 06 · P5 校验（Verify）


> 目的：交付前最后一关。**三轮独立 review，Critical 清零才放行。**
>
> 本阶段的灵魂是第三轮：**历史缺陷回灌** —— 让踩过的坑真正变成资产。

---

## 为什么是三轮，不是一轮

一轮 review 只能查出"眼前的问题"。你需要三种不同视角：

| 轮次 | 视角 | 回答的问题 | 谁容易漏 |
|---|---|---|---|
| 一 | 需求视角 | **对不对** | 光看代码好看，忘了需求 |
| 二 | 工程视角 | **好不好** | 光跑通，不管可维护性 |
| 三 | 历史视角 | **会不会再犯** | 几乎所有人都漏 |

---

## 铁律：三轮必须独立视角

**同一轮既写又审 = 自证，不算。**

| 情况 | 可否 |
|---|---|
| 写完后立刻自己审一遍就交 | ❌ 不算三轮 |
| 三轮连着做但每轮只看一个维度 | ✅ 可以（单人项目的现实做法） |
| 换一个 agent / 换一会话再审 | ✅ 最佳 |

单人项目无法换人时，**至少要求"分轮且不边看边改"**：
第一轮只记录问题不改代码，三轮全过才开始修。

---

## 输入

- `src/`、`tests/`
- `docs/prd.md`（验收标准）
- `docs/design/DESIGN.md`
- `docs/align/ALIGN-<任务>.md`（真实意图）
- `docs/incidents/`（历史故障库）
- `docs/design/REVIEW-DESIGN.md`（P3 遗留待验证项）

---

## 动作清单

### 第一轮：规格符合性（对不对）

**只看"做的是不是要的"，不看代码写得好不好。**

逐条对照 PRD 验收标准：

| PRD 标准 | 实现位置 | 符合 | 证据 |
|---|---|---|---|
| 用户可用邮箱登录 | `src/auth.py:88` | ✅ | `test_login_ok` 通过 |
| 密码错误有提示 | — | ❌ | 未实现 |

再对照 ALIGN 的边界：
- 「这次不做什么」有没有做
- 「绝对不要」有没有踩

**产出**：符合性表 + 偏差清单。

### 第二轮：代码质量（好不好）

**只看"写得好不好"，不看功能对不对。**

逐项检查：

- [ ] 命名清晰，无死代码
- [ ] 无硬编码 / 无调试残留
- [ ] 错误处理完整，无空 catch
- [ ] 依赖可注入，可测试
- [ ] 无性能隐患（N+1 / 全量渲染 / 同步阻塞）
- [ ] 注释解释"为什么"而非"做什么"
- [ ] 无未确认的新依赖
- [ ] 测试覆盖正常 + 边界

**产出**：问题清单（位置 + 问题 + 严重度）。

### 第三轮：历史缺陷回灌（会不会再犯）⭐

**这是本方案区别于通用框架的核心。**

打开 `docs/incidents/`，**逐条**做：

| INC | 现象 | 本次会再犯？ | 依据 |
|---|---|---|---|
| INC-0001 | 时区导致日期偏移 | 否 | 统一 UTC 存储，`test_tz` 覆盖 |
| INC-0002 | 空数据崩溃 | **是** | `src/list.py:42` 同类写法 → 已修 |
| INC-0003 | 未建 venv | 否 | gate.sh P0 已检查 |

规则：
- 「会再犯=是」→ **必须修**，不能只记
- 若确认无法修 → 登记为「已知限制」并在 RELEASE 说明

**产出一张完整的 INC 对照表，一条不落。**

### 四、汇总与判定

| 轮次 | Critical | Major | Minor |
|---|---|---|---|
| 一 | 0 | 0 | 1 |
| 二 | 0 | 2 | 3 |
| 三 | 1 | 0 | 0 |

**放行规则：**
- Critical 必须为 **0**
- Major 必须已修或登记
- Minor 可登记后放行

## 人工确认

✅ **必须**。用户验收，签字写入 `STATE.md`。

验收时给用户看的是**结论与证据**，不是代码：

```
P5 校验完成。

测试输出：
<paste：42 passed>

是否可以进入归档？（Y / 先看 REVIEW-CODE 详情）
```

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **三轮合成一轮** | 视角混淆，漏检严重 | 分轮，每轮只关注一个维度 |
| **跳过第三轮** | 历史缺陷必然复发 | 这是最重要的一轮 |
| **INC 对照表只写"无风险"** | 等于没查 | 每条都要写依据 |
| **发现问题边审边改** | 后面的轮次审的是改后的代码，前后不一致 | 三轮全记录完再统一修 |
| Critical 不为 0 就放行 | 带病交付 | 硬性要求清零 |
| 只跑测试不看测试内容 | 测试本身可能有错 | 第二轮要检查测试质量 |

---

## 与 P3 的区别

| | P3 设计评审 | P5 代码评审 |
|---|---|---|
| 对象 | 设计文档 + demo | 源码 + 测试 |
| 时机 | 写代码前 | 交付前 |
| 视野 | 架构合理性 | 实现正确性 + 质量 |
| 历史回灌 | ✅ 也做 | ✅ **重点做** |

两处都做历史回灌，是刻意的：设计阶段防"设计层面重蹈覆辙"，实现阶段防"代码层面重蹈覆辙"。
