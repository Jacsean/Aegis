## 动作清单

### 1. 环境确认（每次开始前）

```bash
# Python 项目
[ -d .venv ] || { echo "缺 .venv，回 P0"; exit 1; }
.venv/bin/python --version

# Node 项目
[ -d node_modules ] || pnpm install
```

**铁律：Python 一律用 `.venv/bin/python` 显式调用，不依赖 activate。**

### 2. TDD 循环（每个功能点）

```
写一个失败的测试 → 看它失败 → 写最小实现 → 看它通过 → 重构
```

**关键**：必须**真的看到测试失败**。没看到失败就写实现，等于没测。

对每个功能点：
- 至少 1 个正常用例
- 至少 1 个边界用例
- 修 bug：先写能复现的失败测试，再修

### 3. 前端实现以 demo 为准

- 样式取值从 `docs/design/STYLE.md` 拿，不临时决定
- 交互 5 态（正常/空/加载/错误/交互反馈）必须都实现，不能只做正常态
- 与 demo 不一致的地方，**改代码不改 demo**（demo 是用户确认过的）

### 4. 小步提交

- 一个提交只做一件事
- 提交信息：`<类型>(<范围>): <描述>`
- 提交前跑测试，不过不提交

### 5. incident 记录（强制触发）

满足任一条件，**必须**新建 `docs/incidents/INC-<序号>.md`：

| 触发条件 | 说明 |
|---|---|
| 调试超过 15 分钟 | 计时从"发现问题"开始 |
| 试错 2 次以上 | 换了两种做法才解决 |
| 发现"设计时没考虑到" | 设计遗漏 |
| 用户指出的问题 | 尤其是设计层面的 |
| 环境/依赖导致非预期行为 | 不是代码问题也要记 |

**「预防」一节必填** —— 没写预防，incident 不算闭环。

示例预防：
- 加了测试 `test_xxx`
- 加了 `gate.sh` 检查项
- 改了 `.ai/` 规范
- 补了 `DESIGN.md` 某节

### 6. 实现偏离设计时回写

实现中如果发现设计不可行或需调整：

1. **不要偷偷改**
2. 在 `DESIGN.md` 对应节标注「实现时调整为 <...>，原因 <...>」
3. 若涉及架构：新增 ADR
4. 若涉及需求范围：回 P1 或 P0.5

## 人工确认

❌ **不需要**。可连续执行。

但如果出现以下情况，**必须停下来问**：

| 情况 | 为什么 |
|---|---|
| 设计不可行，需要改架构 | 属方案性问题 |
| 需要引入新依赖 | 属方案性问题 |
| 需求有歧义，两种实现都说得通 | 属意图性问题 |
| 想删除/重写已有代码 | 高风险 |

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **没看到测试失败就写实现** | 测试形同虚设 | 必须真的看到 RED |
| **调试完不记 incident** | 下次同一坑再踩 | 超 15 分钟就记 |
| **incident 不写预防** | 只是日记，无累积 | 「预防」必填 |
| 偷偷改设计不吭声 | 文档与代码背离 | 必须回写 |
| 用系统 python 不用 venv | 环境不可复现 | 显式调 `.venv/bin/python` |
| 前端只做正常态 | 用户看到的是半成品 | 5 态全做 |
| 一个提交改十个文件 | 出问题无法定位 | 小步提交 |

## 与 P3 的边界

| | P3 验证 | P4 实现 |
|---|---|---|
| 做什么 | 审查设计 | 写代码 |
| 产出 | REVIEW-DESIGN.md | src / tests / INC |
| 改设计吗 | ❌ 只判定，要改就退回 P2 | ⚠️ 可回写标注 |
| 人工确认 | 建议 | 不需要 |

---

## 关键提醒

**P4 最容易出问题的地方不是写不出来，而是"写着写着就偏离了"。**

三个偏离信号：
1. 开始觉得"这样写更好"但又说不出好在哪
2. 需要临时加一个设计里没有的模块
3. 发现某条验收标准无法满足

任一出现 → 停下来，回写 DESIGN.md 或退回 P3/P2，不要闷头继续。
