# 附录 · 本阶段详细手法（自旧骨架迁移后已按 S 编号重写；旧文本仅设计者档案可回溯）

# S7 · 固化（手法细则）


> 目的：把"这次干成了什么"固化成**下一次能直接用**的东西。
>
> S7 不产出新功能。它只做一件事：**让下一个会话、下一个任务、下一个月的你，能在 30 秒内接上。**
>
> 这是解决"阶段性成果没固化，新任务要重新分析整个项目"的那一环。

---

## 为什么归档要单独成一个阶段

多数流程把"归档"当成交付的收尾动作，顺手做。结果必然是：

- STATE.md 一个版本用了半年，写的还是上个阶段
- CHANGELOG 三个月没更，回头查"这个功能哪来的"查不到
- 分支合了但没人知道合的是哪次需求
- 下个任务开工时，agent 又从零读一遍全部文档

**归档不是"整理"，是"为下一次启动准备燃料"。**

没有 S7 的 30 分钟，S2 会多花 3 小时。

---

## 两条铁律

### 铁律一：归档只允许写，不允许改代码

S7 期间**禁止修改 `src/` 和 `tests/`**。

发现代码问题 → 记进 `STATE.md` 的「已知限制」，或另开分支修。不能在归档时顺手改一行 —— 那会让 S5 的评审结论失效（评审的是改前的代码）。

> 判断标准：S7 的提交里如果有 `.py` / `.js` / `.ts` 文件被改动，就是错的。
> `gate.sh S7` 会检查这一点。

### 铁律二：归档的读者是"没有上下文的自己"

写每一条时问一遍：**三个月后完全忘了这事的我，看这条能懂吗？**

不能 → 重写。具体到：

| ❌ 写了等于没写 | ✅ 有效 |
|---|---|
| 优化了性能 | 列表页首屏从 2.1s 降到 0.4s（加了索引 + 去掉 N+1 查询，见 INC-0007） |
| 修了几个 bug | 修了 3 个：空数据崩溃（INC-0005）、时区偏移（INC-0006）、导出乱码（INC-0007） |
| 重构了登录 | 登录从 session 改 JWT，原因见 ADR-0003，代价是登出需要前端主动清 token |

## 输入

- `STATE.md`（当前状态）
- `docs/reviews/REVIEW-CODE-<日期>.md`（S5 结论）
- `docs/incidents/INC-*.md`（本迭代新增的）
- `docs/adr/ADR-*.md`（本迭代新增的）
- `git log main..HEAD`（本分支做了什么）
- `git diff --stat main...HEAD`（改了哪些文件）

## 动作清单

### 1. 从 git 提取本轮事实（不靠记忆）

```bash
# 本分支相对主分支做了什么
git log --oneline main..HEAD
# 改了哪些文件、多少行
git diff --stat main...HEAD
# 本分支涉及的所有 INC
git log --oneline main..HEAD -- docs/incidents/
```

**先看事实，再写字。** 凭记忆写 CHANGELOG 必然漏项。

### 2. 更新 `STATE.md`（最重要的一步）

STATE.md 是下一个会话的**唯一入口**。它在 S7 必须被整体重写，不是小修小补。

按 `.ai/99-reference/state-schema.md` 逐节过：

| 小节 | S7 要做什么 |
|---|---|
| 项目 / 类型 / 技术栈 | 若本迭代有变化（换了库、加了数据库），改 |
| **当前阶段** | 改为 S7 或 S8 |
| **当前迭代** | 改成这次的名字，如 `v1.3 用户登录` |
| 已完成 | **把本迭代完成的项追加进去**，旧的压缩成一行 |
| 进行中 | 清空本迭代的项，只留真正未完成的 |
| 下一步 | 重写为"下一个人该干什么"，可执行 |
| 门禁签字 | 补 S5 的签字 |
| 最近决策 | 追加本迭代的 ADR 和 INC 编号（最多留 5 条，旧的删） |
| 已知限制 | 追加本迭代确认不修的项（从 S5 的 Major/Minor 登记里搬） |
| 豁免记录 | 追加本迭代的跳步豁免（若有） |

**硬约束：全文仍不超过 40 行。** 超了 = 没压缩 = 下个会话要读太多。

> 压缩原则：已完成的细节去 CHANGELOG 查，STATE.md 只留"做完了哪些大类"。

### 3. 更新 `CHANGELOG.md`

按语义化版本，写清「新增 / 变更 / 修复 / 移除」。

格式：

```markdown
## [1.3.0] - 2026-03-14

### 新增
- 邮箱密码登录（INC-0007: 时区处理）
- 密码错误提示与三次锁定

### 变更
- 登录态从 session 改为 JWT（ADR-0003）

### 修复
- 修列表空数据崩溃（INC-0005）

### 移除
- 移除旧的 cookie 登录接口
```

**规则：**

- 每条都要能被追溯到 ADR 或 INC 编号（有的话）
- 版本号：新功能 → MINOR；只有修复 → PATCH；破坏性变更 → MAJOR
- 不写"优化若干细节"这类无法追溯的话

### 4. `docs/INDEX.md` 完整性检查

```bash
# 找出 docs/ 下没登记进 INDEX 的文件
for f in $(find docs -name '*.md' -o -name '*.html' | sort); do
  grep -q "$(basename "$f")" docs/INDEX.md || echo "未登记: $f"
done
```

**未登记的一律补上。** 索引的价值在于"能查到"，漏一条就断一条链。

同时检查可追溯性：

- 每个 `ALIGN-*.md` 是否被 `prd.md` 引用
- 每个 `INC-*.md` 是否在 `STATE.md` 或 `REVIEW-CODE` 里被引用
- 每个 `ADR-*.md` 是否在 `DESIGN.md` 里被引用

孤立文档 = 死了的文档。

### 4.5 写开发事件记录（铁律三之二）

这是归档阶段**必做**的动作，不是可选项。

**两层，各写各的：**

```bash
# 1. 记录层：一条完整记录
dev/handoff/H-<编号>-<短名>.md
```

```markdown
# H-0012 加了导出功能

- **时间**：2026-10-21
- **谁**：agent（会话 23）
- **事件**：实现 CSV 导出
- **为什么这样处理**：你没说格式，我按「能直接发给客户」理解，选了 CSV
- **怎么处理的**：`src/export/csv.py`，42 行，commit `a1b2c3d`
- **地点**：`src/export/csv.py:42`（代码问题 → 文件:行号；需求变更 → 办公场所/客户现场）
- **试过什么**
  - ❌ Excel：手机上打不开 → 放弃
  - ✅ CSV：能跑通，但丢表格线
- **下一步 / 等谁**：〔未知〕你能否接受丢格式
- **上接**：H-0009（提出导出需求）
- **下接**：暂无
```

```bash
# 2. 索引层：一行
dev/HANDOFF.md
```

```markdown
| H-0012 | 2026-10-21 | agent | 实现 CSV 导出 | 待确认 | [H-0012](handoff/H-0012-加导出.md) |
```

**七要素一条都不能缺**，其中两条最容易漏：

| 容易漏的 | 为什么最要紧 |
|---|---|
| **试过什么（成没成）** | 不写，下一个 agent 会把失败的路重走一遍 |
| **下一步 / 等谁** | 不写，读的人知道发生了什么，但不知道该怎么办 |

**事实 / 推断 / 未知 必须分开标。** 把「我猜的」写成「就是这样的」，是交接里最危险的错误。

细则见 `.ai/99-reference/handoff-schema.md`，`gate.sh S7` 会检查七要素与索引配对。

### 4.6 docs 分 develop / public

| 目录 | 放什么 | 读者 |
|---|---|---|
| `dev/` | 开发过程文档：align / prd / design / adr / incidents / reviews / handoff | 开发时的人和 agent |
| `docs/public/` | 交付文档：给项目使用者看的说明、验收材料 | 项目使用者 |

**判据只有一条：这份文档是「做的时候用的」还是「交出去给人看的」。**

`STATE.md`、`CHANGELOG.md`、`docs/INDEX.md` 留在根目录，不归任何一边。

### 5. 归档 demo 与临时产物

| 产物 | 处理 |
|---|---|
| `docs/design/demo/*.html` | **保留**（它是设计的证据，用户确认过的那一版） |
| 调试用的一次性脚本 | 删除，或移入 `archive/scripts/` |
| 大体积测试数据 | 移入 `archive/fixtures/`，不留在 `tests/` |
| 旧的 RELEASE 草稿 | 移入 `archive/releases/` |

`archive/` 目录规则：

```
archive/
├── scripts/     一次性脚本
├── fixtures/    大体积测试数据
├── releases/    历史交付说明（超过 2 个版本的）
└── README.md    说明什么该放这、什么不该
```

**不进 archive 的：** 源码、测试、docs 下的正式文档（它们本身就是资产）。

### 6. 打 tag

```bash
# 在合并到 main 之后打
git tag -a v1.3.0 -m "v1.3.0 用户登录"
```

**tag 必须在合并后的 main 上**，不在功能分支上。理由：tag 指向的应该是"可运行的完整状态"。

tag 命名与 CHANGELOG 版本号**必须一致**。不一致 = 门禁 FAIL。

### 7. 提交归档改动

```bash
git add -A
git commit -m "chore(archive): v1.3.0 归档 — STATE / CHANGELOG / INDEX / tag"
```

## 必备制品

| 制品 | 路径 | 要求 |
|---|---|---|
| 状态快照 | `STATE.md` | 已整体重写，≤40 行，下一步可执行 |
| 概念固化 | handoff 记录「**新词**」一行 | 本任务产生的新词全部有词条（升 `已定` 或 `暂定` 待验收），无新词写「无」——铁律七 |
| 事件索引 | `dev/HANDOFF.md` | 一行一条，表头齐全，与记录文件一一对应 |
| 事件记录 | `dev/handoff/H-*.md` | 七要素齐全，「试过什么」非空，上下游链接非空 |
| 变更日志 | `CHANGELOG.md` | 本版本条目含变更类型 + 可追溯编号 |
| 文档索引 | `docs/INDEX.md` | 所有 docs/ 下文件已登记 |
| 版本标签 | git tag | `v<X.Y.Z>`，与 CHANGELOG 一致 |
| 归档说明 | `archive/README.md` | 首次归档时创建 |

## 出口门禁

- [ ] `STATE.md` 已更新，**全文 ≤ 40 行**
- [ ] `STATE.md` 的「当前阶段」已推进，「下一步」是可执行动作（不是"继续开发"）
- [ ] `CHANGELOG.md` 有本版本条目，版本号与 tag 一致
- [ ] `docs/INDEX.md` 无未登记文件（`gate.sh` 会扫）
- [ ] 本版本 tag 已打，且在当前 HEAD
- [ ] **S7 的提交里没有代码文件改动**（只允许 .md / tag）
- [ ] `bash scripts/gate.sh S7` 输出 PASS

## 人工确认

❌ **不需要逐条确认**。但归档完成后必须给用户一份**归档摘要**，让用户有机会纠正事实错误。

摘要格式：

```
S7 归档完成，v1.3.0。

本迭代交付：
- 邮箱密码登录（含三次锁定）
- 修复 2 个历史问题

记录沉淀：
- INC 新增 3 条（时区 / 空数据 / 导出乱码）
- ADR 新增 1 条（登录态改 JWT）

已更新：STATE.md、CHANGELOG.md、INDEX.md，tag v1.3.0

有哪里写错了请指出，我改。没问题就可以进入 S8 交付。
```

> 注意：这里问的不是"可以吗"，而是"有没有写错"。归档的正确性由用户校验，不需要用户批准。

## 常见失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| **STATE.md 只改阶段字段** | 下个会话读到过期的"已完成/下一步"，白读 | 整体重写 |
| **STATE.md 越写越长** | 50 行、80 行，token 优势消失 | 细节进 CHANGELOG，STATE 只留大类 |
| **CHANGELOG 写"优化若干细节"** | 三个月后查不到任何东西 | 每条可追溯到 ADR/INC |
| **忘记打 tag** | 无法定位"哪个 commit 是 v1.3.0" | 合并后立即打 |
| **在功能分支上打 tag** | tag 指向未合并状态 | tag 在 main 上打 |
| **归档时顺手改代码** | S5 评审结论失效 | 铁律：S7 只写文档 |
| **INDEX 漏登记** | 文档链断裂，等于文档不存在 | 跑 find 脚本扫一遍 |
| **把 demo 删掉** | 丢失用户确认过的设计证据 | demo 永久保留 |

---

## Red Flags — STOP

- "STATE.md 改一下阶段号就行" → 下个会话会被误导
- "CHANGELOG 等发版时一起写" → 到那时细节已经忘了
- "这个改动太小不用记" → 小改动堆积起来就是"这个功能哪来的"
- "顺手把这行代码也改了" → S7 禁止改代码，评审结论会失效
- "tag 下次再打" → 下次你就找不到这个 commit 了

---

## 与其他阶段的边界

| | S5 校验 | S7 归档 | S8 交付 |
|---|---|---|---|
| 做什么 | 审代码 | 固化状态 | 写给人看的说明 |
| 改代码吗 | ✅ 改（修问题） | ❌ 禁止 | ❌ 禁止 |
| 产出 | REVIEW-CODE | STATE / CHANGELOG / tag | RELEASE |
| 读者 | 自己 | 下一个会话的 agent | 使用这个项目的人 |

**一句话区分**：S5 问"对不对"，S7 问"记下来了吗"，S8 问"别人会用吗"。
