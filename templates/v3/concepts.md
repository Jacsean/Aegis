# 概念表（术语表）

> **本表是本项目唯一的概念定义处。** 任何文档里出现的概念词，含义以本表为准。
> 文档开头若要说明用词，只放一句话 + 指向本表；**定义只在本表写一次。**

---

## 为什么必须有这个文件

人和 AI 协作时，最大的偏移来源不是技术，是**同一个词被两边理解成不同东西**。

会话一结束上下文就没了。只有固化成文字的词条能跨过去，
让下一个接手的人（或 agent）不必从头问一遍"你说的 X 是什么意思"。

**空表也比没有强**：有了位置，遇到分歧时才有地方落笔；没有位置，分歧只会留在对话里然后消失。

---

## 收录判据（三条同时满足才收）

> 依据：GB/T 10112-2019 / ISO 704 术语工作原则

1. **至少使用两次** —— 只用一次的词不必立条
2. **不同人/不同语境下理解会不一致** —— 大家都懂的不必立条
3. **尚无定义，或已有定义需要改写** —— 已有明确定义的不必重复

**反过来说**：代码里的变量名不需要立条（代码本身就是定义）；通用技术词不需要立条（查得到）。

---

## 条目写法

| 要求 | 说明 |
|---|---|
| **内涵定义** | = 上位概念 + 区别特征。不用否定式定义，不循环定义 |
| **「不是什么」必填** | 至少一条，用来划边界 |
| **长度** | 单条 100~150 字；超了说明该拆成两条 |
| **附例句** | 词义由语境圈定，没有例句的定义是悬空的 |

## 什么时候该往这里加词

| 情况 | 动作 |
|---|---|
| 你和 agent 对某个词反复确认过两次以上 | 加一条 |
| 发现同一个词在文档里有两种用法 | 加一条，并统一现有文档 |
| 引入了一个新概念、且它会出现在多份文档里 | 加一条 |
| 只是代码里的命名 | **不加**，改代码或加注释即可 |
| 通用技术名词（API / 数据库 / 缓存） | **不加**，查得到 |

---

## 维护规则

- **只增不删**：删词会让旧文档失去锚点。确实不用了，标记为「已废弃 → 被 X 取代」
- **改要留痕**：在条目里加一行 `> 2026-XX-XX 修改：原为「……」，因为……`
- **一条一处**：同一概念只在本表定义一次，别处只引用
